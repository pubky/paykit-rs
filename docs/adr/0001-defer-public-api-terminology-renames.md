# Defer terminology renames to a deliberate breaking-change release

We aligned Paykit domain language around Payment Endpoint Identifier, Payment Endpoint Payload, Payment List, and Private Payment Envelope, but existing Rust, FFI, generated binding, runtime string, and wire/protocol surfaces still expose legacy names such as `PaymentEndpointIdentifier`, `PaymentEndpointPayload`, `PaymentList`, `PrivatePaymentEnvelope`, `payment_endpoint_identifier`, `payment_endpoint_payload`, `fetch_payment_list`, and `paykit.private_payment_envelope`.

We will not rename those surfaces in the terminology-cleanup pass. Docs and comments should mark the legacy mapping clearly. The actual rename will happen only in a deliberate breaking-change release that updates public Rust APIs, public FFI/generated binding APIs, runtime logs/errors, tests, downstream integration guidance, and wire/protocol message names together.

The intended breaking-change direction is to rename everything user-, developer-, and protocol-visible to the canonical Paykit language. That includes public API names and FFI names. It also includes serialized/wire names and message kinds.

When the wire/protocol rename happens, Paykit will hard-break old wire names rather than preserving backward read compatibility. New versions should write and read only canonical protocol names. Old names such as `paykit.private_payment_envelope` should be rejected or treated as unsupported rather than silently accepted. This is intentionally protocol-breaking: old peers or queued old messages may stop working, but the protocol language becomes unambiguous and avoids carrying legacy aliases forward.

The hard-break rename does not by itself require bumping the current private message envelope version. Unless the payload schema changes independently, the envelope version should remain at the current value. The canonical message kind/name can change while preserving the existing envelope version semantics.

The canonical future private payment message kind is `paykit.private_payment_envelope`. It replaces `paykit.private_payment_envelope` in the breaking rename pass and matches the canonical domain term Private Payment Envelope.

The Receipt Access message kind stays `paykit.receipt_access`. It already matches the canonical domain term Receipt Access, and adding suffixes such as `_envelope` or `_message` would add churn without improving clarity.

In the FFI crate, `FfiPaymentEndpoint` should become `FfiPaymentEndpoint`, and `FfiPrivatePaymentEnvelope` should become `FfiPrivatePaymentEnvelope`. The `Ffi` prefix remains useful inside the FFI boundary because it distinguishes boundary DTOs from future core domain types such as `PaymentEndpoint` and `PrivatePaymentEnvelope`. Generated Swift/Kotlin names should strip the `Ffi` prefix if UniFFI configuration allows this cleanly, so platform consumers see domain names rather than Rust boundary implementation details. FFI payment-list results and private-envelope endpoints should continue using vectors of endpoint DTOs, such as `Vec<FfiPaymentEndpoint>`, rather than mirroring Rust core maps directly; arrays of records are more portable across generated bindings and preserve the whole Payment Endpoint concept.

FFI and generated binding functions should mirror Rust high-level helper names such as `paykit_get_payment_list` / `getPaymentList`, not platform/network idioms such as `fetchPaymentList`. FFI exposes Paykit Library helpers, not transport traits; using `fetch` at the binding layer would blur the distinction between transport retrieval and user-facing helpers. Rust FFI exports can keep the `paykit_` prefix to avoid global/boundary collisions, but generated Swift/Kotlin/platform APIs should expose clean module-scoped names such as `getPaymentList` rather than `paykitGetPaymentList` when the module/package already provides Paykit scope.

The core Paykit Library should rename `PaymentEndpointPayload` to `PaymentEndpointPayload`, not the shorter `EndpointPayload`. The longer name matches the thesaurus exactly and avoids ambiguity with Pubky, HTTP, API, or transport endpoints. `PaymentEndpointPayload::new()` should remain a generic UTF-8 payload wrapper, not become identifier-aware validation. Identifier-specific validation belongs in higher-level payment-provider integrations or future Paykit Daemon logic. It should not enforce a generic maximum size; public and private storage constraints differ. Size limits should be enforced where they actually exist, such as transport/storage adapters or the Private Payment Envelope serialization path that must fit within the pubky-noise message limit.

The core Paykit Library should rename `PaymentEndpointIdentifier` to `PaymentEndpointIdentifier`, not the shorter `EndpointIdentifier`. The longer name matches the thesaurus exactly and avoids ambiguity with Pubky endpoints, transport endpoints, API endpoints, and HTTP endpoints. `PaymentEndpointIdentifier::new()` should keep the current loose structural validation: path-safe ASCII identifier, max length, and reserved-word checks. It should not enforce the recommended `asset-rail-endpoint-format` convention unless that convention is separately promoted from recommendation to protocol rule. It should also keep the current allowed character set — ASCII alphanumeric characters, hyphen, underscore, and dot — rather than tightening to lowercase alphanumeric plus hyphen only. The constructor should preserve input exactly and must not lowercase or otherwise normalize identifiers, because implicit normalization would change path-key identity semantics and could create collisions.

The core Paykit Library should introduce a real `PaymentEndpoint` struct in the breaking rename pass. A Payment Endpoint is the whole list entry, so the public API should expose that concept directly. The intended shape is a plain public-field struct containing a `PaymentEndpointIdentifier` and a `PaymentEndpointPayload`. No additional constructor invariant is needed beyond each field's own validation, because Paykit does not perform identifier-aware payload validation in the core library.

`PaymentList` should expose its endpoints as a public map field keyed by `PaymentEndpointIdentifier`, with values as `PaymentEndpointPayload`, rather than as a `Vec<PaymentEndpoint>`. This preserves efficient identifier lookup and matches the storage semantics where each Payment Endpoint is stored at a path keyed by its identifier. The `PaymentEndpoint` struct should still exist for APIs that deal with a single whole endpoint, FFI boundary DTOs, iteration helpers, or conversions, but the primary `PaymentList` representation remains keyed by identifier. Empty Payment Lists should be valid; they represent a payee with no currently published or discoverable Payment Endpoints, and callers can decide whether that state is acceptable. The field should be public because there are no additional list-level invariants beyond valid key/value types.

The `PaymentList` map field should be named `endpoints`, not `entries`. The canonical thing contained by a Payment List is Payment Endpoints, and `entries` is too generic.

The public getter should remain `get_payment_list`, not `get_public_payment_list`. Payment List already means the payee-published/shared list, and adding `public` risks implying a corresponding Private Payment List, which Paykit explicitly avoids. Supported Payment List remains a domain term for the payer-side intersection between payer capabilities/preferences and a payee's Payment List; it should not become a public type/API until Paykit actually implements that intersection workflow. The current `PaymentList` type should become `PaymentList`, not `PublicPaymentList`, because it represents the payee's Payment List.

Single-endpoint public APIs should remain `get_payment_endpoint`, `set_payment_endpoint`, and `remove_payment_endpoint`, not become `*_payment_endpoint_payload`. These operations address the whole Payment Endpoint identified by its Payment Endpoint Identifier, even when the returned or stored value is a Payment Endpoint Payload.

Transport trait method `fetch_payment_list` should become `fetch_payment_list`. Transport trait methods should keep the `fetch_*` verb while high-level helpers keep the `get_*` verb: `fetch` communicates network/transport retrieval, while `get` is the user-facing library helper. This keeps layers distinguishable without domain-term drift.

The `PrivatePaymentEnvelope` map field should also be named `endpoints`, not `entries`. The current field contents are private Payment Endpoints, and naming the field specifically leaves room for other envelope fields later without preserving ambiguous terminology. Empty `PrivatePaymentEnvelope` endpoint maps should be invalid: an envelope is a payment/request-specific private endpoint disclosure, and empty disclosure would be ambiguous. If clearing or revocation is needed later, it should get an explicit concept/message rather than overloading an empty endpoint map. Because non-empty endpoints are an invariant, the field should be private and constructed through `PrivatePaymentEnvelope::new(...)`, with read/consume accessors such as `endpoints()` and `into_endpoints()`.

`PrivatePaymentEnvelope` keeps its public `reference: PaymentReference` field. In Paykit's private payment flow, the latest-state private endpoint envelope intentionally carries the per-payment/per-request correlation ID. Even though the envelope is latest-state data, the Payment Reference is part of the private payment disclosure state and should remain in the envelope rather than moving to a separate request wrapper. The reference can stay public because `PaymentReference` is already a validated UUID-v4 type and there is no extra structural invariant to protect. `PaymentReference` should remain UUID-v4 rather than becoming a generic caller-supplied correlation string.

Receipt-related structs and bindings should rename fields such as `payment_endpoint_identifier: Option<PaymentEndpointIdentifier>` to `payment_endpoint_identifier: Option<PaymentEndpointIdentifier>`. The stored value is a machine identifier, not the higher-level human/domain Payment Method, so keeping `payment_endpoint_identifier` would preserve the ambiguity the breaking rename is meant to remove. Serialized receipt JSON fields should hard-break the same way: `payment_endpoint_identifier` becomes `payment_endpoint_identifier`.

Future functions that get/set the private envelope should use singular canonical names such as `get_private_payment_envelope` and `set_private_payment_envelope`. The function returns or writes one latest-state Private Payment Envelope, so plural `private_payment_envelope` should not survive the breaking rename pass.

Receive semantics for Private Payment Envelopes should be latest-state per Known Peer, not latest-state per Payment Reference. If multiple envelopes are queued, the newest envelope supersedes all older Private Payment Envelopes, even when older envelopes have different Payment References. This means `PaymentReference` identifies the payment/request represented by the latest private payment disclosure; old disclosures are not retained as separate active state.

The primary low-level receive API should be singular: `get_private_payment_envelope(link) -> Option<PrivatePaymentEnvelope>`, returning only the latest currently available Private Payment Envelope. It should not return a list of envelopes keyed by Payment Reference.

The primary send API should be singular: `set_private_payment_envelope(link, envelope: &PrivatePaymentEnvelope)`. Sending one private payment disclosure for one Payment Reference is the natural unit of work. Bulk send can be added later if needed, but should not be the primary API because it creates avoidable ambiguity around ordering and supersession.
