# Paykit v0.2 specification (Path A)

**Status.** Review candidate, not frozen. The spec has had two rounds of peer review, an independent review, a package review, a package recheck, and four reviews of 2 and 3 November: a code review, a crypto design audit, a gaps review and a further design review. The fix round for those four is done (2026-11-03), and so are the changes from the follow-up review of 4 November (2026-11-04). Each finding, with its status (fixed, fixed and retested, accepted risk, deferred, team decision, production plan or wording), is in the review records, which are shared separately; none is open. The second prototype phase implements the spec, and the wire format (`specs/v0.2/wire-format.md`) is complete, with test vectors. A clean-room implementation reproduces every vector, after its twelfth pass (2026-11-05), whose gaps are settled (Section 23). The spec is frozen once the package recheck's reviewer has checked its two retention fixes (Sections 6.3 and 8.4), the team has decided the open questions and the team decisions (Section 22), and an independent human crypto review and the measurements on real infrastructure are done (Section 23).

**Design rule for implementations.** Each user action needs at most one call to each Pubky Switch involved (the counterparty's, for the message, and the identity's own, for claims and shared state), sent in parallel, before the user sees its result, plus local bookkeeping. Follow-up messages, such as the acceptance after an attempt, go in the background. The only other calls allowed are the background and parallel Homeserver calls listed in Section 18, and one re-send when the counterparty's inbox answers `stale_key` because a recipient app has just replaced its receive key or the recipient has added an app (Sections 3.7 and 8.1). A first message to a new counterparty also reads its directory, writes its conversation entry and may deliver the sender's `identity.json`, in one parallel round before the append (Sections 7 and 18).

## Terms

| Term | Meaning |
|---|---|
| **Identity** | A Pubky identity, named by its Ed25519 public key. |
| **Signer** | The software holding the identity key: Ring, or Bitkit acting as signer. |
| **Paykit App** (app) | One application acting for an identity in Paykit, with its own keys and certificate. An app may run on several devices; Paykit treats it as one app (Section 3.1). |
| **App ID** | The identifier of an app, derived from its signing key. |
| **Current app** | An app listed in the identity's newest `identity.json` that the switch hasn't revoked or recorded as departed (Section 3.5). |
| **Own app** | A current app of the identity in question. |
| **App record** | An app's public, self-signed description: signing key, certificate, accepted message kinds, optional public endpoints. |
| **Bundle key** | An app's static X25519 key, named in its certificate, to which the signer seals its key bundles (Section 3.6). |
| **Receive key** | An app's current X25519 encryption key for messages. A fresh random key replaces it after the app reads its feed, about once a day by default (Section 3.7). |
| **Receive key record** | The app-signed record of an app's current receive key, held by the switch and returned by its directory (Section 4.4). |
| **`identity.json`** | The identity-signed document naming the switch, the current apps, removed apps and the current data epoch. |
| **Version** | The counter of `identity.json`; it increases on every update. Shared records, Private Payment Lists and the chain have versions of their own (Sections 5.4, 10.3 and 14.6). |
| **Generation** | The counter of the switch named in `identity.json`; it increases when the identity moves to another switch and after a provider loss (Section 13.6). |
| **Scope** | A permission string in an app's certificate, such as `pay` or `request`. |
| **Shared Data Key** | Identity-wide keys, one per scope and data epoch, that encrypt data shared between own apps. |
| **Data epoch** | The counter of the Shared Data Key; it increases on each rotation. |
| **Key bundle** | An app's scope keys for the data epochs it lacks, and the naming key, sealed to its bundle key by the signer (Section 3.6). |
| **Naming key** | An identity-wide key that blinds natural keys and obligation inputs, so the keys of records and claims don't name their counterparty (Section 3.6). |
| **Pubky Switch** (switch) | The service that receives an identity's messages and hosts its coordination primitives. Its mailbox part, where senders' messages land and apps read them, is the inbox. One service hosts many identities, like a Homeserver; each identity uses one service at a time. |
| **Inbox entry** | One encrypted message stored for one or more target apps. |
| **`seq`** | The position of an item at the switch within one generation. Inbox entries and chain items share one sequence. |
| **Feed** | The ordered stream an own app reads: the items after its cursor that it may read, and chain stubs for the other chain items. |
| **Cursor** | An app's position in the feed. |
| **Chain** | The hash chain over operations, `identity.json` deliveries and service transitions, one per generation (Section 8.4). Inbox entries and cursor moves are not in it. |
| **Chain stub** | A chain item's `seq` and hashes, without its content. |
| **Signed head** | The service-signed chain hash at a given `seq`. |
| **Conversation entry** | An allowlist entry an app adds for a counterparty it writes to or invites, so that the two can keep talking until the user blocks the counterparty (Section 7). |
| **Invite** | A conversation entry added before any message, so that the counterparty can write first, for example a shop at checkout (Section 7). |
| **Connect request** | A content-free request from a stranger to be invited, which an identity may allow (Section 7). |
| **Invite code** | A random code an app registers at its own switch and shows, for example as a QR code, so that anyone who has it can write once and start a conversation (Section 7). |
| **Obligation** | Something that must happen at most once, such as paying one request in one Billing Period. |
| **Billing Period** | One period of a recurring request, computed as in Section 11.2. |
| **Claim** | The server-checked state of one obligation. |
| **Attempt** | One try at carrying out an obligation, such as one payment, with its own outcome. |
| **Step** | The position of an entry in one obligation's log. |
| **Shared record** | A small piece of encrypted shared state, updated by compare-and-swap. |
| **Collection** | A set of shared records that can be listed together. |
| **Policy** | The scopes a shared record requires, fixed at creation. The admission settings in `identity.json` are also called `policy` (Section 4.3). |
| **Operation** | A change sent in a batch: a claim entry, a shared record write, an allowlist or deny list change, a cursor move, an app record, a receive key registration or a key bundle. All are signed by their writer except cursor moves, which the request signature covers. |
| **Transition proof** | The service-signed result of one operation, with its place in the chain. |
| **Condition** | A requirement attached to an operation, checked atomically with it. |
| **Batch** | Up to 8 operations and their conditions, applied all or nothing. |
| **Executor** | The one app that an Allowance record names, with the app's own signed grant, to pay automatically under that Allowance (Section 11.3). |
| **Push relay** | A vendor-run service that turns signed webhooks into APNs or FCM pushes. |
| **Handle** | An opaque ID the push relay maps to one device. |
| **Push key** | The signing key the switch mints for one app's push registration; it signs that app's webhooks and appears in no public document (Section 9). |
| **Paykit Profile** | Optional public display metadata of an identity at `/pub/paykit/profile.json`, with v0.1 semantics. |

## 1. Goals and product restrictions
- **Goals:**
  - Payments between Pubky identities; Pubky is the only identity layer required.
  - About one round trip per action, independent of contact count or history size.
  - Several apps per identity, isolated by scope, sharing only what their scopes allow.
  - Payment-method agnostic: the protocol never interprets rails, addresses, amounts' meaning, or proofs.
  - Feature agnostic: the switch offers generic primitives (claims and shared records). Features such as Allowances are built in apps, without changes to the switch.
  - An identity can move to another provider without the old operator's cooperation.
- **Product restriction:**
  - v0.2 has **no unsolicited first contact by Pubky ID alone**.
  - A sender must be on the recipient's allowlist: a contact, or a conversation the recipient started or invited, for example at a checkout.
  - Strangers can't message without an invite. An identity can hand out invite codes, for example a shop's QR code, and, where the user allows it, strangers can ask to connect (Section 7). Messaging without either is deferred.

## 2. Components

| Component | Role |
|---|---|
| **Signer** (Ring, or Bitkit as signer) | Holds the Pubky identity key. Approves apps, signs `identity.json`, derives Shared Data Keys and writes key bundles, enrolls the identity at the switch, performs revocation, key rotation, freeze and recovery. An identity has one signer at a time; it can hand the identity to another signer (Section 13.8). |
| **Paykit App** | Its own keys, scopes, local data, outbox, cursor and payment journal. |
| **Homeserver** | Long-term data: `identity.json`, the records of apps with public payment endpoints, the Paykit Profile, optional encrypted backups. |
| **Pubky Switch** (hosts many identities; each identity uses one at a time, chosen by the user) | Inbox and feed, allowlist and deny list, the coordination primitives (claims and shared records), app records, key bundles, receive key records, push hooks, directory, revocation, freeze, export and recovery. |
| **Push relay** (per app vendor; a reference relay is published) | Turns signed, content-free webhooks into APNs or FCM pushes. |

- The switch is a separate service with its own operator. Closer coupling with Homeservers may come later; the protocol stays decoupled either way, since `identity.json` can point to any switch.
- There is no ordering server and no federation.

## 3. Keys, apps and authorization

### 3.1 Keys
- **Identity key:** exists only in the signer and the signer's backups. Whoever holds it, or the seed it comes from, derives `paykit_root` (Section 3.6), and with it the naming key and every data epoch's scope keys: all of the identity's sealed data, past and future.
- **Each app** holds three keys:
  - **Signing key** (Ed25519, static): signs messages, requests to the switch, operations, its own record and its receive key records. It changes only when the app is replaced.
  - **Bundle key** (X25519, static): named in the app's certificate. Only key bundles are sealed to it (Section 3.6).
  - **Receive key** (X25519, rotating): messages to the app are wrapped to it. Each receive key is a new key, from fresh random bytes as recommended, with a number `n` and an 8-byte key ID (kid, Section 14.3). It rotates as Section 3.7 describes.
- **Restoring from backup** keeps the signing key, the bundle key and the receive key it held at the backup (Section 13.4).
- **Derived keys:** an app may derive its signing and bundle keys from a secret it already backs up, such as a wallet's seed, under its own derivation labels, so that restoring that secret brings the app back without a new approval. Devices restored from one secret are one app (several devices, below). Receive keys stay random, so the backed-up secret reveals no message sealed to them. It does give the signing key, which can register new receive keys until the app is revoked (Section 3.7).
  - **Recommended profile** (not normative): derive both keys from the secret with the identity's Pubky ID and an index as inputs, for example `derive("<app label>/paykit-app-key", secret, identity, u64(index))` and a second label for the bundle key, so that one secret approved for two identities gives two unrelated App IDs. A revoked or departed App ID is never approved again (Section 13.2), so after a revocation the app derives its next keys with the next index and joins as a new app. A new index doesn't help if the secret itself leaked: whoever holds it derives every index.
- **App ID:** the first 16 bytes of `BLAKE3(signing public key)`, z-base-32 encoded. An App ID names an app; it never stands in for its keys: wherever a key matters, apps compare the key itself, or a kid derived from it (Section 3.7).
- **Where keys live:** an app keeps its secret keys (signing, bundle, receive and scope keys and the naming key) only in storage that is bound to the device and not backed up: on iOS, keychain items whose class ends in `ThisDeviceOnly`, one item per receive key, in one access group shared with the push extension (Section 9); on Android, the Keystore or files excluded from backups. Never in plain files of the app's container or a shared App Group container, which go into iCloud and computer backups by default. Other local state that a key could be derived from or that holds key material, such as a journal, is encrypted at rest under a key kept the same way. The app's own backups (Section 13.4) are separate and follow their own rule. Zeroizing keys in memory and platform keystores are production work, on the plan list, not in the prototype.
- **Deleting a key** means removing it from every copy the app keeps: its key store item, any file, journal entry, cache or snapshot that holds it, on every device that has it, and in any backup the app controls, so that no copy left behind can open what was sealed to it. Overwriting an in-memory value, or dropping it from the app's current state while an append-only journal or snapshot still holds it, isn't deleting it. Forward secrecy (Section 17) assumes this definition.
- **Several devices** are each integrator's choice. Every device can be its own app, or one app can run on several devices with the same keys, which the integrator keeps in sync; Paykit sees one app. A claim allows one attempt at a time, but every device holding the app's keys can act on that attempt. The app therefore makes sure only one device carries out a given attempt, for example by passing the attempt ID to the payment method as its idempotency key, and keeps its cursor, receive keys, payment journal and local state consistent across devices. Such an app is one principal: a stolen device needs no registration of its own to act and read as the app, so losing any of its devices means revoking the app and approving it again. One app per device is recommended.

### 3.2 App certificate
The signer issues a certificate for each app, signed with the identity key (Section 14.2). It delivers the certificate in the approval, the companion claim of the app's Pubky grant approval (`specs/pubky-auth-companion-claims.md`), so one approval gives the app its Pubky grant, its certificate, its scope keys and the naming key (Section 3.6):

```json
{ "v": 1, "kind": "paykit.app_cert",
  "identity": "<pubky id>", "app_id": "<app id>",
  "signing_key": "<ed25519>", "bundle_key": "<x25519>",
  "scopes": ["pay", "request", "allowance", "allowance_execute", "contacts", "manage_contacts"],
  "inbox": ["claims.read", "claims.write", "lists.read", "lists.manage", "conversation.add"],
  "issued_at": "<rfc3339>", "expires_at": "<rfc3339>" }
```

- **Later suites:** a certificate may carry `suite_keys`, a list of bundle keys of later suites, each tagged with its suite number (the envelope's suite byte, Section 5.1). It is the one place a later suite, such as a post-quantum key encapsulation, adds a key, so it needs no `v: 2` certificate. No suite but suite 1 exists in this version: signers write no `suite_keys`, and readers check its form (`specs/v0.2/wire-format.md` Section 3.1) and ignore the keys of suites they don't support. The receive key record reserves the same member (Section 4.4).
- **Approval** (`specs/v0.2/wire-format.md` Sections 3.10 and 3.11). The app asks with an app request signed by its signing key, which proves it holds that key, and binds the Pubky auth request it travels with: its client ID, its client key, the exact capabilities and the hash of its secret. The signer checks the request (its bundle key not of low order, every scope one it knows), derives the App ID from the signing key and the app's paths from the App ID, requires the capabilities to be exactly those paths (Section 3.5), refuses an App ID that is listed with other keys, removed or revoked before (Section 13.2), and shows the user the App ID. The approval it returns carries only public material and one sealed bundle: the certificate, the `identity.json` that lists it, and the app's full key bundle made for that certificate (data epochs 1 to the current one, with the naming key), sealed to the certified bundle key and signed by the identity key (Section 3.6). The app checks that the certificate names its own signing and bundle keys and opens the bundle as it opens every later one. So the auth request's secret, which anyone who sees the QR code or deep link holds, protects only the handshake: the claim it unlocks holds no key. A request naming an App ID listed with the same keys renews that app's certificate.
- **Lifetime:** every certificate expires. The signer sets `expires_at` 1 year after `issued_at` by default and never more than 2 years after. Every reader enforces this too: a certificate without `expires_at`, or one that expires more than 2 years after its `issued_at`, is invalid at apps, at the switch and at payers (`specs/v0.2/wire-format.md` Section 3.1). At each run it renews the certificate of every current app once less than half its lifetime remains, with a later expiry (renewal, below), so an app the user keeps never lapses, and a revoked app's key stops working everywhere, at switches that never learned of the revocation too, once its certificate expires.
- **`scopes`** are Paykit permissions, which apps check (Sections 3.4 and 3.5).
- **`inbox`** lists the switch permissions the app holds, which the switch checks. The service authorizes calls by `inbox`, never by `scopes`, which it reads only to check `inbox` and as strings named in a shared record's policy (Section 10.3). The signer sets `inbox` from the scopes, using the table in Section 3.3. Every verifier, at apps, at the service and at payers, derives the list again from the scopes and refuses a certificate whose `inbox` is any other list, so a certificate never carries a permission its scopes don't grant (`specs/v0.2/wire-format.md` Section 3.1). A change to that table therefore needs a new certificate version (`v`).
- **Renewal.** The signer renews a certificate to change its expiry or scopes, keeping the app ID, signing key and bundle key, with a later `issued_at`:
  1. The signer stores the new certificate at the service (operation `cert.put`, Section 14.5), with a full key bundle made for it (Section 3.6). The bundle replaces every key bundle part stored for the app, whether the renewal adds a scope, removes one or keeps them all.
  2. It delivers and then publishes `identity.json` listing the new hash and moving the earlier one into `renewed` with `until: null` (Section 4.3). From this delivery the service checks the app against the new certificate.
  3. The app finds `cert.put` in its feed, takes the new certificate once its own `identity.json` lists it, and delivers its updated record (`app.put`), republishing it on the Homeserver if it has public endpoints. An app that holds an earlier certificate than the one its `identity.json` lists and has no `cert.put` for it, as after a restore from a backup older than a renewal it took (Section 13.4), takes the listed one from its own app record in its directory, which carries it (Section 4.2). It takes it only if the record is signed with its own signing key and the certificate verifies for the identity, names its own App ID, signing key and bundle key, is issued after the one it holds, and has the hash `identity.json` lists for it.
  4. Once the service holds that record, the signer sets `until` to the time the service took it plus the clock tolerance (5 minutes, Section 12), at its next delivery. A renewal isn't a distrust event, so the tolerance goes on the side that keeps the app's last messages: the app stops presenting the earlier certificate when the service takes its new record, and recipients then reject only messages accepted after that.

  - **Reductions close at once.** A renewal that removes a scope or a switch permission, or makes the certificate expire earlier, is a reduction, and its cutoff can't wait for the app, which may never take the new certificate. Right after the delivery of step 2, the signer delivers another `identity.json` that sets `until` of every open renewal of the app to the service time at which the service took that delivery (from the delivery's transition proof, which a retry of the delivery gets too) plus the clock tolerance, and then publishes it. The cutoff is signed by the identity key and needs nothing from the app. A signer stopped between the two deliveries finds the closing delivery it owes at its next run, before any other delivery or provider change: every open renewal that was a reduction, which it judges from the certificates it issued. It delivers the renewing version again, and that retry's answer carries the delivery's proof (`specs/v0.2/wire-format.md` Section 3.9). Messages accepted before the cutoff keep counting (Section 12). A closed renewal leaves the earlier certificate current nowhere: a switch holding the newer document refuses it, and recipients reject messages carrying it that their inbox accepted after the cutoff. A sender stops wrapping to the app from its next send after it sees the closing document, until the app delivers a record with its new certificate. It sees that document through the Homeserver event stream, from an append answer with a newer `directory_version`, or when it re-fetches a copy more than 10 minutes old (Section 8.1). Until then its appends may still wrap kinds the app may no longer receive, and the inbox can't refuse them, since kinds are sealed. So a removed receiving scope stops at most the sender's directory cache lifetime after the cutoff, while a removed sending scope stops at the cutoff. Own apps deliver the closing `identity.json` to the switches they wrote to recently, as after a revocation (Section 13.2 step 5). Step 3 then only brings the app's record up to date, and step 4 has nothing left to close. Renewals that only add scopes or extend the expiry keep the cooperative flow of steps 3 and 4. Senders tie their cached directories to the `identity.json` version they were read under, and read them again when they see a newer one (Section 8.1), so an app given a new scope receives its kinds as soon as it has delivered its new record.
  - **A removed scope's keys rotate.** The app keeps every key it holds for the data epochs so far, and later writes would go on using the current epoch. So a reduction that removes a scope with keys also rotates the data epoch, as a revocation does (Section 13.2): a Paykit scope, a labelled selling scope, whose label keys go, or plain `request` replaced by labels, whose key derives every label's. Removing only extension scopes rotates nothing, since they have no keys. The full bundle of step 1 then runs through the next data epoch e+1 and is made for the new certificate, so it holds no key of the removed scope for e+1. The signer also stores every other current app's bundle for e+1, each holding that app's own scopes, so only the certificates that keep the scope get its new key. Only then does it deliver step 2's `identity.json`, which raises `data_epoch` to e+1 in the same delivery that lists the new certificate. From then on writes use e+1 (Section 3.6), so the reduced app can't read data under the removed scope written after that delivery, even if a hostile switch, a cache or a backup hands it the ciphertext. What it read before stays readable to it, as for a revoked app.

  While `until` is null the earlier certificate still counts wherever the app presents it, so nothing it sends before holding the new one is refused. Once `until` is set, it counts only for messages accepted more than the clock tolerance before `until` (Section 12). Messages from before a renewal keep the authority they were sent with, as a removed app's do at or before `distrust_from` (Section 12), and so do the app's shared record writes: the service keeps with each record the certificate it checked the write against and the transition proof that dates the write, and readers judge the write by that certificate at that time (Section 10.3). A write by the earlier certificate that no proof dates before the cutoff doesn't count. Removing a scope takes effect at once at the service and, through the closed renewal, at recipients, which reject the app's messages accepted after the cutoff; senders stop wrapping the removed kinds to it from their next send after they see the closing document (above). A removed scope with keys also rotates the data epoch, so the app reads none of that scope's later data (above). An app whose certificate has expired is refused everything, its feed read included, until the signer stores a renewal, which brings it back without anything from the app. Meanwhile it counts as not current for the claim rules, so its open attempts become orphaned (Section 10.2).

### 3.3 Scopes

| Scope | Allows | Requires |
|---|---|---|
| `pay` | Act as payer. Send acceptance, rejection, payer cancellation, proof, Private Payment List requests and resend requests. Receive requests, period details, payee cancellations, receipts, Private Payment Lists and resend requests. Read and write claims. Read and write `payer_activity` and `payment_lists` | - |
| `request` | Act as payee. Send requests, period details, payee cancellations, receipts, Private Payment Lists and resend requests. Receive acceptance, rejection, payer cancellations, proofs, Private Payment List requests and resend requests. Read and write `payee_activity` | - |
| `request:<label>` | Act as payee under one label: what `request` allows, with every request sent under the label, the payer's replies received only for that label's requests, and only that label's `payee_activity` records read and written | - |
| `allowance` | Send and receive `allowance_*` messages and resend requests for them; read and write `allowances`; read `allowance_ledgers` and claims | - |
| `allowance_execute` | Act as an Allowance executor; write `allowance_ledgers` | `allowance`, `pay` |
| `contacts` | Read the contacts, conversation entries and deny list at the switch | - |
| `manage_contacts` | Change the contacts and the deny list | `contacts` |
| `ext:<prefix>` | Send and receive the extension kinds `<prefix>.<name>` (Section 3.4) | - |

- A certificate lists every scope explicitly, including required ones. The signer never issues a scope without the scopes it requires. Every reader refuses a certificate that lists a scope twice, lacks a scope another requires, or holds more than 8 extension scopes or a malformed one (such as `ext:Cap`), or more than 8 labelled selling scopes or a malformed one (such as `request:Shop1`), or a labelled selling scope beside plain `request`; it ignores other names it doesn't know, which a later version may add. The signer refuses an app request naming a scope it doesn't know (`specs/v0.2/wire-format.md` Sections 3.1 and 3.10).
- **Extension scopes:** one scope `ext:<prefix>`, for example `ext:paykit-cap`, covers every message kind whose name starts with that prefix. An app narrows it to the kinds it handles with its record's `accepts` (Section 3.5), which it signs itself, so a new extension kind needs no new certificate and no prompt at the signer. A certificate holds at most 8 extension scopes; the prefix `paykit` is Paykit's own (`specs/v0.2/wire-format.md` Sections 3.1 and 5.3).
- **Labelled selling scopes:** `request:<label>`, for example `request:shop1`, lets a hosted selling app, such as paykit-server, act as payee for its own sales only. The label is 1 to 32 characters of `a-z`, `0-9` and `-`, starting with a letter or digit, the syntax of an extension scope's prefix; a certificate holds at most 8. Payers and the switch see the label, so it should be opaque, like `shop1`, never a name (Section 16). Plain `request` covers every label: an app holding it reads and writes every label's records and gets the payers' replies about every label's requests, so the identity's own wallets show all its sales. So a certificate holds `request` or labels, never both: the signer never issues one with both, it refuses an app request naming both, and every reader refuses such a certificate. A labelled app reads and writes only its label's `payee_activity` records (Section 8.3), under its label's keys (Section 3.6), and gets the payers' replies only about its label's requests (Section 3.5). It has the switch permissions of `request`.
- **Switch permissions** that go with the scopes, for the certificate's `inbox` list (Section 3.2):

  | Switch permission | Lets the app | Given with |
  |---|---|---|
  | `claims.read` | Read claims, and see claim entries in the feed | `pay`, `allowance` |
  | `claims.write` | Write claim entries | `pay` |
  | `lists.read` | List contacts, conversation entries and the deny list | `contacts` |
  | `lists.manage` | Change contacts and the deny list, remove conversation entries, and restore the lists after a provider loss | `manage_contacts` |
  | `conversation.add` | Add conversation entries, including invites | `pay`, `request`, any labelled selling scope, `allowance`, any extension scope |

### 3.4 Message kind to scope

| Kind | Sender needs | Recipient app needs |
|---|---|---|
| `payment_request`, `payment_period_details`, `payment_receipt`, `private_payment_list` | `request` | `pay` |
| `payment_request_acceptance`, `payment_request_rejection`, `payment_proof`, `private_payment_list_request` | `pay` | `request` |
| `payment_request_cancellation` | `request` or `pay` | the other one |
| `allowance_proposal`, `allowance_acceptance`, `allowance_rejection`, `allowance_end` | `allowance` | `allowance` |
| `executor_notice` (own apps only) | `allowance` | `allowance_execute` |
| `resend_request` | Any: every current app of the counterparty may send it | Any; the answer re-sends only kinds the requesting app's certificate receives, and a payer's replies only under the label rule of Section 3.5 (Section 12) |
| An extension kind `<prefix>.<name>` | `ext:<prefix>` | `ext:<prefix>` |

- **Labelled selling scopes** send and receive the kinds of `request`. A `payment_request` carries the signed `label` of the scope it is sent under, and recipients drop one whose sender holds neither `request` nor `request:<label>` for its label, and one without a label whose sender doesn't hold `request`. So an app holding only labelled scopes sends every request under one of its labels. The payer's acceptance, rejection, cancellation and proof copy the request's label (`specs/v0.2/wire-format.md` Section 5.3).
- **Extension kinds** carry no Paykit payment semantics: no payment relies on one, they carry no destination, and no Paykit collection records one. An app that handles one passes it to its extension as it arrives; an app that doesn't know it ignores it, like any kind it doesn't know (`specs/v0.2/wire-format.md` Section 5.1, check 10). Its body follows the JSON rules of every message, the integer rule included, so an extension writes a decimal such as a price as a string, outside the body's opaque `metadata` (Section 14.1; `specs/v0.2/wire-format.md` Sections 1.1 and 5.3).

### 3.5 Authorization rules
- **Current apps only.** An app is current while the identity's newest `identity.json` lists it with its certificate and the switch hasn't revoked it or recorded its departure. The service applies its own revocations and departures at once. Other parties see them through the directory, which drops the app at once (Section 13.2), and through the next `identity.json`. For orphaned attempts (Section 10.2) the service's view decides. Senders, payers and the switch use only current apps' records and keys.
- **Scopes** come only from the signer-signed certificate. An app record's `accepts` may narrow them, never widen them.
- **Senders** wrap a message to an app only if its certificate allows receiving that kind and its `accepts` lists the kind. A payer sends its acceptance, rejection, cancellation and proof for a labelled request only to the payee's apps holding `request` or that label, and for an unlabelled request, or a payment without one, only to those holding `request`. So a hosted app never receives the payer's replies about the identity's own requests. A payee's cancellation carries no label and goes to the payer's apps holding `pay` or `request`.
- **Recipients** drop a message when the sender's certificate lacks the sending scope, or the kind is outside their own certificate. They also drop a payer's reply that the rule for senders above wouldn't have sent them: an acceptance, rejection, cancellation or proof with a label, unless they hold `request` or that label, and one without a label unless they hold `request`, or `pay` for a cancellation, which may be the payee's.
- **Homeserver grants.** Each app's Pubky grant covers exactly these paths, with `<app_id>` derived from the certified signing key, and nothing else:
  - `/pub/paykit/v1/apps/<app_id>.json`, read and write (its record);
  - `/priv/paykit/v1/apps/<app_id>/`, read and write, for an app that keeps its backups on the Homeserver;
  - `/pub/paykit/profile.json`, read and write, only for an app the user allows to edit the Paykit Profile.

  The signer grants these and refuses any capability that covers `/pub/paykit/v1/identity.json`, that path or a folder it lies in, such as v0.1's `/pub/paykit/:rw` or a root grant: only the signer writes `identity.json`, so a grant that covers it would let an app replace it with an older version that still lists a revoked app. It warns the user when another app asks it for such a capability. It revokes an app's grant when the app is revoked or leaves (Section 13.2 step 1). Payers use a record only if its `app_id` is the one in its path (Section 4.2).
  - **From v0.1:** v0.1 apps hold `/pub/paykit/:rw` grants. Before the signer publishes an identity's first v0.2 `identity.json`, it revokes every such grant, or replaces it with one scoped as above.

  No grant carries Shared Data Keys; they travel sealed in the approval's key bundle (Section 3.6).
- **Check order.** The service, recipients, senders and payers check an app in this order and stop at the first failure:

  | # | Check | At the service | A recipient, sender or payer |
  |---|---|---|---|
  | 1 | The certificate is signed by the identity key | `401 bad_signature` | Drops the message, or skips the app |
  | 2 | It names the identity and the app, whose ID derives from its signing key, and that key signs the request, message or record | `401 bad_signature` | As 1 |
  | 3 | It hasn't expired: at the service's time for a request, at the acceptance time for a message, now for sending or paying | `403 cert_expired` | As 1 |
  | 4 | The request, message or app record signature verifies with that key | `401 bad_signature` | As 1 |
  | 5 | Its hash is listed for the app in the newest `identity.json` held, or it is an earlier certificate that still counts (Section 3.2), or the app is removed and the message was accepted at least the clock tolerance before `distrust_from` (Section 12) | Own app: `403 not_current`. Another identity's app: `409 identity_needed`, or `403 not_current` if its renewal has closed; an app listed as removed gets a stranger's answer (Section 6.1) | As 1 |
  | 6 | The app record is signed with that key and carries that certificate, or an earlier one of the same app and keys | `403 not_current` | Skips the app |

  Then come scopes and switch permissions (`403 permission_missing`, or the message is dropped), and admission (Section 7). Checks 1 to 3 need only what the caller presents. Check 4 authenticates the caller before the service consults anything it holds, so that someone holding an app's public certificate can't learn whether this switch holds its identity's `identity.json`, which would show the two identities correspond. For an own app the service checks the certificate the newest `identity.json` lists; for another identity's app, the one the request presents (`Paykit-Cert`); a recipient checks the one the inbox entry carries, a sender or payer the one the app record carries.

### 3.6 Shared Data Key
One identity-wide key family encrypts data that own apps share, such as payment activity and Allowances.

- **Derivation (signer only):** `scope_key(e, s) = derive("paykit/v1/scope-key", paykit_root, u64(e), s)`, where `paykit_root = derive("paykit/v1/scope-root", identity secret)` (Section 14.3). `e` is the data epoch and `s` a scope name from Section 3.3. Only the signer computes `paykit_root`; it is never granted or delivered.
- **Label keys:** a labelled selling scope `request:<label>` has keys of its own, `label_key(e, label) = derive("paykit/v1/label-key", scope_key(e, "request"), label)` (Section 14.3). An app holding `request` derives every label's key from its `request` key, so no key bundle carries them for it and a new label needs nothing from the signer. An app holding only the label gets its label keys in its key bundles and can't work back to the `request` key. A data epoch rotation rotates them with the `request` key.
- **Independent of Pubky path keys.** Pubky's hierarchical keys derive every child path's key from its parent directory's key, so a key grant on an ancestor of a path would yield that path's key. Scope keys don't use them: they come from a Paykit-only derivation, so no Pubky grant, on any path, reveals a scope key.
- **What apps hold:** only `scope_key(e, s)` for the scopes in their certificate, a label key for a labelled selling scope, for every data epoch from 1 to the current one. Extension scopes have no scope keys: no shared record holds an extension kind, so key bundles and the approval carry keys for the other scopes only (`specs/v0.2/wire-format.md` Sections 3.5 and 3.11). A scope key reveals no other scope's or epoch's key, nor `paykit_root`, and never the identity secret.
- **Delivered at approval:** the approval in the grant's companion claim carries the app's scope keys, for each of its scopes and every data epoch so far, and the naming key as a full key bundle: the same format as later bundles (below), sealed to the bundle key the certificate names and signed by the identity key (Section 3.2). Nothing in the claim is readable with the auth request's secret alone.
- **Naming key:** `naming_key = derive("paykit/v1/naming", paykit_root)`, one per identity. It blinds natural keys and obligation inputs (Section 14.3), so the keys of records and claims don't name their counterparty. That protects stored state, exports and dumps taken once the related inbox entries are gone, not against a live operator, which links records and claims to their counterparties through batches and timing (Section 16). The signer delivers it to every app in every key bundle, the approval's included. It doesn't rotate: it hides inputs from the service, not data from apps. An app keeps the naming key it was approved with: it refuses a key bundle part carrying another one and alerts the user, since taking it would split the app's obligation IDs and record keys from the other apps'. A former holder, such as a revoked app or an old backup, keeps it, and together with the operator can test guesses of counterparties against blinded keys whose inputs are public (Sections 15 and 16).
- **Current data epoch:** published in `identity.json` (`data_epoch`). It starts at 1 and only increases.
- **Sealed fields** (Section 14.4) sit inside writer-signed operations, so the switch can neither read nor change them.
- **Writes use the current data epoch.** The switch rejects a sealed field whose data epoch isn't the current one (`409 stale_epoch`), except in uploads during a provider move or recovery (Section 13). An app that doesn't hold the current key yet reads older data but writes no sealed data until it has the key.
- **Key bundles for later epochs:** an approval happens once, so when the data epoch increases (Sections 3.2 and 13.2) the signer stores each remaining app's key bundle at the switch (operation `key_bundle.put`, Section 14.5). The bundle is an envelope (Section 5.1) sealed to the app's bundle key, signed by the identity key, holding the naming key and the app's scope keys for the data epochs it lacks: those after the ones it already holds (below). So bundles stay small while an app keeps up. A bundle names the certificate it was made for, by hash, and holds exactly one key for each scope of that certificate, extension scopes aside and a labelled selling scope counting with its label key, and each data epoch of its range, and no other. **Parts:** a bundle too large for one envelope (64 KiB, about 700 scope keys), such as a full bundle after many epochs or the delta of an app that was offline through many rotations, is stored as several `key_bundle.put` parts, each covering a contiguous range of data epochs `[first_epoch, last_epoch]` within 64 KiB, each signed and sealed on its own; the app opens every part and assembles the keys. Parts stored for an app never overlap: a new part replaces those whose range it overlaps. Every renewal stores a full bundle made for the new certificate (Section 3.2), which replaces them all, so the parts stored for an app name its newest certificate. No part ever holds `paykit_root` or a key for a data epoch after the one it was made for: the current one, or during a rotation the next one, whose parts the signer stores before it raises the epoch. An app refuses a list of parts that overlap or are out of order. It skips a part whose sealed range differs from the range it names in the clear, which the signature doesn't cover, one with a key after the next data epoch, and one whose naming key differs from an earlier part's or from the one the app holds. It also skips a part made for a certificate other than its own or a renewal of it that its newest `identity.json` lists, and a part whose keys aren't exactly those of that certificate's scopes over its range, so it never takes a key its certificate doesn't grant or has to choose between two keys. A key it still lacks leads to a full-bundle request (below; `specs/v0.2/wire-format.md` Section 3.5). Only that app can fetch it. A new bundle appears in the app's feed, so an app that was offline fetches it whenever it returns. The app keeps the scope keys in its own state and backups, so a rotating key would protect nothing here; the bundle key is static.
- **What each app holds:** the signer learns it from `GET /v1/{id}/apps` (`keys_through`): the newest data epoch through which the app holds every scope key. The service works it out from what it sees: the data epoch of the first `identity.json` that lists the app, which is the epoch of its approval, raised to a part's last data epoch once the app's cursor has passed that part's item in the feed, for each part that continues what the app holds. It is worked out again over every passed part in epoch order, so a part passed before the gap below it was filled counts once the gap is filled. An app fetches a new bundle before its cursor passes the bundle's item, so a cursor past it means the app holds the bundle. For this, `key_bundle.put` names the bundle's first and last data epoch in the clear; data epochs are public in `identity.json` anyway. A bundle that replaces one the app never fetched starts where the app's holdings end, so nothing is skipped. When the service shows no value, for example after a provider loss, the signer stores a full bundle.
- **Full bundles:** after a restore, an app may ask for a full bundle with every epoch so far (`POST /v1/{id}/apps/{app_id}/keys`), which the signer stores the same way. The app asks when, after fetching its current bundle, it still lacks a scope key for some data epoch up to the current one, and asks once until a full bundle arrives. The service shows the request, with the time of the first one, in `GET /v1/{id}/apps` until the parts it stores for the app together cover every data epoch from 1 to the current one. The signer, when next online, stores a full bundle for every current app with a pending request, made for the app's current certificate: `GET /v1/{id}/apps` lists the ranges of the parts the service stores, so the signer stores only the ranges not yet covered by parts it stored for that certificate, and a delivery that was cut short resumes where it stopped. Its parts replace every part made for another certificate, which the app skipped. When the app's record at the service carries an earlier certificate, as after a restore from a backup older than a renewal or after a provider loss, the signer stores the current one with them (`cert.put`), as at a renewal, so the app takes it and then the parts. Any delivery cut short resumes from the epoch after `keys_through`; it starts from epoch 1 only with a pending full-bundle request or without `keys_through`.
- **Recovery:** anyone holding the identity secret re-derives `paykit_root`, and from it every data epoch's keys and the naming key, so restoring the signer restores access to all shared data.
- **Exposure:** every app holding a scope key can read all data under that scope. A compromised app exposes its scopes' shared data until it is revoked and the key is rotated (Section 13.2).
- **A copied app state reads on:** the bundle key is static, and later key bundles are sealed to it, so a copy of a current app's state (from a seized device or a backup) opens every key bundle stored for that app and reads its scopes' shared data, past and future, for as long as the app is current, through every data epoch rotation made for other apps. Reading records and key bundles creates no registration, so nothing shows the copy. It stops only when the app itself is revoked and the epoch rotated (Section 13.2), and for a scope a reduction removes, at the epoch that reduction starts (Section 3.2). This is accepted: sealing later bundles to rotating keys would heal only later epochs, at a cost in availability (Section 22, question 2).

### 3.7 Receive keys
Each app rotates its own receive key, without involving the signer, its other own apps or its contacts. Forward secrecy comes from deleting a receive key once everything sealed to it has been read.

- **Generation:** each rotation brings a new X25519 key. The app keeps the secret of its current key, plus those of retired keys it hasn't deleted yet. How the app makes the key is its choice; the spec recommends 32 fresh random bytes, clamped as an X25519 secret. Keys then share nothing, so a stolen receive key reads nothing sealed to an earlier or a later one. Rotation protects against a leaked receive key only. A leaked signing key, which a full copy of the app's state or a backup contains, can register receive keys of its own, so it reads new messages until the app is revoked (Section 13.2); unexpected registrations, below, make that visible. It can also ask counterparties to re-send what they sent in the last 30 days, which they seal to its keys (Section 12), so it pulls that much history too. An app may derive its keys instead, for example from a seed, to make backups or devices easier; whoever copies that seed then reads every key derived from it, and the forward secrecy in Sections 16 and 17 holds only from the app's next fresh random key.
- **Registration:** the app registers each receive key record (Section 4.4) with the switch (operation `receive_key.put`, Section 14.5). Its first record at a service has `n` 0 for a new app; after a provider loss, its first record at the new service may carry any `n` higher than every `n` the app has registered (Section 13.6). Each later record has `n` exactly one higher than the current record's; anything else gets `409 conflict` with the current record. A registration is an item in the chain (Section 8.4), and the key is current from that item's `seq`.
- **Kids are unique:** a kid names one key in the whole account. The service refuses a registration whose kid any app of the identity has registered before (`400`), so an envelope's kid names exactly one recipient key. The 8-byte kid only routes an envelope; HPKE binds the key itself, so a kid shared by chance across identities changes nothing.
- **Low-order keys:** X25519 with a key of low order gives the all-zero shared value, which RFC 9180 aborts on, so such a key can't be sealed to. The service refuses to register one (`400`), a certificate that names one as its bundle key is invalid, and a sender that meets one in a directory skips that app and seals the message to the identity's other apps (Section 8.1), so one bad key never blocks the others.
- **When to rotate:** at the first feed read at least 24 hours after the last rotation, if the app has opened an envelope wrapped to the current key since that rotation. An app may use a shorter interval, down to 1 hour; a server app that reads continuously should. An app that has opened nothing new doesn't rotate, and a push extension's peek doesn't count (Section 9).
- **Cut-over:** from a registration on, the service rejects every envelope wrapped to any other key of that app with `409 stale_key`, whose `current` holds the app's current receive key record (Section 6.4). The sender checks the record (Section 8.1), seals the message again and re-sends it. A sender whose cached directory predates the rotation pays this extra round once, unless it refreshed the directory in the background (Section 8.1).
- **Deletion:** the app deletes a retired key, in the sense of Section 3.1, once its cursor has passed the `seq` of the next key's registration. So the order is: read; register the new key, after which the service rejects envelopes to the old one; read on past the registration, which picks up everything that reached the old key before the registration; then delete the old key. Nothing can reach the old key after its successor's registration, so there is no race. In the foreground the open long-poll returns the registration at once; an app reading in the background passes it at its next read.
- **Backups:** backups are the app's responsibility (Section 13.4). A backup holds the app's current receive key, so the app should refresh it at every rotation, replacing and deleting the previous one, so the receive key in a leaked backup reads at most the messages sent until the next rotation, as the live state would. A backup that also holds the signing key reads new messages until the app is revoked, as above; Section 13.4 recommends keeping that key out of routine backups. A restore from an older backup can't open entries sealed to keys created since; it registers a fresh key and asks those senders to re-send (Section 13.4).
- **Devices:** devices of one app share its receive keys. The device that rotates passes the new key to the app's other devices through the app's own device sync (Section 3.1). A device that finds a registration of its app with a higher `n` than every key it holds reads no further until it has the key, so it never moves the shared cursor past entries it can't open. When two devices rotate at once, the second registration gets `409 conflict` naming the first one's key, and the second device discards its own. A device that can't get keys from its sync should be its own app. A restore from a backup older than the last rotation registers a fresh key instead (Section 13.4).
- **Unexpected registrations:** an app treats a registration of its own app that neither it nor one of its devices made as a compromise, including a `409 conflict` naming such a key: it stops, alerts the user, leaves at once (`leave`, Section 13.3) and asks the signer to revoke it (Section 13.2), with `distrust_from` at the service time at which the registration was accepted, from its chain item. The leave is app-initiated and irreversible, so the copy that registered the key, which holds the same signing key, is refused by the service from that moment, without waiting for the signer. Payers still check only `identity.json`, so the app's destinations stay payable until the signer publishes the revocation; that window is accepted. An app that shares keys across devices authenticates registrations through its own device sync (Section 3.1), so its devices can tell their own registrations from someone else's.
- **After a restore:** a restored app can't tell a thief's registration made before the restore from one of its own that it made after the backup and no longer remembers. It treats every registration after its backup's newest key whose kid it doesn't know as a possible compromise: it asks the user whether the app ran on that device after the backup was made, and makes no attempts until the user answers. If the user confirms, the app takes those registrations as its own; if not, or in doubt, it leaves at once and asks the signer to revoke it, as above. A registration after the key the restored app registers itself is unambiguous: someone else's. So a restore alone doesn't cut off a thief who holds a copy of the app's state (Section 13.4).

### 4.1 Locations

| Location | Data | Written by |
|---|---|---|
| HS `/pub/paykit/v1/apps/<app_id>.json` | App record, only for an app with public endpoints | That app |
| HS `/pub/paykit/v1/identity.json` | Switch pointer, policy, current and removed apps, data epoch | Signer |
| HS `/pub/paykit/profile.json` | Paykit Profile (optional) | Signer or authorized app |
| HS `/priv/paykit/v1/apps/<app_id>/` | Optional encrypted backup (Section 13.4) | That app |

| App storage | Derived state (such as Allowance budgets), outbox and the messages it sent in the last 30 days, payment journal, processed message IDs, cursor, the Private Payment Lists it publishes | The app (storage is its choice) |

### 4.2 App record

```json
{ "v": 1, "kind": "paykit.app",
  "identity": "<pubky id>", "app_id": "<app id>", "signing_key": "<ed25519>",
  "cert": "<signed certificate>",
  "accepts": ["paykit.payment_request", "paykit.payment_receipt", "paykit.private_payment_list"],
  "capabilities": { "endpoint_identifiers": ["<payment endpoint identifier>"] },
  "public_endpoints": { "<payment endpoint identifier>": "<opaque payload>" },
  "label": "Bitkit", "updated_at": "<rfc3339>", "expires_at": "<rfc3339>" }
```

- Signed by the app's signing key (Section 14.2).
- **Expiry:** a record with public endpoints carries a signed `expires_at`, chosen by the app; at most 30 days ahead is recommended. The app publishes a renewed record before then, once less than half its lifetime remains, and the same rule applies to the `expires_at` of the Private Payment Lists it sends (Sections 5.4 and 11.4). Payers refuse public endpoints from an expired record. So an identity whose publishing app doesn't run for longer than its record's lifetime, about a month at the recommended expiry, can't be paid publicly (tips, a profile's pay button) until the app runs again; v0.1's endpoint files had no expiry. A record without public endpoints may set it to null.
- **Record age limit:** the app key signs `expires_at`, so a stolen app key could sign a record that never expires. Each identity therefore sets, in its `identity.json`, the longest time payers trust one of its app records after it was signed (`record_max_age`, Section 4.3; 90 days when absent). A payer uses a record's public endpoints only until the earlier of its `expires_at` and its `updated_at` plus that limit, and not at all when its `updated_at` is more than 5 minutes ahead of the payer's clock. The signer signs `identity.json`, so a stolen app key can't extend the limit. The app renews its record within the limit too. An identity whose publishing app doesn't run for longer than the limit has no payable public endpoints until it does.
- **Path:** a payer uses a record read from `/pub/paykit/v1/apps/<app_id>.json` only if the record names that `<app_id>`.
- **Where it lives.** The app delivers its signed record to the switch (operation `app.put`, Section 14.5) when it is added and whenever the record changes, and the directory serves it to admitted senders. An app with public endpoints also publishes the same record on the Homeserver, where public payments read it. Other apps need no Homeserver record: recipients verify messages with the certificate each inbox entry carries, and payers check the `identity.json` listing.
- **The later `updated_at` wins.** Each new record of an app has an `updated_at` strictly later than every record of it the app delivered or published. Devices of one app agree on it through the app's own device sync, as for receive keys (Section 3.7). A party that sees two versions uses the one with the later `updated_at`. The switch applies the same rule: it replaces the record it holds only with one whose `updated_at` is later, so a replayed older record never replaces a newer one. The held record again, byte for byte, changes nothing. A different record with the same `updated_at` is refused (`409 conflict`, naming the held record), and the device that gets that answer writes again with a later time (`specs/v0.2/wire-format.md` Section 7.2).
- **Two records at one time are a conflict.** A reader that sees two records of one app with the same `updated_at` and different bodies, for example one from the switch and one from the Homeserver, pays that app by neither and tells the user. It keeps using an earlier record of that app it already holds, if any, and can still pay the identity's other apps. A record with an `updated_at` strictly later than both ends the conflict. A record whose `updated_at` is too far ahead isn't used at all (above), so it takes part in no comparison.
- **No encryption key.** Messages are wrapped to the app's current receive key, which has its own record (Section 4.4), so the app record changes only when the app's capabilities or endpoints do, or to renew its `expires_at`.
- **`capabilities.endpoint_identifiers`:** the Payment Endpoint Identifiers the app can pay to, so payees can offer matching destinations.
- **Public payments are optional.** An app may leave `public_endpoints` empty. The identity's public Payment List is the `public_endpoints` of every current app, each listed under its app; payers may use any of them. An identity whose records list none has no public Payment List.
- **Public endpoints are read from the Homeserver.** They are public, non-interactive data: anyone reads them without authentication or the switch, and they stay readable while the switch is down or the identity is moving to another provider. A payer also compares the Homeserver's `identity.json` with the switch's copy, in parallel and waiting on it at most a short grace, and pays without the switch's answer only as Section 4.3 allows.
- **Payers check every destination's app** before paying (Section 10.4): the app that published a public endpoint, or sent the request, period details or Private Payment List, must be current in its identity's `identity.json` with the certificate it presented (listed, or renewed and still counting, Section 3.2); that certificate must allow `request`, and a listed certificate must not have expired. The record or Private Payment List carrying the destination must not have expired either (Section 5.4). A removed app's destinations are ignored, even if its record is still on the Homeserver.
- **Withdrawing a destination:** stale copies of a record or a Private Payment List can't be recalled before they expire. A payee whose destination is compromised therefore removes it and also revokes the app, or replaces it with a new app (Section 13.2), so that payers stop paying to it once their 10-minute copy of `identity.json` shows the app removed.
- **What is public:** only an app with public endpoints has a public record. Every other app appears publicly only as an app ID and certificate hash in `identity.json`, so anyone can see how many apps an identity has, but not what they are. Admitted senders get the full records from the directory.

### 4.3 `identity.json`

```json
{ "v": 1, "kind": "paykit.identity", "identity": "<pubky id>",
  "version": 12, "generation": 3,
  "inbox": { "url": "https://inbox.example", "service_key": "<ed25519>" },
  "policy": { "admission": "contacts_and_conversations",
              "connect_requests": { "enabled": false, "max_pending": 50, "push": false } },
  "apps": [ { "app_id": "<app id>", "cert": "<BLAKE3 of the signed certificate bytes>" } ],
  "removed": [ { "app_id": "<app id>", "distrust_from": "<rfc3339>" } ],
  "data_epoch": 4,
  "recovery_from": null,
  "record_max_age": 7776000,
  "renewed": [ { "app_id": "<app id>", "cert": "<BLAKE3 of the earlier signed certificate>", "until": null } ] }
```

- Signed by the identity key (Section 14.2). The certificate hash is over the signed document bytes (Section 14.2).
- **Current apps:** `apps` lists every current app with the hash of its certificate, up to the switch's app limit, announced at enrollment: 32 by default, never more than 255. The signer adds an app when it approves it, and moves it to `removed` on revocation or after a leave (Section 13).
- **Each App ID once:** an App ID appears at most once in `apps`, at most once in `removed`, and never in both; a document that breaks this is invalid. An App ID once in `removed` is never listed in `apps` again (Section 13.2): an app holding a version that lists it as removed refuses a later version that lists it in `apps` and alerts the user, and the switch refuses such a version.
- **Record age limit** (`record_max_age`, optional): the longest time, in seconds, payers trust one of the identity's app records after its `updated_at` (Section 4.2), 90 days when absent. It is signed with the rest of the document, and only the signer sets it.
- **Removed apps** stay in `removed` until the signer purges them. `distrust_from` is the time the service revoked the app or recorded its departure, or an earlier time the user picks when revoking it after a compromise. Recipients reject its messages accepted later than 5 minutes before that time, the clock tolerance (Section 12). An app in neither list is not current, so once the signer purges an app, its remaining messages are rejected too; signers purge only apps they expect no more messages from, and should wait until the app's certificate has expired: switches of other identities answer an app listed as removed like a stranger but can't tell a purged one from a new one (Section 6.1), while an expired certificate is refused everywhere. The signer and the switch keep a purged App ID for good, and never approve or list it again (Section 13.2).
- **`renewed`** lists the earlier certificates of current apps during and after a renewal (Section 3.2), absent when empty. An entry goes with its app when the app moves to `removed`, and the signer purges it only when no more messages carrying that certificate are expected, for example once no stored request still relies on it.
- **`recovery_from`** names the generation lost in the most recent provider loss (Section 13.6), or is null. Once set, it stays in later versions until a later loss replaces it.
- **`service_keys`** lists the service keys of earlier generations, `{ "generation", "key" }`, ascending, at most 256, absent when empty. Each generation has one service key. A switch keeps with each current record the transition proof of its write, which may be an earlier generation's, and readers, apps added later included, check such a proof with the key listed for its generation, which the identity key signs (Section 10.3). So a key stays listed for as long as a current record's proof needs it: the switch reports to the signer every generation that some current record's kept proof names (`proof_generations` in `GET /apps`, Section 6.2), and at every cooperative move (Section 13.5) and every key change in place the signer keeps the key of each generation reported and drops only the others. It never drops one that is reported. If they would be more than 256, it refuses the move or key change and shows the user why, until records are rewritten, which moves their proofs to the current generation. The switch refuses an `identity.json` that drops a reported key or lists a wrong one (`409 conflict`). A provider loss adds no key: the lost generation's proofs date nothing.
- **Service key:** `inbox.service_key` is the key the switch generated for this identity's account at enrollment (Section 6.2). It signs the service's responses, transition proofs and signed heads for this identity (Section 14.2). Each account has its own key, so a leaked key affects only that identity. Push webhooks are signed with separate push keys that appear in no public document (Section 9).
- **Version and generation only increase.** Apps and the switch reject a document whose version or generation is lower than one they have seen. A new identity starts at `version` 1, `generation` 1 and `data_epoch` 1. Two documents with the same version and different body bytes are equivocation: apps stop paying and alert the user. The same body under another signature isn't: it shows only a signer that signed one version twice, against Section 14.2. The switch keeps the body it holds at a version: a peer delivery of another body there, by an app of that identity or by an own app delivering a counterparty's document, is refused with the switch's copy, so the sender holds both and stops paying (`specs/v0.2/wire-format.md` Section 8.4.5).
- **Enrollment** (Section 6.2), for a new identity or a new provider:
  1. The signer sends `POST /v1/enroll`, signed with the identity key, naming the identity, the service origin, a random nonce and the policy, with the current `identity.json` if there is one and the App IDs it revoked or saw depart, which the new account keeps as tombstones from the start (Section 13.2).
  2. The service creates the account, staged, and answers with the account's service key and limits, signed with that key. Repeating the same enrollment returns the same answer.
  3. The signer delivers an `identity.json` naming that service and key (`PUT /v1/{id}/identity`), then publishes it.
  4. The account becomes active once it holds a document naming it; until then it answers `503 staged` to everything else.
- **Delivery to the service:** the signer sends every new version to the switch (`PUT /v1/{id}/identity`). The service enforces the current apps, removals and data epoch of the newest version it holds, and records each delivery in the chain, so own apps see it in their feed.
- **Compare-and-swap at the service:** the switch is the compare-and-swap point for `identity.json`, so two signers can't both build on one version. `PUT /v1/{id}/identity` names the hash of the previous version the new one builds on (none when the service holds no earlier version), and the service refuses it with `409 stale_identity` unless that is the version it holds. That answer carries the copy the service holds, with its version, generation and document hash, so the signer can republish it and build its next version on it. The signer keeps the generation, version and document hash of the newest version a service accepted from it, or that it adopted, and never adopts or republishes a copy with a lower version or generation, or another body at that version: from any service, after an import too, that is a rollback or equivocation, which it shows the user as an alarm instead of building on it. A strictly newer copy, another signer's, it may adopt. The same document delivered again, as a retry, is accepted whatever it names as the version it builds on, and its answer carries the original delivery's transition proof, as a batch retry's does, so the signer learns when the service took it even when the first answer was lost. The signer delivers first, and publishes on the Homeserver only after the service accepts. If the Homeserver copy differs from the service's, the signer republishes the service's copy.
- **Caching for verification and paying:** at most 10 minutes, re-fetched after any failure. A sender's cached directory may be older, as long as this document still names the same switch and generation (Section 8.1). A payer that holds both the Homeserver copy and the copy in the payee's directory uses the one with the higher version.
- **The switch's copy:** the switch serves the newest `identity.json` it holds for its identity, as the signer delivered it, with a public, read-only `GET` (`specs/v0.2/wire-format.md` Section 8.4.15). A payer about to pay a payee's public endpoints that holds no copy fresher than 10 minutes reads the Homeserver copy and then, in parallel with the app record reads that follow it, which need only that document, the switch's copy, and uses the higher version: the same document at an equal version, and a different one at the same version is equivocation (above). So a stale or malicious Homeserver that serves an older document, still listing an app since revoked, doesn't make a first-time payer pay that app. Its limits are in Section 15.
  - **No added latency:** the lookup runs beside reads the payer makes anyway, so it adds no request in sequence. It is made only for public-endpoint payments and only without a fresh copy, and the payer waits for it at most until its Homeserver reads finish plus a short grace (500 ms in the prototype).
  - **No silent fallback:** a lookup that hasn't answered by then keeps running; in a real app the user confirms the payment meanwhile. If the lookup has failed, or still hasn't answered, when the payment is made, a manual payment goes ahead only once the user explicitly confirms paying although the payee's switch couldn't confirm the payee's apps, and the app records an event for it. An answer that arrives before money moves is still used. An automatic payment to a public endpoint waits for the lookup instead, with the client's usual timeout and one retry, and never pays on the Homeserver copy alone: if the lookup still fails, it isn't paid automatically. A failed lookup counts until the payer looks up again, once its copy is more than 10 minutes old.
  - **Hard to switch off:** the service limits the read per network source, with a higher backstop per account (Section 6.5), so one source flooding it can't push every payer onto an unconfirmed payment. The answer is a signed public document, the same for every reader, so caches may keep it for a short time (60 seconds); a payer keeps the copy it got for 10 minutes, as any other, so its copy may lag the service's by up to that minute more.
  - **After a move:** an old service, frozen, answers with its last `identity.json` and the signed freeze naming the next service (Section 13.5). A payer that gets a freeze checks it with the payee's identity key, follows it once to the next service's public read, and uses the higher copy. A next service still staged means the move isn't published, so the old service's copy is the newest. A next service that is frozen too isn't followed, and the lookup counts as failed.
- **Watching for changes:** a running app subscribes to the Homeserver event stream (`/events-stream`, live, filtered to `/pub/paykit/v1/identity.json`) for its own identity and for the counterparties it caches, and re-fetches a document as soon as an event names it. A subscription that closes is opened again from the cursor of the last event it took, never from the newest event, so the events in between aren't missed; while it is closed, the document counts as unwatched. A document it watches this way needs no 10-minute re-fetch for sending; one on a Homeserver it doesn't watch keeps the 10-minute rule. Checking a destination before paying always uses a copy at most 10 minutes old, watched or not (Section 10.4). After waking, the app resumes the stream from its cursor, so it catches up on missed changes in one request.
- **Fresh before paying:** an app fetches or revalidates its own identity's `identity.json` in parallel with each `attempt`, unless it did so in the last 60 s. It moves money only when it holds such a copy and that copy names the service whose key signed the attempt's transition proof (Section 10.4); a payment made while its own switch doesn't answer, which has no attempt yet, needs a copy naming the service the app uses (Section 11.4). If the Homeserver is unreachable for longer, the app makes no new attempts. An open event stream doesn't replace this check, because a stalled stream looks the same as a quiet one.

### 4.4 Receive key record

```json
{ "v": 1, "kind": "paykit.receive_key",
  "identity": "<pubky id>", "app_id": "<app id>",
  "n": 41, "kid": "<kid>", "x25519": "<public key>" }
```

- Signed by the app's signing key (Section 14.2) and registered with the switch (Section 3.7). The directory returns the record of each current app.
- **`n` only increases** for an app.
- **The app signs it, the service holds it.** The service can withhold a record or offer an older genuine one, but can't make one; senders check every record before using it (Section 8.1).
- **Later suites:** like the certificate (Section 3.2), the record may carry `suite_keys`, receive keys of later suites beside the suite 1 `x25519` key. Each such key's kid is derived over its suite and the key (Section 14.3), so it differs from every suite 1 kid. Apps of this version write none and ignore those of suites they don't support.

## 5. Messages

### 5.1 Envelope (binary)

```
header:
  magic "PKT1" (4 B) | version (1 B) = 1 | suite (1 B) = 1 | flags (1 B, bit0 = notify) | recipient count n (1 B, 1-255) | key commitment (32 B)
  n x { kid (8 B) | hpke_enc (32 B) | wrapped_cek (48 B) }
body:
  nonce (24 B) | ciphertext
```

- **Suite 1:**
  - **Content:** XChaCha20-Poly1305 under a random 32-byte content key, with the whole header as AAD.
  - **Key commitment:** `derive("paykit/v1/key-commit", content key)` (Section 14.3). A recipient whose unwrapped content key doesn't match it rejects the envelope, so every recipient app opens the same plaintext or none.
  - **Key wrap:** one per recipient app, to its current receive key, named by its kid. A key bundle is wrapped to the app's bundle key instead (Section 3.6). HPKE base mode (RFC 9180) with DHKEM(X25519, HKDF-SHA256), HKDF-SHA256 and ChaCha20-Poly1305. The HPKE plaintext is the content key; `info` is defined in Section 14.3; the HPKE AAD is the first 40 bytes of the header (magic through key commitment). As RFC 9180 requires, sealing and opening abort when the X25519 shared value is all zero, which a low-order key or `enc` gives (Section 3.7).
  - **Randomness:** the content key, the nonce and each wrap's ephemeral key come from the operating system's secure random generator. No sealing interface takes them from its caller; only test code fixes them, to reproduce the shared vectors.
- **Padding:** the envelope's total size is padded up to 1, 4, 16 or 64 KiB. Maximum 64 KiB.
- **`notify` flag:** authenticated by the AAD and by the sender's signed request. The switch pushes only when it is set, and rate-limits notifying writes per sender.

### 5.2 Plaintext and signature

```
sender app ID (16 B) | signature (64 B) | JSON length (u32, big-endian) | message JSON bytes | zero padding
```

- **Signature:** covers the recipient identity and the exact message JSON bytes (Section 14.2). Nothing is canonicalized; JSON with duplicate keys is rejected.
- **Verification:** against the sender's certificate, which the inbox entry carries, its scopes, and the sender identity's `identity.json` (Section 12). The plaintext app ID must equal `from.app_id`.

### 5.3 Common message fields

```json
{ "v": 1, "kind": "paykit.<kind>", "msg_id": "<uuid v4>", "created_at": "<rfc3339>",
  "from": { "identity": "<pubky id>", "app_id": "<app id>" },
  "to": "<pubky id>",
  "refs": ["<BLAKE3 of referenced message JSON bytes>"],
  "body": { } }
```

- **No sessions and no ordering.** Every app derives state deterministically from the messages, claims and shared records it holds, using `refs`. Section 11.1 says how messages that cross resolve.
- **`created_at` is informational,** except that provider-loss recovery uses it to find requests made before the loss (Section 13.6). Freshness rules use the inbox's acceptance time (Section 12) and, for request expiry, a clock tolerance of +/-5 minutes. A local clock never decides whether something was paid.
- **Deduplication:** by (sender identity, `msg_id`), durably (Section 12).

### 5.4 Message kinds
Kind strings are `paykit.` followed by the names below, or extension kinds `<prefix>.<name>` under an extension scope, which carry no Paykit payment semantics (Section 3.4). Message bodies use the field definitions of the v0.1 SDK specs at commit `53b8c8cb2735c0845232fbdf34bc83052bf88404`: `specs/payment-requests.md` for requests, recurrence, Billing Periods, acceptance, rejection, cancellation, proofs and receipts; `specs/payment-conversion.md` for conversion terms, quotes and deadlines; `specs/allowances.md` for Allowance terms and messages; and `specs/paykit-sdk.md` for Private Payment List versioning. Those files title their protocol "Payment Request Protocol v0.2"; here they are the v0.1 bodies. This spec defines transport, authorization, storage and lifecycle, and changes the bodies as listed below. The exact v0.2 bodies are in `specs/v0.2/wire-format.md` Section 5.

| Kind | Notes |
|---|---|
| `payment_request` | Carries its amount and `payment_reference`, and usually its destination (`payment_endpoints`), which the payer must then use; without one, the payer pays to any of the payee's current endpoints, or only those of the payee app named in `required_app_id` (Section 11.1). A request carries at most one of `payment_endpoints` and `required_app_id`. Optional: proposal expiry, `recurrence`, conversion terms, payment deadline, and `per_period_endpoints` for a recurring request (Section 11.2). |
| `payment_request_acceptance` | One-time request: sent once the attempt is confirmed (Section 10.4), while the payment runs; not awaited. Recurring request: sent once, when the user, or an executor under an Allowance, accepts the subscription, before any payment, and recorded first (Section 11.2). The proposal expiry bounds the acceptance. |
| `payment_request_rejection` | Recorded before it is sent (Section 11.1). |
| `payment_request_cancellation` | From either side. A payer records its cancellation before sending it (Section 11.1). |
| `payment_period_details` | New in v0.2; replaces v0.1's conversion quote. The payee's details for one Billing Period of a recurring request: its `payment_endpoints`, its conversion rates (cross-asset only, as v0.1 quotes), or both, with an `expires_at`. Its rates apply to a payment whose verified payment time is at or before `expires_at`, as a quote's do. A later one for the same period, by `created_at` and then `msg_id`, replaces it, and the proof references the one it used (Section 11.2). |
| `payment_proof` | References the request and Billing Period, or none for a payment without a request, and the period details or Private Payment List version it paid to. Carries the `attempt_id` it reports and an opaque proof. Required after paying a single-use endpoint (Section 11.4). |
| `payment_receipt` | Optional; signed by the payee. References the proof it confirms, and so the attempt. |
| `resend_request` | Asks the counterparty to re-send messages by `msg_id`, request, Billing Period, or a range of acceptance times. Best effort. |
| `private_payment_list` | Latest state per publishing app. Its version is the publishing time in milliseconds, and the app always sends a higher one than before, even after a restore. It carries a required `expires_at`, which the publishing app computes from its current time, not from the version. Payers use the list only until the earlier of `expires_at` and 30 days after their inbox accepted it, so a stolen app key can't sign a list payable for long, and refuse it after that. Endpoints are reusable unless marked `single_use` (Section 11.4). |
| `private_payment_list_request` | Asks for the current list and names the version the sender holds. Best effort. |
| `allowance_proposal`, `allowance_acceptance`, `allowance_rejection`, `allowance_end` | The acceptance names the executor app at acceptance, for information; a later handoff doesn't change it. |
| `executor_notice` | New in v0.2, between apps of one identity only. Tells an executor that an Allowance ended (`reason: ended`) or was handed to another app (`reason: handed_off`), naming the Allowance's record key. Its only effect is on the recipient's consent list (Section 11.3). |

- **Differences from the v0.1 bodies and rules:**
  - `required_app_id` is optional and only allowed without `payment_endpoints`, whose owner is always the sending app (`from.app_id`).
  - Dropped: `event_id` and `payment_request_id`, replaced by `msg_id` and `refs`; Encrypted Links, Receipt Access and Delivery Confirmations; the 1000-byte limit; and FIFO message order, which Section 11.1 replaces.
  - `per_period_endpoints`, `payment_period_details` (which replaces the conversion quote and can also carry a period's destination) and `executor_notice` are new. So is `label`: a request sent under a labelled selling scope carries it, and the payer's acceptance, rejection, cancellation and proof copy it (Section 3.4). Private Payment List endpoints may carry `single_use: true`, and a list carries `expires_at`.
  - Billing Periods follow one rule, the anchored period rule of `specs/allowances.md` (Section 11.2), where v0.1 left expansion open.
  - Readers ignore unknown fields in message bodies (Section 14.1), where v0.1 rejected them.
- **Size:** the JSON of each kind stored in activity records (Section 8.3) is at most 16 KiB.
- There is no refund message; a refund is a normal Payment Request in the other direction.

## 6. Pubky Switch

### 6.1 Request authentication
Every call is signed by an app, or by the identity key for signer operations. There are no sessions.

- **Headers:** `Paykit-Identity`, `Paykit-App` (absent for signer operations), `Paykit-Cert` (from apps of another identity: the signed certificate), `Paykit-Invite-Code` (optional, Section 7), `Paykit-Timestamp`, `Paykit-Signature`.
- **Signature covers** the method, path and query, `BLAKE3(body)`, the timestamp, the switch origin and the identity, app, certificate and invite code headers (Section 14.2).
- **The service checks:**
  - for an own app: that it is current in the newest `identity.json` the service holds, and its switch permissions and scopes, from the record and certificate it delivered with `app.put` (its first call carries one);
  - for an app of another identity (inbox appends, connect requests and directory reads): that the presented certificate is signed by the identity in `Paykit-Identity`, names the app and its signing key, and hasn't expired; that the request signature verifies with the app's key; its admission (Section 7); and, for appends and connect requests, that the newest `identity.json` of that identity the service holds lists the app with that certificate. The service keeps the newest `identity.json` delivered for each identity (`PUT /v1/{id}/peers`) and names its version in every successful response to that identity's apps and in `409 identity_needed` (`known_version`, in the signed body); other errors don't carry it, so they reveal nothing of what it holds. A sender delivers its identity's document before its first append to an inbox, in parallel with the directory read a first message needs, and again whenever a response shows an older version. An append from an app that the service's copy doesn't list gets `409 identity_needed`; the sender delivers its document and retries. The service fetches nothing from the sender's Homeserver. The document is signed by the sender's identity key, so it can't be forged; the service keeps the highest version it has seen and never goes back to an older one. A revoked app can still reach a switch that hasn't yet received its identity's newer document. Recipient apps reject its messages anyway, since they check senders against the document from the sender's own Homeserver (Section 12), and an own app that holds a newer document than its switch delivers it. An app that the service's copy lists as removed, or that the document it delivers lists there, is answered exactly like an app of an identity the service doesn't admit and holds no copy of: only an invite code admits it, an append or connect request then gets `409 identity_needed` naming no version, and `PUT /peers` answers with the version it delivered. So a revoked app's key can't probe switches to learn which identities correspond with its own; its certificate's expiry (Section 3.2) ends what a switch without the newer document still allows;
  - the timestamp, within +/-5 min;
  - **cheap before costly:** every call has a body cap, refused with `413` before the body is read; the timestamp is checked before any signature, and signatures before anything that reads the account's state; an own app's first call is authenticated from only the first `app.put` naming it, whose key must give its App ID before the request, then the record, certificate and operation are verified; a claimed caller that keeps failing authentication is rate-limited before any signature work (`specs/v0.2/wire-format.md` Sections 8.1, 8.2);
  - **retries, by content:** an append whose envelope the service still holds returns the original result, and so does a batch whose batch ID is already in the chain, while the service keeps that batch's transition proofs (30 days). After that, a batch carrying an ID the service still holds gets `409 conflict` (Sections 6.3 and 14.5). Any other request is applied as new, which is safe: a repeated message is dropped by its recipients by `msg_id` (Section 12), and a repeated operation in a new batch fails its expected step or version, so the app finds its earlier write in the current state. No key or timer is needed, and a replay within the timestamp window is recognized the same way. Requests outside batches carry no nonce, so their own rules make a repeat harmless: a freeze is used once and the same freeze is answered with its original proof (Section 13.5); a push start changes a registration only when it names the push key it replaces, so the same start again answers the current registration (Section 9); a repeated app record is a no-op, and an older one is refused (`app.put` needs a later `updated_at`); a connect request keeps one pending request per sender; an erasure names the account's service key, so a repeat finds no account, or a later one with another key, and erases nothing (Section 13.7). A replayed cursor-only batch can move the app's cursor back to where that request put it, within those 5 minutes, which only delays deletion until the app's next move.
- **Switch origins:** an app or a service that connects to a switch origin it read from an `identity.json`, which the identity's owner chose, applies the classifier of Section 9: HTTPS only, port 443 unless the connecting side's operator allows another, every address after DNS resolution globally reachable, the connection made to the address checked, and redirects not followed. A service such as a merchant's server that reaches many switches should also connect through an egress proxy that applies the same rule.
- **Every response** carries `Paykit-Service-Signature`, which binds the status, the server time (`Paykit-Server-Time`) and the body to the exact request it answers through the hash of the request's signature (Section 14.2). A client checks it with the service key it pinned for the account, from `identity.json` or, for the signer, from its enrollment answer, and acts on no answer it can't check: without a pinned key it sends nothing but an enrollment, whose answer names the key. Anything else an app relies on goes in the signed body. Responses to own apps and the signer also carry the newest signed head. Responses to apps of other identities carry no `seq` and no head, so counterparties don't learn the identity's activity.

| `POST /v1/{id}/import/activate` | Signer | Make the import live, naming the manifest hash |
| `POST /v1/{id}/recovery/admission` | Signer | End staged admission after a provider loss (Section 13.6) |
| `POST /v1/{id}/recovery/upload` | Own app | Upload signed operations, transition proofs, signed heads and sealed shared records during recovery (Section 13.6), or signed heads and the proofs and record versions an app holds during a cooperative move (Section 13.5) |
| `POST /v1/{id}/erase` | Signer | Erase the account: the service deletes everything it holds for the identity and from then on answers as for an identity it doesn't host; refused during a move (Section 13.7) |

Every write by an own app or the signer returns its transition proofs and the newest signed head.

### 6.3 Storage rules
- **Inbox entries are transport.** Writers can't read, overwrite or delete them. An entry is deleted once the cursor of every target app that is still current, and not lagging, has passed it. There is no expiry: an app that stops reading shows an old last-seen time, which the signer uses to suggest removing it (Section 13.3), and removing it releases its entries, while the identity's quota bounds storage meanwhile. Lasting state lives in claims and shared records (Section 8.2), never in the inbox.
- **Lagging apps:** an app whose unread entries exceed its share of the inbox quota (the quota divided among current apps) is marked lagging in `GET /v1/{id}/apps`. Entries no longer wait for it, so one silent app can't fill the inbox for every sender. An app counts as lagging only while another current app is reading: when every current app's unread entries exceed its share, none is marked, entries wait as before, and the inbox quota refuses senders, which tells them the recipient isn't reading (Section 16). A lagging mark ends when the app reads its feed. The feed then tells the app what it missed, and the app asks senders to re-send it (Section 8.2).
- **Sequence:** one monotonic `seq` per identity and generation covers inbox entries and chain items (Section 8.4). Cursor moves take none.
- **Retention:** the service keeps every claim's entries and transition proofs until the claim is finished: once it is SETTLED with no open or `unknown` attempt, the service may compact it, at once or later, to a **tombstone** holding the claim key, its state, and each attempt's ID and outcome, in a transition proof. Apps keep that proof until the later of the bounds that apply has passed (Section 10.4): the later of the pinned deadline and their own, where there is one, plus the 30-day reconciliation window below; and, for a claim pinned to no deadline, 400 days after the proof's entry (Section 8.4). A pinned deadline where they compute none is an early pin, and they keep that proof for good. Before attempting, they compare it with the claim (Section 10.4); in a cooperative move they upload it, and after a provider loss it is evidence that the claim was settled (Sections 13.5 and 13.6). A re-sent, restored or delayed copy of the request therefore still shows as paid, and a late receipt is still recorded on the tombstone (row 3 of Section 10.2). The tombstone also keeps the claim's deadline, the one its first attempt pinned, or none (Section 10.2). Other time conditions, such as an executor's ledger window, never count as a deadline. Once the service's clock reaches it, no compliant app can start an attempt any more. The service still keeps the tombstone for the **reconciliation window**, 30 days after the deadline, so a receipt that comes late is still recorded on it, and deletes it once its time base, with trusted time, reaches the deadline plus 30 days (Section 10.1). A tombstone without a deadline is kept until 400 days after the claim's last entry (`max_claim_age`), and deleted then the same way. The same holds for a claim that never settled, whose every attempt has failed: from its deadline no attempt can start any more, but a payment marked failed may still turn out to have settled, and its receipt must name the attempt (Section 10.4). So the service keeps it to the deadline plus 30 days too, and deletes it then; one pinned to no deadline, 400 days after its last entry. After the window a late receipt can't be recorded on the claim (Section 11.3). A claim with an open or `unknown` attempt is never deleted by age, so no unresolved obligation goes. After 400 days the payer's own record of a payment without a deadline, not its claim, stops a second payment (Section 10.4), so the payer never deletes that record (Section 8.3).
- **Each app's claims are bounded.** An app holds at most 1,000 attempts open or `unknown` at once (`open_attempts_per_app`), and the claims its `attempt` created, live and tombstones, are at most a quarter of the claim limit, rounded down (`claim_share_percent`). Beyond either its `attempt` is refused (`429 quota_exceeded`, `open_attempts` or `claim_share`), and the other apps keep the rest of the limit. So a compromised payer app can't fill the claim limit for every app. Once it is revoked, its open attempts, at most 1,000, are orphaned, and the user resolves them through another app (Section 10.5); its finished claims and its failed ones go at their deadline plus 30 days, or 400 days after their last entry without one. Everything else the service keeps, and for how long, is in the retention table below.
- **Targeting:** envelope kids identify the target apps, and each must be that app's current receive key (Section 3.7). Each app reads only its own entries.
- **What the service keeps.** Defaults are for one identity on a shared service; an operator may raise them and announces them at enrollment (Section 6.2). "For good" in this section means for the account's life: an erasure deletes the account with everything it holds (Section 13.7).

  | Kind | Kept for | Counts against | Default limit |
  |---|---|---|---|
  | Inbox entry | Until every current target's cursor has passed it, not waiting for lagging apps (no expiry) | Inbox quota: its size plus 256 bytes; one sender identity's unread entries at most a quarter of it | 64 KiB each |
  | Unreadable entry (Section 8.2) | Until every current app's cursor has passed it | Inbox quota: 256 bytes; never refused | - |
  | Missed item (Section 8.2) | Until its app's cursor has passed it | Nothing; never refused | One per lagging app; a later miss replaces it |
  | Shared record value | While current, with its write's operation, certificate and transition proof; a superseded value is deleted at once | Storage quota: its sealed size, the bytes of ciphertext and tag. The certificate and the proof, about 1.6 KB together, aren't counted; the record key limit bounds them | 256 KiB each |
  | Shared record key | While live; once deleted, until the service forgets it, which it may do once nothing refers to it (Section 10.3) | Record key limit: live keys only | 100,000 live keys |
  | Live claim or tombstone | Until finished, then a tombstone until its deadline plus the 30-day reconciliation window, or 400 days after its last entry without one; a claim whose every attempt failed the same way (above); never by age while an attempt is open or `unknown` | Claim limit, and its creating app's share | 1,000,000; 64 attempts per claim; a quarter of the limit created by one app; 1,000 attempts open or `unknown` per app |
  | Chain stub | Within the generation, until it is older than a checkpoint and either every current app's cursor has passed it or it is 30 days old (Section 8.4); reads alone hold no stub back; dropped oldest first, and the service keeps the `seq` and chain hash of the newest one dropped, which an export's checkpoint signs (Section 13.5) | Control reserve | Grows at most as fast as the operation and control rates allow; no cursor holds a stub back once it is 30 days old |
  | Batch record | Its transition proofs 30 days, for retries; its ID and operation hash as long, and also while any of the batch's chain stubs is kept (row above) | Control reserve | Proofs: bounded by the rates over 30 days. IDs: one per batch of the last 30 days or with a chain stub kept, so bounded like the proofs and the stubs |
  | Contact, conversation entry, deny list entry | Until removed; conversation entries are pruned once idle by an app with `lists.manage` (Section 7) | List limit | 100,000 each; an append admitted by an invite code waits while conversation entries are full |
  | Invite code | Until it expires, runs out or is withdrawn | Invite code limit | 1,000 live codes |
  | Connect request | Until answered; once `max_pending` are pending, new senders are refused | The policy's `max_pending` | at most 1,000 |
  | App record, current receive key record, key bundle parts | While the app is listed in `apps` or `removed` | App limit (Section 4.3) | One record and one current receive key record per app; key bundle parts never overlap, so they hold at most one key per scope and data epoch |
  | Retired receive key record, renewed certificate | Retired keys until 8 newer exist; a renewed certificate until the app's record carries it | Control reserve | 8 and 1 per app |
  | Departure, revoked app | Until the signer purges it from `removed`, after its rotation, and it owns no open or `unknown` attempt | App limit | - |
  | Cursor, last-seen time, push registration | While the app is kept; push registrations while it is current | Control reserve | One cursor; 8 push handles per app |
  | Peer copy of `identity.json` | The newest per identity; the least recently delivered drops beyond the limit, strangers' copies (neither contact nor conversation) first, and a stranger's never pushes out an admitted identity's. A dropped admitted copy leaves a floor at its version, which a later delivery must reach | Peer limit | 10,000; floors one per admitted identity |
  | Enrollment answer | One per distinct enrollment; the oldest drops beyond the limit | - | 16 per account |
  | Staged import, uploaded heads (Section 13.5) | Until the `identity.json` naming the service arrives, or an abort | Import limit | 4 GiB, announced at enrollment; 1 MiB per chunk. An account at every default limit exports under 1 GiB; the rest holds the chain stubs and batch IDs it keeps (`specs/v0.2/wire-format.md` Appendix A47) |
  | Divergent upload (Section 13.6) | Until a newer write at the service | - | 8 per record |

- **Two quotas.** The inbox quota counts inbox entries, each with a fixed overhead so that it bounds their number as well as their bytes, and blocks only appends. It is the identity's, so **each sender's share** is capped: one sender identity's unread entries may hold at most a share of it, a policy value, a quarter by default; past it that sender alone gets `429 quota_exceeded`, so one admitted sender within its rate limit can't fill the inbox for every other while the identity's apps are offline. The storage quota counts current shared record values and blocks only writes that make them larger. They are separate, so a full inbox never blocks the record writes that drain it.
- **Per-kind limits** refuse only the write that would create something new: a live record key (a new one, or a deleted one written again), an `attempt` on a new claim key, beyond 64 on one, or beyond its app's share or open attempts (above), a contact, conversation entry or deny list entry, or an invite code. Writes to existing objects, outcomes, deletions and removals always pass.
- **Control reserve.** Control operations count against neither quota nor any per-kind limit: cursor moves, deletions and removals, claim outcomes, key registrations, app records, key bundles and renewed certificates, `identity.json` deliveries, revocation, leave, freeze, export, import and recovery uploads. An operation that would change nothing, an app record, receive key record, renewed certificate or key bundle part the service already holds byte for byte, is a no-op: a batch made only of such operations creates no chain item and no batch record, and its answer carries the current head. The service decides this before it checks the batch's conditions and permissions. That is safe, since a no-op changes nothing and returns only the head. A batch that also moves the app's cursor changes something, so it is checked in full, conditions and permissions included, and the cursor moves only if every check passes. Repeatable control mutations, an app record or receive key record that changes what the service holds (a new record, a new registration), and a deletion or removal of something that isn't there, count against their app's control rate, 60 batches a minute by default, and its operation rate. An unchanged app record or receive key record counts against no rate, also in a batch with other operations. Whether a record is unchanged, and whether something is there, is judged against the state before the batch. Cursor moves, claim outcomes on existing attempts, deletions and removals of something present, and revocation and leave are never rate-limited, so a full inbox can still be drained, an existing payment reconciled and an abusive app revoked. The state control operations create is bounded: chain stubs by those rates and by checkpoints, which no cursor holds back from a stub 30 days old (Section 8.4); batch records' proofs by their 30 days and their IDs by those 30 days and the stubs; and the rest per app (the table above). The operator plans that capacity apart from the quotas.
- **Operation rate limit.** A batch carrying an ordinary operation or a repeatable control mutation counts against its app's rate, 3,000 batches a minute by default; other batches of control operations alone never do. With the control rate this bounds how fast chain stubs and batch records grow; old stubs may be dropped behind a checkpoint, and with them the IDs of batches whose proofs are gone (Section 8.4).
- **Rate limits per sender** and the 64 KiB envelope cap apply as in Section 7.
- **Dropping is safe.** A dropped peer copy is delivered again after `409 identity_needed`, and never at a lower version than the one dropped, so a revoked app can't take the service back to a document that still lists it by having many fresh identities push the copy out; a repeated enrollment gets the same answer. A batch's transition proofs go after 30 days, and a retry after that gets `409 conflict`. Its ID stays as long, and also while any of the batch's chain stubs is kept. An app compares a batch ID only with the batches of the last 30 days of the chain, and the service holds every one of those IDs (Section 14.5). So the service never accepts a batch that an honest app would take for a rollback, and an app never compares an ID the service has forgotten. The ID goes once its proofs are gone and none of the batch's stubs is kept. A request is accepted only within 5 minutes of its signed timestamp, so an old batch can come again only in a new request, which only its app can sign, and apps resend a batch only in their immediate retries. So nobody can replay a batch, list changes included, which carry no expected version.
- **Not public:** nothing is ever published to a public feed.
- **Lists:** contacts, conversation entries and the deny list hold Pubky IDs. The operator can read them, as it sees every sender anyway (Section 16).

### 6.5 Operating a switch
These rules make a service a **consistent switch**, the condition of Section 17's guarantee. A service that breaks them is non-compliant, like one that rolls back on purpose.

- **Durable before acknowledged.** The service releases no answer that carries a `seq`, a transition proof or a signed head until the items it commits are durable: written and synced (fsync) to storage, or committed synchronously to every replica that could ever be promoted to serve the account. An asynchronous replica may serve reads for operators, but is never promoted to serve writes under the same generation. "Not replicated" doesn't allow an asynchronous failover. The confirmation of an erasure carries none of these, and is still released only once the deletion it confirms is durable (Section 13.7).
- **No restore and continue.** Any recovery that may have dropped an item the service acknowledged, such as restoring a database backup, failing over to a replica that may lag, or replaying an incomplete log, is a loss of committed state: the account must not serve under that generation again (Section 10.1). The operator tells the user, and the signer declares a provider loss (Section 13.6), at the same service or another: at the same service the account starts the next generation afresh, with a new service key.
- **The key's mark.** The service keeps, with each account's service key and apart from the state a backup restores (in a key store or HSM that holds the key), the newest head that key signed: its generation, `seq` and chain hash. The key signs nothing for a state behind that head or beside it (a fork), and the account fails stop with `503 unavailable` until the signer starts a new generation; only the enrollment that answers the next generation's pending key, and the `identity.json` naming it, go through. The mark moves with the key: whoever holds the key holds the mark.
- **Failed authentications:** before a request verifies, the service trusts nothing it claims, so it limits failed authentications only by network source, an IPv4 address or an IPv6 /64, before it does any signature work. It also counts them per claimed caller (its `Paykit-Identity` and `Paykit-App`), for monitoring, but never refuses a request because of that count, so a flood of bad signatures that claims a victim app's App ID can't keep that app out. Limits per caller apply only to requests that have verified. The prototype counts per source where its HTTP adapter sees the peer address; the in-process transport has no source, so there no limit applies before authentication.
- **Public reads:** the service limits the public read of `identity.json` per network source, an IPv4 address or an IPv6 /64, with a higher backstop per account, so one source can't use up the account's budget and switch payers' lookups off (Section 4.3). A source's refused reads don't count against the backstop. A cache in front may serve the answer for up to 60 seconds. The prototype counts per source where its HTTP adapter sees the peer address; behind a reverse proxy the source is the address the proxy reports. The in-process transport has no source, so there only the backstop counts.
- **Detecting lost state.** The key's mark catches a restore at once. Apps catch it too, as a rollback, when a head or chain item they verified is missing (Section 10.1), and the signer when a service shows an older `identity.json` than it delivered (Section 4.3). Operators should also compare each account's head after a restart with the mark, and alert on any refusal.
- **Provider-loss runbook (outline).** 1. Stop serving the affected accounts (the key's mark does this for them) and keep the old keys' marks. 2. Find the accounts affected: those whose state is behind their mark. 3. Tell their users, through the signer's operator channel, that a provider loss must be declared. 4. The signer declares it (Section 13.6), here or at another service; apps recover, upload their evidence and treat earlier obligations as uncertain. 5. Never serve the lost generation again, and keep the old service keys retired, never reused.
- **Erasure and backups.** An erasure (Section 13.7) deletes the account's service key and its mark too, so nothing can sign for the account any more. The operator lets the erased account's data age out of its backups. Until the last backup that holds it has aged out, it keeps the identity's ID and the time of the erasure apart from the backups, so a restore from an older backup erases the account again before it serves anything.

## 7. Admission
A write to an identity's inbox is accepted when one of these holds:

1. **Contact:** the sender is a contact on the allowlist. Saving a contact adds them; removing the contact removes them.
2. **Conversation:** the allowlist holds a conversation entry for the sender, because an own app wrote to it or invited it.
3. **Invite code:** the sender presents a valid invite code.

The **deny list** overrides all three. The same rule admits a sender to the directory (Section 6.2). Answers never reveal the deny list: every refusal reads the same (`403 not_admitted`, one message), whether the sender is denied, unknown, or holds an unknown, expired or used-up invite code; where connect requests let strangers deliver their `identity.json` and ask to connect, a denied sender is answered exactly as they are, and its request is simply not kept; while a provider loss stages admission, denied senders get `503 staged` like the others (Section 13.6). A denied sender holding a valid invite code still learns from its refusal that it is denied, since the code admits anyone else.

**Conversation entries:**
- **Writing to someone admits them for good.** When an app first writes to a counterparty that isn't a contact, it adds a conversation entry for that counterparty to its own identity's allowlist before sending, in parallel with the directory read a first message needs anyway. An app that can't read the lists writes the entry before its own first message to each counterparty; adding an entry that already exists changes nothing. A `resend_request` adds no entry: it answers entries the service shows the app, which the app can't check, so a forged one must not admit its sender (Section 12).
- **Invites let the other side write first.** An app may add the entry before any message, which is an **invite**. At a checkout, for example, the user's wallet or the Pubky app reads the shop's Pubky ID from the site (a QR code or a link, `pubky://<shop id>?paykit=invite`), invites the shop, and the site passes the user's Pubky ID to the shop, which then sends its request.
- **Permission:** both need the switch permission `conversation.add`, not `lists.manage`. From then on the two can keep talking, as in any conversation; the entry has no expiry.
- **Stopping it:** blocking the counterparty puts it on the deny list, which overrides every entry, and an app with `lists.manage` may remove an entry.
- **Pruning:** entries never expire on their own, so an app with `lists.manage` prunes them, for example daily, before the list fills: it removes an entry whose counterparty isn't a contact, whose last admitted append is at least 180 days old (the service records it with the entry, `last_used`, or its creation time when never used), to whom the app sent nothing in that time, and with whom no record it holds is unfinished (a request without a receipt, rejection or cancellation, an accepted subscription not cancelled, an Allowance or a Private Payment List). A pruned counterparty is admitted again once an own app writes to it, or with an invite code; apps that see the removal in their feed (with `lists.read`) add the entry again before their next message to it. An app without `lists.read` that wrote to the counterparty keeps no such view, so its counterparty's reply may be refused until the user or that app writes again (residual).
- **Visible:** each entry records the app that wrote it. Apps with `lists.read` list entries (`GET /v1/{id}/allow`). An app's entries stay when it stops being current, so its conversations continue through the identity's other apps.
- **Limits:** a conversation entry never overrides the deny list, and it is not a contact: it admits messages, nothing else.
- **What it shows:** the operator learns whom the identity writes to or invites (Section 16).

**Spam:** a stranger can't write at all. Admitted senders are rate-limited per sender identity and per sender app, with a tighter limit for messages that trigger a push, and each identity has an inbox quota and a 64 KiB size cap per message (Section 6.3). One sender's unread messages hold at most its share of that quota, a quarter by default, so a sender that fills its share is refused while others still get in. The service never blocks on its own. It flags senders that keep hitting the limits, which `GET /v1/{id}/allow` shows, and apps may offer the user to block them. Apps should not create activity records (Section 8.3) for messages from a counterparty the service has flagged, or that the user has blocked; they keep at most a count of them. A message from such a counterparty that updates an existing record, such as a receipt for a payment in progress, is still applied.

**Invite codes** (optional), for a counterparty that the identity doesn't know yet, such as a customer scanning a shop's QR code:
- **Registering:** an app with `conversation.add` registers a code at its own identity's switch (operation `invite_code.put`): the hash of a code of at least 16 bytes from a secure random generator, an `expires_at`, a `max_uses`, and an opaque `context`, such as an order reference. The `context` is stored in the clear, so the operator reads it (Section 16): apps put in it only what they would show the operator, such as an opaque order number, never personal data. It shows the code as `pubky://<id>?paykit=invite&code=<code>`. It can withdraw the code at any time (`invite_code.delete`).
- **Using:** a sender presents the code in the `Paykit-Invite-Code` header. The switch checks its hash, expiry and remaining uses. A directory read with the code uses none, and such reads are rate-limited per code; an admitted append uses one, atomically with the append.
- **Then a conversation:** the first append admitted by a code also adds a conversation entry for its sender, written by the service and naming the code, so later messages need no code. The feed shows the code's `context` with the entry. The `context` is a hint attached by the recipient's service, not signed by the sender, so apps match orders through the signed request and its `payment_reference`, never through the `context` alone.
- **A bearer secret:** anyone who sees a code can use it until it expires, runs out or is withdrawn, so apps keep uses and lifetimes small.
- **One per order:** an app SHOULD register a code per order or per counterparty, with one use and a short expiry, minutes to hours, as a checkout needs. A shop SHOULD NOT publish a reusable code, such as one printed on a poster: whoever copies it can write to the identity until it runs out. A code with more uses is an explicit choice of the app, rate-limited per code as above, and capped by the operator's policy (`max_invite_uses`, 100 by default; `specs/v0.2/wire-format.md` Section 7.2).

**Connect requests** (optional, off by default):
- **What it is:** where the identity's `identity.json` allows it (`policy.connect_requests.enabled`), a stranger's app may ask to be invited (`POST /v1/{id}/connect`). The request is content-free: the service keeps only the sender's Pubky ID and the time. The user's app shows the sender's public Pubky profile, so a request carries no text, link or payment data.
- **Kept apart:** pending requests are a separate list, not inbox entries, and admit nothing. Each sender has at most one pending request.
- **When the list is full:** once `max_pending` requests are pending (50 by default, set by the user), a new sender is refused (`429 quota_exceeded`, naming connect requests), and the requests already waiting stay, so a flood can't push them out. The refusal is the same for every sender, denied or not, so it reveals nothing about the deny list; a sender already pending is still answered as pending. Apps reading the list see that it is full (`GET /v1/{id}/connect`), so the user can clear it or block senders.
- **Senders** are authenticated like any other sender (Section 6.1) and rate-limited, and the deny list applies. Identities are free, so per-sender limits don't stop a flood from many fresh ones: connect requests, and the `identity.json` deliveries of senders admitted only because connect requests are on, are also limited per account, 60 a minute together by default, and a stranger's peer copy never pushes out an admitted identity's (Section 6.3). `POST /v1/{id}/connect` answers a denied sender exactly as it answers anyone else, as pending or, while the list is full, refused, so the answer doesn't reveal the deny list.
- **No push** for connect requests unless the policy turns it on (`push`); apps show the list when the user opens them. With `push`, a request queues the apps' webhooks like an entry does, at most once per app a minute however many requests arrive.
- **Answering:** accepting is an invite, which removes the request; declining removes it (`DELETE /v1/{id}/connect/{pubky}`); blocking puts the sender on the deny list.
- **Names are unverified:** anyone can call themselves "Bitkit Support", so apps show the sender's Pubky ID prominently.
- **Filters** for who may ask, such as identities on trusted Homeservers or in a social graph, are left for later (Section 20).

**Own apps** are admitted to their own identity's inbox only for messages between own apps, which today means `executor_notice` (Section 11.3); any other kind from an own app is dropped by its recipients.

## 8. Routing and shared state

### 8.1 Routing
- Senders read the recipient's directory and wrap each message only to current apps allowed by Section 3.5.
- **Directory caching:** a sender may use a cached directory of any age, while the recipient's `identity.json` still names the same switch and generation. The sender watches that document through the Homeserver event stream, or re-fetches it in the background when its copy is more than 10 minutes old (Section 4.3). When it names another switch or generation, the sender drops the cached directory. If the new document records a provider loss since the sender's copy (its `recovery_from` is at least the generation of that copy), the sender also re-sends to the new switch the messages the old one accepted since its previous check; after a cooperative move it doesn't, because the new service imported the old one's pending entries. Each append response carries the recipient's `directory_version`; when it is newer than the cached one, the sender refreshes the directory in the background for its next send. A cached directory is also tied to the version of the recipient's `identity.json` it was read under: once the sender sees a newer version, it reads the directory again before its next send, since a renewal may have changed which apps receive which kinds (Section 3.2). Each append MUST also name the `apps_version` it was sealed for, a version of the recipient's app set that changes only when apps are added or removed. A rotated or removed app's key, or an app added since, gets `stale_key` (Section 3.7), whose answer includes the added apps' records, so a stale cache costs at most one extra round and no current app is left out.
- **Refreshing ahead of rotations:** a sender that expects to write a recipient again may refresh the recipient's directory in the background once its cached receive key record is older than about a day, the default rotation interval (Section 3.7), so that its next append is sealed to the new key. This costs one directory read per active counterparty per day, off the critical path, against one refused append, re-seal and re-send on the critical path per rotation.
- Counterparties see which of the sender's apps sent each message (`from.app_id`).
- **Checking receive keys.** Before wrapping to a receive key record, from the directory or a `stale_key` answer, the sender checks:
  1. its signature, with the signing key in the app's record;
  2. that the app record's certificate is signed by the recipient identity, hasn't expired and allows the kind being sent (Section 3.5);
  3. that the app is current in the newest `identity.json` the sender holds, with that certificate;
  4. that the record's `identity` and `app_id` are that identity and app;
  5. that its `n` isn't lower than the highest `n` the sender has seen for that app;
  6. that its key isn't of low order (Section 3.7), and its kid is derived from it (Section 14.3).

  A record that fails a check is ignored, and the app counts as unreachable until a valid record is found: the sender seals the message to the identity's other apps, so one bad record never blocks them. A sender whose cached directory leaves no app that may receive the kind re-reads the directory before treating the recipient as unreachable.

### 8.2 Shared state
- **Messages are transport.** An inbox entry is deleted once every current target app has read it, not waiting for apps marked lagging (Section 6.3).
- **Shared state lives in claims and shared records.** Everything that own apps share, including apps added later, is in the claims and the shared records of Section 8.3: what was requested, paid and received, and Allowances. Contacts and blocked IDs are the switch's own allowlist and deny list (Section 7), not records. Names and pictures come from each counterparty's public profile, and nicknames and notes stay in each app for now (Section 22, question 10). State that belongs to one app alone, such as the Private Payment Lists it publishes and its payment journal, stays in that app.
- **Shared by scope, by design:** every app holding a record's read scope can read it, including what other own apps wrote and what was written before it was added. That is the purpose of shared state: all the identity's wallets show the same payments, and a new one starts with them. Encrypting per app was rejected: every record would grow with the number of apps, and adding an app would mean re-encrypting existing records for it. A compromised app exposes its scopes' data until it is removed and the keys rotate (Section 13.2). A labelled selling scope narrows this on the payee's side: a hosted app holding `request:<label>` reads only that label's `payee_activity` records, and the apps holding `request` read them all (Section 3.3).
- **Receiving:** an app that processes a message with a lasting effect writes the effect to its shared record and advances its cursor in one batch. If the record already reflects the message's `msg_id`, because another own app processed it first, the app only advances its cursor. Advancing the cursor alone, for items the app has nothing to apply, needs no shared record write. An app may apply several messages in one batch, within the batch limit, and may defer cursor moves that apply nothing and send them with its next batch, for at most a few seconds while it runs, never more than 10 seconds. It sends a deferred move before it stops reading, for example when a phone app goes to the background. The inbox keeps the entry until the cursor passes it, so a failed batch is retried from the feed. An entry whose sender can't be checked yet, for example because its Homeserver is unreachable, doesn't hold up later ones: the app processes those and keeps its cursor at the oldest entry it hasn't processed, so nothing is deleted before it is processed. After a bounded wait, which the app chooses, it MUST store that entry locally and move its cursor past it, so a long outage doesn't fill the identity's quota. Re-reading entries it already processed is harmless, since it keeps their IDs (Section 12).
- **The feed never stalls.** An app whose record write for an entry hits a per-kind limit or the storage quota (`429 quota_exceeded`, Section 6.3), or would take the record over the 256 KiB limit for a shared record value (`413 too_large`), MUST store the entry locally and move its cursor past it. It writes the record once room frees. A message whose body doesn't parse for its kind is dropped like any message that fails the recipient checks (Section 12): the app keeps its (sender identity, `msg_id`) as processed and moves its cursor past it, so one bad message never holds up later ones.
- **Entries an app can't open,** for example after a restore from a backup older than its last rotation (Section 13.4), are passed with the cursor. The app sends each entry's sender a `resend_request` for the messages accepted at that entry's time, which the feed shows, but never for a time before the time of its cursor, less the clock tolerance (Section 12).
- **Entries an app missed while lagging** (Section 6.3) are gone, and the feed tells it. When the service deletes an entry that a lagging app hasn't read, it records the miss and shows that app a `missed` item: how many entries it missed, and the first and last of their acceptance times. Like the unreadable items of a departed app (below), the item takes a new `seq`, so the app's cursor reaches it wherever it stands, and it goes once the app's cursor passes it. A later miss replaces an item the app hasn't passed yet with one covering both. On a `missed` item the app asks the counterparties of its unfinished activity records to re-send what their inboxes accepted from the later of the item's first acceptance time and the time of its cursor, less the clock tolerance, as after a provider loss (Section 13.6). The service writes the item, and the app can't check it, so the app never asks for anything accepted before its cursor's time on the item's word, and ignores an item whose times don't parse. It also lists its collections again, since the service may have forgotten deleted record keys while it was away (Section 10.3).
- **Entries left unread by a departed app:** when an app is revoked or leaves, each entry it never read and that no current app can open is added to the feed of the identity's other apps as a new, unreadable item, with its sender and acceptance time but no content. Each of them asks the sender to re-send, as above; re-sends are deduplicated by `msg_id`. So a message sent to a lost phone's app reaches the identity's other apps. The service writes these items too, so an app acts on one only after it has verified a departure of another own app in its chain, the `leave` or `revoke` transition, and only for an entry accepted at or before it.
- **Sending:** before sending a message with a lasting effect, the app records two jobs in its outbox: delivering the envelope, and writing the matching shared record. It runs both in parallel and retries each until it completes. Delivery completes when the recipient's inbox accepts the envelope (Section 12). A first message to a counterparty that isn't a contact also needs its conversation entry, written before it is sent, except a `resend_request` (Section 7).
- **Verifiable copies:** a record stores, for each message it reflects, the signed plaintext (sender app ID, signature, JSON bytes) and the sender's certificate from the inbox entry. Any own app, including one added after the sender app was removed, can verify the signature independently of the app that wrote the record. Whether the sender app was current when its message was accepted was checked by the app that recorded it; paying never relies on that check (Section 10.4).
- **Verified on use, never trusted:** an own app can write any record its scopes allow, so no app trusts a record because an own app wrote it. Before acting on a stored message, an app verifies it as it would a new one: its signature and certificate, that its sender identity is the record's counterparty and its kind fits the record, that it names the record's obligation by its own signed fields, and, for a request, that its hash matches the record key. The signed fields are the request hash where the kind places it in `refs` and, for a Billing Period, the signed `billing_period`. A period record is bound by nothing else: every message in it names the request and the period, all the same ones, and the record sits at the key of that request and period start (Section 14.3). A message whose binding field is missing, or that names another obligation, makes the record invalid, and so does a period's message in a request record. The other collections are bound the same way, each record to the key the reader derives with its own naming key (Section 14.3): a `payment_lists` record to its payee and publishing app, whose list must come from that identity and app; an `allowances` record to its counterparty and Allowance ID, which every message it stores must name, sent between the identity and the counterparty from the side its kind requires; and an `allowance_ledgers` record to the same counterparty and Allowance ID, those of the Allowance record it is checked against (`specs/v0.2/wire-format.md` Sections 6.4 and 6.5). The sender's standing is the exception: it is checked once, when the message is recorded, against the sender identity's `identity.json` current then, and not against later versions, so a signer that purges `removed` or `renewed` entries (Section 4.3) doesn't invalidate stored evidence. Paying still checks the destination's app against the current document (Section 10.4). A record's status is worked out from its verified messages and, while the service holds it, the obligation's claim, never taken from a field on its own. An app that has seen a record also ignores a write that replaces a message with an older one of the same role from the same sender, such as period details or a Private Payment List with a lower `version`, or that removes a single-use endpoint's used mark. An activity record holds one message per role (Section 8.3), so it also ignores a write that drops or replaces a message it has seen in one, such as a rejection or a cancellation, which would make a request it saw closed look payable again. Deleting a finished activity record (Section 8.3) isn't such a write, but what the app saw stays seen, so a later write that brings the record back without it is. A request record's `attempted_periods` (Section 11.2) is informational for status, which comes from the claims, but a payer's cancellation is fenced on it, so a write that drops a listed period without a condition on that period's claim is a conformance error: an app that holds the version the write was built on ignores and flags it, and keeps the period listed. A record that fails these checks is not acted on: the app keeps the content it trusts, writes its next update on top of the record's current version, and shows the user which app signed the bad write, so the user can remove that app.
- **Destinations come only from the payee.** An app pays only to endpoints in a verified message from the payee's current app, or to the payee's public endpoints (Section 10.4). No own app can redirect a payment by writing shared state; at most it can hide records, replay older messages from the same counterparty to an app that never saw newer ones, or act within its own scopes.
- **Apps added later** read the current shared records their scopes allow, then follow the feed. They start with the identity's full shared state and never need older messages.

### 8.3 Paykit shared records

| Collection | One record per | Contents | `read_scope` | `write_scopes` |
|---|---|---|---|---|
| `payer_activity` | Request received; for a recurring request also each Billing Period; or payment made without a request | **Request record:** the request, acceptance, rejection, cancellations and the request's status, and for a recurring request the Billing Periods that may have an open attempt (Section 11.2). **Period record:** the period details, proof sent, receipt received and the period's status. A one-time request has only a request record, holding both | `pay` | `pay` |
| `payee_activity` | Request sent; for a recurring request also each Billing Period; or payment received without a request | The same, from the payee's side | `request`, or `request:<label>` for a request sent under that label | `request`, or `request:<label>` |
| `payment_lists` | Payee and publishing app | The latest Private Payment List received and the single-use endpoints used | `pay` | `pay` |
| `allowances` | Allowance, on either side | Proposal, accepted terms, the executor's grant and every grant it has held, status, end or rejection (Section 11.3) | `allowance` | `allowance` |
| `allowance_ledgers` | Allowance | Its ledger entries and running totals (Section 11.3) | `allowance` | `allowance_execute` |

- **Fixed policies:** each collection's records use the policy above. A request sent under a label has its `payee_activity` records, its request record and for a recurring request its period records, under that label's policy: `read_scope = request:<label>`, `write_scopes = ["request:<label>"]`. Apps ignore any record in these collections whose policy differs, and a labelled one whose request, or payer's message, names another label or none, and a fixed one whose request names a label, so no app can plant a record readable under another scope or another label.
- **One message per role:** an activity record stores the messages that make up its state, one per role. A request record holds the request, the payer's response (acceptance or rejection) and a cancellation from either side; a period record holds the period details, the proof and the receipt; a one-time request's record holds the request's roles and its proof and receipt; a record of a payment without a request holds its proof and receipt. A later message for a role already held is still processed when it arrives, for example a second proof, which shows a duplicate payment, but isn't stored. A record of a payment without a request is keyed by its settlement (Section 14.3), so a second proof there names the same settlement: a replay, not a second payment, and credited once (Section 11.4). The one exception is period details: newer ones replace those held, unless a proof already references them. Allowance records hold their proposal, response and end the same way (Section 11.3). Recorded kinds are at most 16 KiB (Section 5.4), and a record lists only a bounded number of `msg_id`s (Section 12), so a record stays well within the 256 KiB limit for a shared record value without any message count, however many messages repeat a role it holds.
- **Deleting finished activity:** an app may delete an activity record (Section 10.3) once the user no longer wants it, with one exception: a payer never deletes its record of a paid obligation without a deadline (Section 10.2), one that carries the proof of its payment. The user may archive that record, which hides it in the app, but the record stays: the claim is gone 400 days after its last entry (Section 6.3), and from then on the record, not the claim, stops a second payment of a re-sent copy (Section 10.4). It stays whole, since a reader ignores a write that drops a message it has seen (Section 8.2). The cost is one record per payment without a deadline, kept for the identity's life. A record of an obligation with a deadline may go: its claim, or its tombstone, still shows the payment as done until 30 days after the deadline, after which a later copy can't be paid anyway (Section 6.3). A period record's deadline comes from its request, so the payer keeps a recurring request's record while it keeps any of the request's period records; a period record whose request record is missing counts as one without a deadline.
- Collection IDs and record keys are derived as in Section 14.3. Values are sealed under the read scope's key, a label key for a labelled policy (Sections 3.6 and 14.4).

### 8.4 Feed and chain
- **One order per generation.** Every item at the switch has a `seq` within its generation. Chain items, which are operations other than cursor moves, `identity.json` deliveries and service transitions, also have a place in the chain (Section 14.6); inbox entries don't. A cooperative move continues the sequence and the chain under the new generation (Section 13.5); a provider loss starts both afresh (Section 13.6).
- **What an app reads:** `GET /v1/{id}/feed` returns, for each `seq` after `after`:
  - the full item, if the caller may read it: inbox entries targeting the caller, with the sender's identity and certificate, the acceptance time, and the `context` of the invite code that admitted it, if any; the unreadable and `missed` items made for it (Section 8.2); its own key bundle writes; app records and receive key registrations of its identity's apps; `identity.json` deliveries and service transitions; claim entries, if it holds `claims.read`; allowlist and deny list changes, including those the service makes itself such as an invite code's conversation entry, if it holds `lists.read`; invite code changes, if it holds `lists.read` or `conversation.add`; and shared record writes whose `read_scope` it holds, while they are current (a superseded write is shown as its stub);
  - the chain stub of any other chain item;
  - nothing for other apps' inbox entries.

  Each page also returns `scanned_through`, the last `seq` it covered, including items it shows nothing for, and whether more items follow, so an app always makes progress.

  A feed page never ends inside a batch. Every app can therefore verify the chain from its cursor onward.
- **One cursor per app,** shared by its devices, written as `<generation>:<seq>`. An app may move its cursor back only to re-read entries the service still holds; deleted entries don't come back. A cursor from a sequence that a provider loss ended reads from the start of the current sequence, whose first item is the recovery record (Section 13.6).
- **Chain version:** this spec defines chain version 1, a linear hash chain (Section 14.6), which a service serves by default. A later version, such as a Merkle log, can be added without breaking anything (Section 20).
- **Checkpoints:** the service may drop chain stubs that are older than a checkpoint, a signed head it keeps for that purpose (Section 14.6), and that the cursor of every current app has passed or that are 30 days old in service time. It drops them oldest first, so the stubs it keeps run unbroken from the oldest one to the head, and it keeps the `seq` and chain hash of the newest stub it dropped. Only an app's cursor holds stubs back, never its reads, and only for 30 days. So the stubs from an app's verified position are kept while the chain item there is less than 30 days old, since every later stub is younger, and an app that reads without moving its cursor, or stays more than 30 days behind, can't hold chain retention back for good. A checkpoint is a head signed by the current service. The service signs one whenever the stubs it could drop would free a useful amount; how often, and at which item, is the operator's choice, since apps verify from their cursor whatever the checkpoint. So a checkpoint may lie ahead of stubs the service still keeps. An export starts at the oldest stub the service keeps, not at its latest checkpoint, so it leaves out no stub an app may still need; its checkpoint signs the `seq` and chain hash of the newest stub dropped (Section 13.5). After a cooperative move, N verifies the export's checkpoint with O's key and signs it again, at the same `seq` and chain hash, with its own. Apps verify from their cursor onward as before.
- **Pruning behind a checkpoint:** feed pages carry the service's latest checkpoint. Behind it an app keeps no chain hash: the checkpoint head stands for them, and heads at or before it are no longer compared (Section 10.1). Batch IDs don't follow checkpoints: the app compares each one for 30 days of the chain, by the service time of its stubs, and then forgets it, whatever checkpoints it sees (Section 14.5). For each finished obligation, one its kept SETTLED proof shows with no open or `unknown` attempt, the app also drops the signed claim entries whose items lie at or behind the checkpoint, and keeps the SETTLED proof. It keeps a SETTLED proof until the later of the obligation's pinned deadline and its own, plus the 30-day reconciliation window, has passed on the service clock, and without one until 400 days after the proof's entry (Sections 6.3 and 10.4). A checkpoint at or behind the app's verified position, and not behind a checkpoint the app accepted from an earlier service, must match the chain it verified, or the service has rolled back or forked (Section 10.1). A checkpoint behind the one the app accepted before from the same service can't be matched, since the app keeps nothing behind that one, so it is a rollback too. After a cooperative move the app compares N's checkpoints only with those it accepted from N: N's first is the export's, which may lie behind one the app accepted from O (Section 13.5). Behind the one accepted from O the app keeps no chain hash, so N's checkpoints there, the export's and any later one, can't be matched and aren't compared.
- **A checkpoint beyond the verified position** is never accepted on its signature alone, since its signer is the service being checked. If the feed carries the stubs from the app's verified position, the app verifies that they extend its chain through the checkpoint and that the checkpoint matches that chain, and only then accepts it; one that doesn't match is a rollback (Section 10.1). Without those stubs, it depends on the app. The service rule above keeps them while the chain item at the app's verified position is less than 30 days old, so for an app whose verified item is that recent, and that wasn't restored since, their absence is evidence of a rollback; it judges the item's age on its own clock, with the clock tolerance. How often the app reads doesn't matter. An app whose verified item is older but that holds a signed head or a proof of its own write between its verified position and the checkpoint, from an answer less than 30 days old, has evidence too: the service keeps that item's stub behind the app's cursor, so its absence is a rollback, unless other devices of the app share and may have moved the cursor, or the app was restored since. For an app whose verified item is older, so one more than 30 days behind, or one restored from a backup that hasn't yet moved its cursor and read its feed again, the stubs may otherwise be gone honestly, and the app has no evidence of continuity. It enters an explicit "continuity unverified" state, which is reconcile mode (Section 13.4): no automatic payments, every obligation checked against the SETTLED proofs and claims it keeps before attempting, and the state shown to the user. It continues from the checkpoint's head only as that recovery decision, and reconciliation ends it; reconciliation checks the app's obligations, but doesn't prove the missing chain's continuity. Until then it uploads no head in a cooperative move (Section 13.5).
- **Starting point for a new app:** the app follows the feed from the first `seq` of the batch that registered its first receive key, which comes before any message wrapped to it. Its scope keys came with its approval (Section 3.6). It also lists the current records of each collection it may read. A record write it then sees in the feed applies only if its version is newer than the one the app holds, so the listing and the feed combine into one consistent state, with no pending message skipped. Listing pages need no common snapshot: every write after the starting point appears in the feed, and the newest write of each record is shown in full because it is current when read, so whatever the page boundaries, each record ends at its current value, and a deleted record ends as a delete.
- **Long-poll:** an app in the foreground keeps one feed request open (`wait=25`).

## 9. Push
1. **Start a registration.** The app sends its relay URL to its switch (`PUT /v1/{id}/push`), with no handles and no push key. If the app holds no registration there, the service mints a new **push key** for it, a signing key that appears in no public document, and answers its public half. While the app holds one, a start replaces it only when it names that registration's push key (`replaces`); otherwise the same relay gets the current registration back unchanged, handles kept, and another relay gets `409 conflict` with the current push key. So a retried start, or one replayed within the timestamp window, resets nothing. A start that names the current push key is how an app rotates its push key or moves to another relay. After a provider change the new service holds no registration for the app, so the app starts afresh.
2. **Register with the relay.** Each device of the app sends its device token and that push key to the vendor's relay. The relay returns a random, opaque handle **bound to that push key**. So the relay can't look up which identity a handle belongs to.
3. **Set the handles.** The app sends `PUT /v1/{id}/push` again with the relay URL, the handles, one per device, at most 8, and the push key, which names the registration they belong to. A push key that isn't the current registration's, or another relay URL, gets `409 conflict` with the current push key, and the app starts a new registration. The setting is bound to the caller and removed when the app stops being current.
4. **Trigger.** When a `notify` entry targets the app, the service calls the relay webhook once per handle, with **only** the handle, signed with the registration's push key.
5. **Deliver.** The relay verifies the signature and sends the push.
   - **iOS:** a visible notification. Its extension peeks: it fetches and opens the message and runs the same checks as receiving (Section 12), without their side effects: the signature and certificate, the sender app current in a copy of the sender identity's `identity.json` at most 10 minutes old and not marked stale (Section 4.3), the kind's scopes, that the app hasn't processed the message already, which it only looks up, and the page's chain, checked on a copy of the app's chain state (Section 10.1). If they pass, it shows the message, for example "Bob requests $5"; otherwise, or when it has no such copy, or after the app found itself compromised (Section 3.7), it shows a generic notification, and nothing for a message already processed. It writes nothing. It doesn't move the cursor, write records, change its chain state or rotate the receive key; the app processes the message when it next runs. Its feed read still updates the app's last-seen time at the service, which is intended: the app is installed and reachable.
     - **What the extension holds:** the keys of the table below, and nothing else, as long as it only shows messages. This is the default this section describes: automatic payments wait until the app runs. Whether an app pays in the background, from its extension or from tasks the platform schedules, is the app's choice; an extension that pays also holds the keys paying needs, readable after the first unlock, and the app takes on that exposure.
     - **What a shown message leaves behind:** the text the extension shows goes into the operating system's notification store, outside the app's keys and their deletion, until the user clears it. A peeked message is still unread: the app processes it, and counts it towards rotation, only when it next reads (Section 3.7), so apps should read in the background soon after a push where the platform allows it.
   - **Android:** a high-priority data message.

**Key material of the iOS push extension.** Every request is app-signed, the peek's feed read included, so the extension needs the app's signing key. It reads keys in place from the keychain items it shares with the app (Section 3.1) and writes no key state.

| Key | In the extension | Why |
|---|---|---|
| App signing key | Yes, readable after the first unlock | It signs the feed read |
| Receive keys, current and retired | Yes, readable after the first unlock | It opens the entry it shows |
| Bundle key, scope keys, naming key | No; the app may keep them readable only while the device is unlocked | The peek reads no key bundle and writes no record |
| Identity key | Never | Only the signer holds it (Section 3.1) |

The extension runs while the device is locked, so its items use the class `AfterFirstUnlockThisDeviceOnly`. A forensic extraction of a locked phone after its first unlock therefore gets the signing key, which acts as the app until the app is revoked (it can register a receive key and read new messages, and send forged outgoing messages, Section 15), and the receive keys. A feed-only key for the extension isn't defined in this version.

**Webhook format:**

```
POST <relay URL>
{ "v": 1, "handle": "<handle>", "ts": "<rfc3339>", "nonce": "<16 random bytes>" }
Paykit-Signature: push-key signature over the relay origin and the body (Section 14.2)
```

**Rules for the switch:**
- **Relay URLs:** HTTPS on port 443 only. Every connection resolves the host and refuses every address that isn't globally reachable, checked after DNS resolution, and connects to the address it checked. One classifier decides, the same for switch origins (Section 6.1): an address is usable only if the IANA IPv4 and IPv6 special-purpose address registries mark it globally reachable, and it isn't multicast; an IPv6 address that embeds an IPv4 address (IPv4-mapped, NAT64 at the well-known prefix `64:ff9b::/96`, 6to4) is judged by the IPv4 address it embeds, and the forms that hide one (IPv4-compatible, Teredo, local-use NAT64) are refused. A host with any unusable address is refused. Redirects are not followed. An operator may further restrict relays to a list it accepts, and should send webhooks through an egress proxy that applies the same rule.
- **Isolation from messages:** webhooks are sent from a background queue with a 5 s timeout and at most 3 attempts within 1 minute. A failed or slow relay never delays or fails accepting a message; the app still receives it on its next read.
- **Spam limits:** notifying writes are rate-limited per sender (Section 5.1).

**Relay rules:**
- Accept a webhook only with a valid signature from the push key bound to the handle, a timestamp within +/-5 minutes and an unseen nonce.
- Rate-limit pushes per handle.
- A handle is usable only with the push key it is bound to, which only the switch that minted it holds, so a leaked handle can't be used from another switch.
- **After a provider move or recovery** (Sections 13.5 and 13.6), apps re-register their handles bound to a push key from the new service.

**What a push reveals:** nothing about content. The relay learns that a push is due for a handle, when, and which handles share a push key, so which devices belong to one app; Apple or Google learn that the device received a push. Push keys appear in no public document, but the relay is usually the wallet's vendor and can still link a handle to an identity without the operator's help: the webhook comes from the switch's address, and its timing follows the messages the identity receives, which a relay that also sees other activity, such as the sender's own app, can match. A switch operator and a relay operator together link senders to devices (Section 16). Operators should send webhooks from shared egress addresses and keep no record of which relay they called for which account; relays should keep no source addresses.

## 10. Coordination primitives
The switch offers two generic primitives: **claims** and **shared records**. It never interprets what a feature means: it doesn't know what an Allowance, a budget or a subscription is. Features are built in apps on these primitives (Section 11), so a new feature needs no change to the switch.

### 10.1 Common rules
- **Operations and transition proofs.** Every change is an **operation**: a JSON body signed by its writer (an app, or the signer) that names the object, the change and its conditions (Section 14.5). The service validates the operation, gives it a `seq`, links it into the chain and returns a **transition proof**, signed with its service key, with the resulting state (Section 14.6). Changes the service makes itself, such as recording a revocation or a recovery, are service-signed transitions in the chain.
- **Conditions.** An operation may carry conditions, checked atomically with it against the state before its batch:
  - `record_version(K) == v`;
  - `claim_step(K) == n`;
  - `server_time_in(start, end)`: the service's time when it applies the operation lies in `[start, end)`; either bound may be null.

  If any condition fails, nothing changes and the service answers `409 conflict` with the current values.
- **Batches.** `POST /v1/{id}/ops` applies 1 to 8 operations and their conditions as one transaction: all or nothing (Section 14.5). Every operation names its batch, so a service can't apply part of one without the apps noticing.
- **Server clock.** Every item records the server's time, and every response carries it. Orphan age, deadlines and time windows use it, never a device clock. For each identity it never goes backwards: the service stamps nothing earlier than the last time it committed, and a cooperative import carries that time to the new service, which continues from it. The new service takes it only on its own trusted time: it refuses an import whose last committed time, or freeze time, is more than the clock tolerance ahead of its own, and one it can't check because it has no trusted time (Section 13.5), so a faulty old service can't move its clock ahead for good. Each app keeps the highest service time it has verified. A signed time from the same service key that is earlier than one the app has seen is misbehaviour: the app raises an alarm. **Clock bound:** at each verified answer the app also measures the service's signed time against its device clock. While they differ by more than the clock tolerance (5 minutes), in either direction, or the highest service time it verified lies more than that ahead of the device clock, automatic payments (an Allowance executor's, Billing Periods paid under one) pause and the app tells the user; manual payments stay possible, with a warning. The app's own checks, such as expiries, a record's `updated_at` and a period's start, run on the device clock and the service's on its own, so an automatic payment never relies on two clocks that disagree. A device clock that far off the service's time base can't sign requests the service accepts anyway (`401 stale_timestamp`), so in practice the bound catches a service whose stamped time ran ahead, since it never stamps back, and a device clock that jumped since its last answer. A service time far ahead of the device clock (more than 24 hours) is shown to the user too, and bounds what the app deletes (Section 10.4).
- **Trusted time.** The service keeps its newest authenticated time sample, from the operator's choice of source, such as NTS-secured NTP or Roughtime, sampled at least hourly. Trusted time is that sample plus the time elapsed since it on a monotonic clock, which a change of the wall clock doesn't move; its uncertainty is the sample's own plus the elapsed time times a stated drift bound (for example 100 ppm). The service has trusted time while its sample is at most a maximum age old (for example 24 hours) and the uncertainty is at most 5 minutes. While the wall clock agrees with trusted time within 5 minutes the service uses its wall clock; when they disagree by more, it uses trusted time and alerts its operator. Request timestamps are checked against that time, so a jump of the service's wall clock doesn't lock out apps with correct clocks, and stamped time per identity still never goes back. So service time keeps moving between samples, and a deadline that has passed stays passed however long ago the last sample was taken.
- **Without trusted time** (no sample within the maximum age, or an uncertainty above 5 minutes) the service refuses, with `503 unavailable`, exactly these, whose outcome depends on its time: an `attempt`; a write with a `server_time_in` condition; a claim outcome that only an attempt's orphan age or its owner's certificate expiry allows, that is, an outcome by an app other than the attempt's owner while the owner is current; and an append, directory read or peer delivery admitted only by an invite code, whose expiry is a time. A certificate's expiry can't be judged without trusted time, so "current" in that rule means that the newest `identity.json` lists the owner, or holds its renewal open, and that the owner is neither revoked nor departed. Deletions at a deadline wait (Section 6.3), and once trusted time is back they compare the deadline with it, never with the stamped time, which a time read without it may have moved ahead. Everything else is served as usual: reads, cursor moves, appends and peer deliveries admitted otherwise, record writes without a time condition, list and invite code changes, the other claim outcomes, deletes and removals, and revocation. Request timestamps, certificate expiry and rate windows are then checked against the wall clock, corrected by the last sample (`specs/v0.2/wire-format.md` Section 8.3).
- **Rollback detection.** Every response to an own app carries the newest signed head, which commits to the chain up to its `seq`. Each app keeps the newest head it has seen, and checks that every later head and the chain items and stubs in its feed extend it, with every batch complete, no stub stamped earlier than the one before it, and no batch ID repeated less than 30 days, by the stubs' service time, after the batch that first carried it (Sections 14.5 and 14.6). Every full item in the feed must match its stub's item hash, and a feed read that reaches the end of the feed must reach every head the app has seen. A service's signed answer that contradicts itself, such as an item that doesn't match its stub or a transition proof naming another operation than the one it answers (Sections 10.3 and 10.4), is treated as a rollback too. A head older than the newest one, from a response that was overtaken, must match the chain the app has verified, unless it lies at or behind the latest checkpoint (Section 8.4). If they don't, outside a declared provider loss (Section 13.6), the service has rolled back or forked. The app then makes no new attempts through that service, manual or automatic, and shows the conflict to the user, who resolves it by moving to another provider (Section 13.5) or, if the operator can't explain it, by declaring a provider loss (Section 13.6). Apps detect conflicting history in this way while they can verify continuity. If a restore or long absence predates retained history, they enter explicit recovery; reconciliation does not prove the missing chain's continuity (Section 8.4).
- **A service that loses committed state,** for example by restoring a database backup, must not keep serving under the same generation. Its operator tells the user, and the signer declares a provider loss, to the same operator or another. At the same operator and origin, the service starts the new generation in the existing account, afresh and with a new service key (Section 13.6). A service answers with a `seq`, a proof or a head only once what it commits is durable, and its key refuses to sign for a state behind the newest head it signed (Section 6.5): without that, a failover could lose an acknowledged attempt, and another app could get a second attempt on the same obligation authorized at the same `seq`, a fork seen only afterwards.
- **Not covered: a split view.** A service can show different apps different histories after any shared prefix, from the start or from any later point, and that isn't detected: each app checks only that new heads and items extend the newest head it has seen, and a new or restored app anchors on what the service shows it. The service signs both branches, so two of its heads at one `seq` with different hashes would prove the split, but no app compares heads with another in this version (Section 20, decision 4). A service that loses an acknowledged write and serves on is non-compliant (Section 6.5) and makes the same split; an app holding a head past the lost state sees it as a rollback, and the others don't. On a split each branch can authorize one attempt per obligation: a one-time request can be paid twice, a recurring request once per branch in every Billing Period, and an Allowance up to its limits on each branch.

### 10.2 Claims
A claim tracks one thing that must happen at most once, named by its **claim key**. Every app that might act on it, manually or as an Allowance executor, uses that same claim. Paykit's apps use one claim per obligation (a request, a Billing Period or a payment without a request); its claim key is the obligation ID (Section 14.3), and `done` means paid. A request's and a Billing Period's obligation IDs are blinded with the payer's naming key; a payment without a request's is derived from its attempt ID alone, without blinding.

- **Access:** reading claims needs `claims.read` and writing them `claims.write` (Section 3.3). Apps derive a request's obligation ID from the payee, the request and the Billing Period's start, blinded with the naming key, and a payment without a request's from its attempt ID (Section 14.3), so they all find the same claim; the service treats the claim key as opaque.
- **Claim operation fields** (Section 14.5): `claim_key`, `type`, `app_id`, `expected_step`, optional `conditions`, and per type: `attempt_id` (every type), `orphan_after` in seconds (required) and an optional `deadline` on `attempt`, and on `done` its `basis` with at most one `evidence_ref`, the BLAKE3 hash of its evidence. It is required with basis `evidence`, the counterparty's confirmation, and optional with basis `owner` or `reconcile`, the app's own proof. In Paykit the first is the payment receipt JSON and the second the proof message JSON. Anything else is `400 bad_request`.
- **Server responsibilities:**
  - validate every operation and its conditions atomically, on its **own clock**;
  - reject a stale `expected_step` with `409 conflict` and the current state;
  - never interpret `attempt_id` or `evidence_ref`.

**Attempts and states.** Each attempt has an outcome: `open`, `done`, `failed` or `unknown`. The claim's state is `FREE`, `ATTEMPTING{owner, attempt_id}` (its current attempt), or `SETTLED`. These rules connect them:
- A claim becomes SETTLED as soon as any of its attempts is done, and stays SETTLED.
- It returns to FREE when its current attempt fails or is marked unknown and none of its attempts is done.
- Outcomes of other attempts are still recorded after SETTLED, so a second `done` shows up as a `duplicate`.
- Each outcome is recorded once per attempt: a repeated `done` for an attempt that is already done is answered `409 conflict` with the current state, so the rest of its batch doesn't apply; the app re-reads and writes the rest alone.

An **orphaned** attempt is an open attempt whose owner isn't current, or whose `orphan_after` has passed since its `attempt` entry, or which a new service rebuilt from uploads after a provider loss (Section 13.6); the service checks this. For these rules an owner whose certificate has expired isn't current (Section 3.2). The paying app sets `orphan_after` to the longest its payment method can take to complete or fail, for example a day for an ordinary Lightning payment and longer for a held Lightning or an on-chain payment. Until then, while its owner is current, no other app can resolve the attempt, so a payment still in progress can't be taken over by another wallet. An owner whose certificate expired isn't current, so its open attempts are orphaned at once, whatever their `orphan_after`. The signer renews certificates well before they expire (Section 3.2), and a UI should suggest renewing an expired owner before it offers `failed`.

| # | Applies to | Entry | Allowed writer | Effect |
|---|---|---|---|---|
| 1 | FREE | `attempt` | Any app with `claims.write` | Attempt a opens; ATTEMPTING(writer, a). If an earlier attempt is `unknown`, or was resolved by an app other than its owner (`failed` or `unknown`), a is flagged `possibly_duplicate` |
| 2 | Open or `unknown` attempt a; or a `failed` attempt a of a claim rebuilt from uploads after a provider loss (Section 13.6) | `done`, basis `owner` | Owner of a | a done; claim SETTLED; `duplicate` if another attempt was already done |
| 3 | Open, `unknown` or `failed` attempt a, also on a tombstone | `done`, basis `evidence` | Any app with `claims.write`, citing `evidence_ref` | As row 2. Before writing, the app verifies the evidence. In Paykit it is the payee's receipt: the app verifies its issuer, request and Billing Period, and that it confirms the proof of attempt a. A receipt carries no amount: the amount is the one that proof reports paid, the request's or the period's, or the proof's own for a payment without a request |
| 4 | Open, orphaned attempt a | `done`, basis `reconcile` | Any app with `claims.write`, after the user confirms | As row 2 |
| 5 | Open or `unknown` attempt a | `failed` | Owner of a; or, for an `unknown` or orphaned open attempt whose owner isn't current, any app with `claims.write` after the user confirms | a failed. If a is the current attempt and none is done: FREE |
| 6 | Open, orphaned attempt a, claim not SETTLED | `unknown` | Any app with `claims.write`, after the user confirms | a unknown; FREE |
| 7 | SETTLED | `attempt` or `unknown` | - | Rejected |

- **Attempts never expire.** Orphan age only allows reconciliation (rows 4 to 6); it never frees the claim by itself.
- **Finished claims** may be compacted to tombstones, which keep their outcome until 30 days after the claim's deadline, the reconciliation window, or 400 days after their last entry if it has none (Section 6.3). A claim whose every attempt failed is kept as long, so a late receipt can still correct it (row 3).
- **Per app:** the app whose `attempt` creates a claim is its creator, and the claim counts against that app's share of the claim limit, a quarter by default; an app holds at most 1,000 attempts open or `unknown` at once (Section 6.3).
- **A second wallet** that writes `attempt` while another attempt is open gets `409 conflict` with the current state, and shows "being handled by your other wallet".
- **Deadlines:** an attempt on a one-time request carries `deadline: d + 1 ms`, where `d` is the earlier of its proposal expiry and its payment deadline. An attempt on a Billing Period carries it with `d` the period's start plus the payment deadline's `seconds`. A request with neither carries no `deadline`. `d` is taken at millisecond precision, the precision of every time comparison (`specs/v0.2/wire-format.md` Section 1.6). The service rejects an `attempt` once its clock reaches the `deadline`, so `d` is the last instant at which it takes one. The first `attempt` on a claim pins its deadline, including none: the service refuses a later `attempt` that names another (`409 conflict`), and the claim view shows the pinned deadline, so apps can compare it with their own. The service thus bounds, on its own clock, when an attempt may start; the payee still checks v0.1's inclusive deadline against the verified payment time, read as for the rates of period details (Section 11.2). The proposal expiry of a recurring request bounds only its acceptance (Section 11.2).
  - An app makes no attempt once the deadline is at or before the highest service time it has verified (Section 10.1). A transition proof that stamps an attempt at or after its deadline is misbehaviour: the app pays nothing, writes `failed` and makes no new attempt through that service until the user resolves it, as for a rollback (Section 10.1).
  - Each app computes the deadline itself, from the request, and keeps evidence for an obligation, such as a SETTLED proof, at least until the later of the pinned deadline and its own, plus the 30-day reconciliation window during which the service keeps the tombstone, and longer for a claim pinned to "none" (Sections 6.3 and 10.4), so it can still compare, upload and repair it. A pin earlier than the app's own deadline, or any pin where the app computes none, is an alert, and the obligation is doubtful: the tombstone may already be gone while the payment it records still counts. A later pin is a conformance error. Either way the service refuses this app's own `attempt`, which names its own deadline.
- **No automatic payment of doubtful claims:** a claim with an `unknown` or orphaned attempt, or whose next attempt would be flagged `possibly_duplicate` (row 1), is attempted again only by a user who has seen "may already be paid", never automatically.
- **User confirmation** in rows 4 to 6 is an app rule; the service can't check it.

### 10.3 Shared records
A shared record is a small piece of encrypted shared state, readable by every own app holding its read scope, including apps added later.

**Shared record** (a signed `record.put` operation, Section 14.5): `{key, collection, read_scope, write_scopes, expected_version, value_sealed, app_id}`.
- **Policy:** one `read_scope` and one or more `write_scopes`, fixed at creation. A writer needs any one of the write scopes. Values are sealed under the read scope's key (Section 14.4), so writers also hold the read scope. The service only compares scope strings with the caller's certificate, with one rule of hierarchy: plain `request` covers every labelled selling scope `request:<label>`, so a `request` holder reads and writes every labelled policy, and a `request:<label>` holder only its own label's (Section 3.3). The Paykit collections have fixed policies (Section 8.3).
- **Keys are checked at creation.** A record key is derived from its collection, its blinded natural key and the hash of its policy (Section 14.3). The operation that creates a record carries those inputs (`id_inputs`); the service recomputes the key with the operation's policy and rejects a mismatch. A key can therefore only ever hold the record it was derived for, and no app can occupy it with a different policy. The service sees the collection name and the natural key blinded with the naming key (Section 14.3), so the stored key names neither the counterparty nor the request; equal inputs still link related records, and a live operator links them to counterparties through batches and timing (Section 16).
- **Versions:** a record's version is the `seq` of the write that produced it, written as (generation, `seq`). Versions are ordered by generation, then `seq`, so they only grow across the account: any write in a later generation is newer than every write from an earlier one, and a `record_version` condition names both.
- **Write:** compare-and-swap. The operation names, as `expected_version`, the version the writer read, or 0 for none, which creates the record; the service gives the new version. Policy and collection are fixed at creation; later writes repeat them and the service checks they match. `expected_version` 0 matches a record that is absent, forgotten or deleted, and carries `id_inputs`; a writer that holds a deleted record creates it again this way, so it never has to know whether the service has forgotten the key.
- **Sealed value:** up to 256 KiB, padded to a size bucket (Section 14.4). The service reads only its data epoch and scope, and the bucket, never the content. The AAD binds the record key, so a value can't be moved to another record.
- **Read:** needs `read_scope`. Returns the signed operation that wrote the current version, with the writer's certificate the service checked that write against and the transition proof that gives that version and dates it, both of which the service keeps with the record for as long as that write is current, whatever its batch's proof retention (Section 6.3). List pages and a `409` answer carry them too, and an export carries them with the record (Section 13.5). A record taken from a recovery upload after a provider loss has no proof (Section 13.6).
- **List:** by collection, in pages ordered by record key (`after` is the last key of the previous page), returning the current records the caller may read and the `seq` each page is current at.
- **Accepting a record write.** The service only compares scope strings and gives every version, and a sealed value's AEAD shows only that some holder of the read scope's key sealed it. So an app checks every record write it reads, from the feed, a read, a list page, a `409` answer or a re-read after an upload, before it acts on it:
  1. The operation's signature verifies with its writer's certificate, signed by the identity key and naming the operation's `app_id`. The app finds the certificate in the read, in its own state, or in the records of the identity's apps it keeps from the directory and the feed.
  2. The writer had standing at the write's time: in the own `identity.json` the app holds (Section 4.3), the certificate is listed; or it is an earlier certificate of a listed app, while its renewal is open or for a write before the renewal closed; or it is a removed app's, for a write at or before its `distrust_from`. Only a transition proof or a verified stub dates a write. A proof of an earlier generation, which a switch keeps with a record after a key change or carries after a cooperative move, dates it too when it verifies with the key the newest `identity.json` lists for that generation in `service_keys` (Section 4.3). An earlier certificate of a listed app counts only for a write so dated before its `until`, or while `until` is null: a write by it that nothing dates has no standing, so a switch can't pass off a write after a reduction's cutoff as an old one by withholding its proof. A removed app's write that nothing dates is doubtful, so no automatic payment relies on it (Section 13.2). A certificate that had expired at the write's time doesn't count.
  3. The key, collection and policy are those of the record read, the policy is the collection's fixed one (Section 8.3), the sealed value's scope is the read scope, the writer's certificate holds one of the write scopes, and a create's key derives from its `id_inputs`.
  4. When the app holds the write's chain stub, from the feed, the stub's item hash is the operation's (Section 14.6).

  The version comes only from a transition proof that names the operation, by its stub's item hash and the record key, or from the write's stub in the chain the app verified. Any other version, such as one in a read without a proof (an upload after a provider loss) or from an earlier service's proof, is the service's word: unauthenticated. It must still be in the write's own generation and after the version the write signed as `expected_version`. A write replaces the one an app holds only if it is newer: by number when both versions are authenticated, and otherwise by what the writes signed. A write whose version is unauthenticated must be built on the held version or a later one, and one held with an unauthenticated version is known only to be after the version it was built on. So a service can't pass an older genuine write off as newer. A write is a delete only when its sealed value opens to an empty plaintext. A write that fails a check is ignored and shown with the app it names (Section 8.2), and signed evidence of misbehaviour, such as an item that doesn't match its stub, is a rollback (Section 10.1). An app that doesn't know the writer yet reads its own `identity.json` and directory again first. A read carries the certificate the service checked the write against, kept with the record, so a renewal or a revocation later doesn't change what the write is judged by: an earlier certificate counts for a write its proof dates before the renewal closed, or while the renewal is open (check 2), and an app that reads later still takes the writer's earlier writes under a scope a renewal dropped, since the proof stays with the record. Only such a write needs a date: one by a listed certificate, or by an earlier certificate while its renewal is open, counts without one. Since `identity.json` lists the earlier generations' keys, an app added after a move or key change dates such a write as any other app does. The AAD binds the record key and scope; the operation's signature binds the writer, so the AAD needs nothing more (`specs/v0.2/wire-format.md` Sections 7.2 and 8.4.9).
- **Delete:** a write whose sealed value is empty. It passes the same checks as any write, and the version keeps increasing.
- **Forgotten deletions:** the service may forget a deleted key once nothing refers to it: its current write is the delete, the cursor of every current app that isn't lagging is at or past the delete's `seq`, so every app the service waits for has seen it, no divergent upload names the key (Section 13.6), and the account isn't frozen, since an export carries it. A forgotten key's delete keeps only its chain stub. An app that was lagging lists its collections again on its return (Section 8.2), since it may not have seen the delete. A record created again at that key, with `expected_version` 0, gets a newer version than any the key had, so it still looks newer to every app. Only live keys count against the record key limit (Section 6.3).
- **Current state only:** the service keeps each record's current value; earlier writes leave only their chain stubs (Section 6.3).

### 10.4 Paying order
Every payment follows these steps, whether it pays a one-time request, a Billing Period, a request under an Allowance or nothing requested (Section 11.4). The one exception is a payment without a request to a reusable public endpoint while the payer's own switch doesn't answer, which writes step 1's `attempt` after paying (Section 11.4, Without the switch).

1. **Write `attempt`**, conditioned on the version of the request record the app read (Section 8.3), so that a rejection or cancellation recorded since makes it fail, and on the deadline, if any (Section 10.2).
   - **Check the transfer first,** before any write. The payment method reports the asset, the amount and the largest fee it will transfer to the destination. The amount must equal the amount being paid: the request's, the period details', or the accepted quote's. A destination without an amount, such as an address or an amount-less invoice or offer, is paid exactly that amount. A destination that fixes another amount or asset, or whose amount the method can't tell before paying, is unusable for automatic payment; a manual payment shows the amount it would transfer and pays it only on the user's explicit choice. Fees don't count against Allowance limits, which count the amount paid, as in v0.1. A fee the payee can influence through the destination it chose must stay within a cap the payer app sets; above it, the destination is unusable for automatic payment, and a manual payment needs the user's choice.
   - **Reserve a single-use endpoint** in the same batch: when the destination is a single-use endpoint of a Private Payment List, the batch also writes the `payment_lists` record marking it used, at its next version (Section 11.4), whatever obligation is paid. If that write fails its version check, nothing is written: the app re-reads the record, and pays again to the next usable endpoint or asks for a newer list. An executor's batch adds its ledger and activity writes (Section 11.3), a payment without a request its activity record (Section 11.4), and an attempt on a Billing Period the request record doesn't list as attempted the write of the request record that adds it (Section 11.2).

   In parallel with the batch:
   - **check the destination:** the message or record carrying the destination verifies as in Section 8.2, carries the destination, and hasn't expired: a record at its `expires_at` or its `updated_at` plus the payee identity's record age limit, a Private Payment List at its `expires_at` or 30 days after its arrival (Sections 4.2 and 5.4); a record also names the app whose path it was read from. A request or period details carrying it name the obligation being paid by their signed fields: the request is the one paid, and period details name it first in `refs` and the Billing Period paid; a Private Payment List isn't tied to one obligation. The app that sent the request, period details or Private Payment List, or published the public endpoint, is current in the payee's `identity.json`, cached for at most 10 minutes (Sections 4.2 and 4.3), and, for a public endpoint, the higher of the Homeserver copy and the payee's switch's copy when the payer had to fetch it (Section 4.3). If that lookup failed or hasn't answered, a manual payment needs the user's explicit confirmation before any write, an automatic one isn't made, and an answer that arrives before money moves is still used;
   - revalidate the app's own `identity.json` if needed (Section 4.3).

   All three must succeed before any money moves. If any of them fails, the app writes `failed` instead of paying. An executor checks its Allowance again at this point (Section 11.3), and a payment priced by period details' rates checks that they are still usable (Section 11.2). An automatic payment isn't attempted at all while the device clock and the service's differ by more than the clock tolerance (Section 10.1, Clock bound).
2. **Pay.** For a one-time request, send the acceptance at the same time, without waiting for it.
3. **Write `done`** (basis `owner`) and update the activity record, in one batch. If the payment failed, write `failed` instead.
4. **Send the proof** to the payee.

- **Kept proofs:** before attempting, an app compares the claim with any SETTLED proof it keeps for that claim (Section 6.3). A service that shows FREE, or nothing, for a claim the app holds a signed SETTLED proof for is treated as a rollback (Section 10.1): the app makes no attempt through it and alerts the user. The one exception is a tombstone the service may already have deleted (Section 6.3): from its pinned deadline plus the 30-day reconciliation window, or, for a claim pinned to "none", from 400 days after the proof's entry, the time the switch keeps that tombstone after its last entry, which is no earlier. The app keeps the proof until the later of the bounds that apply: the later of the pinned deadline and its own, where there is one, plus the window; and, for a pin to "none", the 400 days. A pinned deadline where the app computes none (its request sets no deadline) is an early pin, and the app keeps that proof for good, since it may still pay the obligation. While the service may have deleted the tombstone but the app still keeps the proof, the pin differs from the app's own deadline (Section 10.2), early or "none" beside a deadline, so the app alerts and still treats the obligation as paid. A bound has passed, and the app may drop the proof, only when it lies before the earlier of the highest verified service time and the device clock plus 24 hours, so one far-future signed time can't make the app drop its evidence. Until then the app keeps it, compares it with the claim, and uploads it in a move or after a provider loss (Sections 13.5 and 13.6), when a faulty old service may have left the tombstone out.
- **The record shows it paid:** an app never attempts an obligation whose activity record it holds already carries the proof of a payment, whatever the claim shows. A claim without a deadline is gone 400 days after its last entry (Section 6.3), and then the record, not the claim, stops a second payment, for example of a re-sent copy of the request. So the payer never deletes the record of a paid obligation without a deadline; the user may only archive it (Section 8.3).
- The **attempt ID** is random. It is recorded in the app's payment journal before the write, and used as the payment method's idempotency key where the method supports one.
- **Only a verified answer lets money move.** If the answer to the `attempt` is lost or its service signature doesn't verify, the app doesn't pay; it re-reads the claim and continues from what a verified answer shows. The same holds for an answer whose transition proofs don't bind the batch: one proof per operation, each naming its operation by its stub's item hash, and its object (`specs/v0.2/wire-format.md` Section 7.5). Before paying, the attempt's proof must also show the app's own attempt: the claim ATTEMPTING, with this app as owner and the attempt ID it wrote current and open, at the step after the one it expected. Otherwise the app pays nothing and writes `failed`. A signed answer that fails these checks is misbehaviour, treated as a rollback (Section 10.1).
- **Starting to pay** is recorded in the journal before the payment begins. After a crash, an app whose journal shows no payment started writes `failed`; otherwise it resolves the attempt from the payment method's history (Section 10.5). This crash rule holds only for the app's current journal. A journal restored from a backup may predate a payment made after the backup, so a restored app treats its open attempts as Section 13.4 says.
- **Failed means definitively not paid.** Once a payment may have been submitted to the payment method, the owner MUST NOT write `failed` without authoritative evidence that it did not and cannot settle. A timeout, a disconnection, a crash or an ambiguous result MUST keep the attempt open: it blocks any replacement payment, keeps its Allowance reservation, and is resolved only through Section 10.5. As in the v0.1 SDK, the owner reports one of three outcomes: definitive failure, verified success, or nothing yet.
- **No second execution.** An app never carries out an attempt a second time, after a crash or otherwise, unless the payment method's idempotency on the attempt ID makes a repeat harmless or the journal shows the payment never started. When the method's history shows any record of the attempt, the app resolves the attempt from that record and never carries it out again, idempotent or not.
- **What a payment method declares:** each integration states whether it is idempotent on the attempt ID, and for how long it remembers the key; whether its history can show the outcome of a dispatch, and for how long it keeps it; and whether that history is authoritative across a restore of the paying device, because it lives with the account and not only on the device. An empty history means the payment never started only within the history's retention, counted from when the attempt was journaled, and, after a restore, only for a history that is authoritative across one. A dispatch is repeated only on an idempotent method, within its retention, and never from a restored journal. Otherwise a doubtful dispatch stays open, "may be paid", and is resolved only by a receipt or by the user. An owner that finds a payment it reported failed completed after all sends its proof, so the payee's receipt can correct the claim. The service keeps the claim for 30 days after its deadline (Section 6.3); a receipt after that can't be recorded on it, and the app that gets it shows the user that a payment marked failed was paid.
- **Doubtful window:** only a crash between paying and writing `done`, an outcome the method can't report, or a restore whose payment history can't tell (Section 13.4), leaves doubt. It always shows as "may be paid".

### 10.5 Reconciliation
- **Orphaned attempts** (Section 10.2) stay open until reconciled.
- **Resolutions:**

| Resolution | Who | Effect |
|---|---|---|
| `done`, basis `evidence` (row 3) | Any own app with `claims.write` | The attempt the evidence names is done; claim SETTLED |
| `done`, basis `reconcile` (row 4) | Any own app with `claims.write`, user-confirmed, orphaned attempt | Attempt done; claim SETTLED |
| `unknown` (row 6) | Any own app with `claims.write`, user-confirmed, orphaned attempt | Attempt unknown; claim FREE; the next attempt is flagged `possibly_duplicate` |
| `failed` on an `unknown` attempt, or on an orphaned open attempt whose owner isn't current (row 5) | Its owner while current; otherwise any own app with `claims.write`, user-confirmed | Attempt failed, so a budget reservation on it is released; from a non-owner, the next attempt is flagged `possibly_duplicate` |
| The owner's later report (rows 2 and 5) | Owner of an `unknown` attempt, while current | Done or failed, as reported |

- **Only the payee's yes counts.** A receipt can settle an attempt, because the payee confirms it was paid. Nothing from the payee shows that an attempt was not paid: a payee gains from a second payment, and may not have seen the first one yet. A reminder, a re-sent request or a `resend_request` is no evidence either way.
- Features that account for payments, such as Allowance budgets (Section 11.3), derive their accounting from the outcome of each attempt.
- **An app that isn't current can write nothing,** not even outcomes. Its attempts are reconciled through receipts or by other apps.
- **Graceful removal:** the signer warns before revoking an app, or letting its certificate lapse (Section 3.2), while it still owns open attempts, which `GET /v1/{id}/apps` lists. Apps with `allowance` warn when an Allowance's executor stops being current (Section 11.3).

## 11. Payment flows and features

### 11.1 One-time request
1. The payee sends `payment_request`, usually with its destination, admitted by the payer's allowlist, for example after an invite, and writes its `payee_activity` request record in parallel.
2. The payer's apps with `pay` receive it, with a push. The first to process it writes the `payer_activity` request record.
3. One app pays, following Section 10.4.
4. The payee verifies the proof by its own method, updates its `payee_activity` record to paid, and may send a `payment_receipt`.

- **Destination:** a request with `payment_endpoints` is paid only to those. One with `required_app_id` instead is paid only to that payee app's Private Payment List or public endpoints, and that app must be current; a request carrying both fields is invalid. One with neither, for example from an app that receives no payments itself, is paid to any of the payee's current Private Payment Lists or public endpoints, under the rules of Section 11.4, including single-use reservation and the explicit choice between private and public payment; the proof names the endpoint it used.
- **Rejecting and cancelling:** a payer app records its rejection or cancellation in the request record, in a batch conditioned on the request's claim having no open or paid attempt (`claim_step`), and sends it only after that batch succeeds. An attempt is conditioned on the request record (Section 10.4), so one own app can't reject a request while another pays it. A recurring request is answered and cancelled only as Section 11.2 says, conditioned on its Billing Periods' claims, never on a one-time obligation.
- **Labelled requests:** a hosted app holding `request:<label>` sends every request under its label and writes its records under that label's policy; the period details, receipts and cancellations of the request come from it as from any payee app. The payer's replies go to it and to the identity's apps holding `request`, which see the sale too (Sections 3.3 and 3.5).
- **Messages that cross:** a payee that receives a valid proof for an attempt treats it as payment, even if it cancelled the request meanwhile; it may refund with a new request in the other direction. A payer that has recorded a payee's cancellation makes no new attempt, and one already attempting finishes and sends its proof.

### 11.2 Recurring request
- **Billing Periods** follow one rule, the anchored period rule of `specs/allowances.md` applied to the request's `recurrence`. Boundary `k` is `anchor` plus `k * every` units: for minutes, hours, days and weeks a fixed number of seconds; for months and years a calendar step computed from the original anchor, clamped to the target month's last day when the anchor's day doesn't exist. Period `k` is `[boundary(k), boundary(k+1))`.
  - The first Billing Period is the one containing `starts_at`; the last is the one containing the instant just before `ends_at`, when set.
  - Obligation IDs name a period by its start boundary in Unix seconds (Section 14.3). Messages name it by `{starts_at, ends_at}`, which must equal a computed period; anything else is rejected.
- **Accepting:** when the user accepts the subscription, or an executor accepts it under an Allowance, the payer records the acceptance in the request record, in a batch conditioned on the version of the request record it read and on `server_time_in(null, proposal_expires_at + 1 ms)`, and sends it after that batch succeeds. The expiry is inclusive: its own millisecond is the last at which the acceptance is recorded. A rejection is recorded the same way, so an acceptance and a rejection can't both go out. Each period then has its own obligation, attempts, proof, optional period details, optional receipt and period record.
- **Period details:** for any period the payee may send `payment_period_details`, with that period's conversion rates, its destination, or both. Each carries `expires_at`. A later one for the same period, ordered by `created_at` and then `msg_id`, replaces earlier ones, and the payer uses the latest one that hasn't expired; its proof references it.
- **Rates and payment time:** as with v0.1's conversion quotes, the rates of period details apply to a payment whose independently verified payment time is at or before their `expires_at`, compared at millisecond precision. That time comes from the payment method's evidence (`specs/payment-conversion.md`), never from when the proof arrived. Both sides apply it. The payer pays by the rates only while its device clock and the latest service time it has verified are both before `expires_at`, checked again just before money moves (Section 10.4); otherwise it waits for newer period details, or pays to an endpoint of the requested asset. The payee credits a payment at those rates only if its verified payment time is at or before `expires_at`. A payment verified later doesn't pay the period at those rates. As in v0.1, late evidence isn't malformed: the payee still credits the funds received and may label them underpaid, late, or both, and sends no receipt for the period; Paykit adds no refunds, disputes or resolution. A payment to an endpoint of the requested asset is paid 1:1 without rates, so this bound doesn't apply to it, and the destination of period details is used while they haven't expired, as above. An Allowance counts the requested asset and amount and can't authorize repricing, so a payment priced by rates is made only by hand (Section 11.3).
- **Destinations per period:** without `per_period_endpoints`, the request's destination serves every period. With it, the request's `payment_endpoints` serve only the first period, and the payer never attempts a later period before receiving period details with its destination.
- **Not before its start:** no app pays a Billing Period automatically before it starts, and the service enforces it: every attempt on a period carries `server_time_in(s, null)`, so the service applies it only from `s` on its own clock, whatever the payer's clock says. `s` is the period's start. A payer pays a period before its start only by hand, after its user confirms paying that period early; that attempt carries as `s` the time of the confirmation, the latest service time the app had verified then, so the service still never applies it before the user agreed.
- **Tombstones:** each paid period leaves a small tombstone, kept 400 days after its last entry when the request has no payment deadline (Section 6.3) and counted against the paying app's share of the claim limit. Without a payment deadline the payer also keeps the period's record for the identity's life (Section 8.3). So payees of frequent subscriptions should set one.
- **Attempted periods:** a payer's request record lists, in `attempted_periods`, the start of every Billing Period that may have an open attempt: at most 16, in ascending order, each once. An attempt on a period not listed writes the request record in the attempt's batch, adding the period, at the record's next version; the attempt is already conditioned on the version it read (Section 10.4 step 1). An attempt on a listed period doesn't write it. A write of the request record may drop a listed period whose claim has no open attempt, conditioned on that claim's step as the writer read it (`claim_step`), so a new attempt on that period meanwhile makes the write fail. Apps drop finished periods whenever they write the record anyway, for example when adding one. With 16 listed and none to drop, an app makes no attempt on a period not listed until one of them finishes. So every period with an open attempt is listed in the version of the request record its attempt's batch left, the one it was conditioned on or the one it wrote, and stays listed until its claim has no open attempt. This covers every period an attempt may pay: the current one, one paid early by hand (Not before its start, above), and a past one whose payment deadline, which can be longer than the period, hasn't passed.
- **Ending:** either side's cancellation ends the subscription. A payer records its cancellation in the request record, in a batch that writes the record at its next version, so conditioned on the version it read, and conditioned on the claim of every listed period being at the step read with no open attempt (`claim_step`), as in Section 11.1, and sends it after that batch succeeds. An attempt on a period not listed writes the request record, and one on a listed period moves its claim's step, so an attempt and a cancellation can't both succeed. A listed period with an open attempt refuses the cancellation: the app shows that the payment is in progress, as for a one-time request.

### 11.3 Allowances
Allowances are built entirely in apps on claims and shared records. The switch has no Allowance endpoints, objects or rules.

| Allowance concept | Primitive |
|---|---|
| Proposal, terms, the executor's grant and status | Shared record in `allowances` |
| Ledger | One shared record per Allowance in `allowance_ledgers`: an entry per attempt made under the Allowance, and running totals |
| Payment | The request's claim (Section 10.2) |

Record keys are derived from the counterparty and the `allowance_id` (Section 14.3).

**Setting up.** At acceptance, the app that will pay automatically asks its user, checks the accepted terms against the signed proposal and acceptance stored in the Allowance record, and writes its **executor grant** there: its app ID and the terms hash (Section 14.3), signed with its own signing key over the identity, the counterparty, the `allowance_id` and its `confirmed_generation`, the current generation (Section 14.2). It must hold `allowance_execute`.

**Executor.** An app pays automatically under an Allowance only while all of these hold: the record holds its own grant for the current terms and counterparty; its **consent list**, kept durably in its own state, holds the Allowance; and the request comes from that counterparty and is priced in the Allowance's own asset, as in v0.1 (Section 20). It adds an Allowance to the list when it writes the grant, and removes it for good when it sees the Allowance ended, rejected or handed off. No other app can make it pay: a grant can't be forged or moved to another counterparty, changing the terms voids it, and an end it has seen is final.

**Ends reach the executor.** Any app with `allowance` may end an Allowance (Section 22, question 11). An app that ends an Allowance, hands it off, or records an `allowance_end` from the counterparty also sends `executor_notice` to the executor through its own identity's inbox (Section 7), so the executor learns of it even if the record is rewritten afterwards. A notice changes only the executor's consent list; ending the Allowance itself is the `allowance_end` exchanged with the counterparty. **After a restore** from backup, an executor asks the user to confirm each Allowance on its consent list again before paying under it, since its backup may predate an end. This relies on the record: if a compromised own app rewrote an ended Allowance as running before the restore, the user's confirmation is the only check left. Every executor batch carries `record_version(Allowance record) == r`, so once the record changes, an executor working from the older version fails and re-reads it. Handing off means the new executor writes its own grant, with its user's consent, replacing the old one; the previous executor stops at its next batch. Paykit coordinates which app pays automatically and what it reserved. Carrying out payments, honouring grants and enforcing the Allowance's limits are the integrating app's job, and the service doesn't check them.

**Valid terms.** Terms that aren't valid by `specs/v0.2/wire-format.md` Section 5.15 are refused when proposed, dropped when the proposal arrives, make an Allowance record that holds them invalid (Section 8.2), and are checked again before each automatic payment. An executor never pays under them.

**Ledger.** The ledger record holds an entry for each attempt made under the Allowance: the request's obligation, the `attempt_id`, value, asset and time `at`. The value is the amount paid, which the payment method transfers exactly (Section 10.4 step 1); fees aren't counted. It also holds running totals of spent amounts and payment counts for entries already compacted.
- **Who wrote it:** apps accept a ledger version only from the executor whose grant the Allowance record held at the version that write was conditioned on. The Allowance record keeps every grant it has held, oldest first, each with the record version that the write adding it built on (the version its writer read, Section 10.3), which the writer knows before the service gives the new one; the last one is the current grant. Each grant's signature covers that version, so a history with a wrong version doesn't verify. Writers only append to it, and an app that has seen an entry ignores a write that changes or drops it (Section 8.2); for an app that hasn't, a dropped entry only makes later ledger writes fail the check, which stops automatic payment rather than trusting a ledger. To check a ledger version, an app takes the last grant whose write built on a version older than the one the ledger write was conditioned on: it must verify for the identity, the counterparty and the Allowance, name the current terms hash, and belong to the writer. This works for versions the app never saw. A ledger write without that condition, or checked against a history that doesn't verify, isn't accepted either. A ledger written by any other app stops automatic payment under that Allowance until the user confirms again: the executor fails closed instead of trusting lower usage, and after the confirmation writes the ledger again (After a confirmation, below).
- **Building on a version accepts it:** a ledger write built on a ledger version accepts that version, so the executor builds on one only once it passes every check: the kept version (Last ledger version, below), no write of the Allowance record or the ledger by a removed app after its `distrust_from` (Section 13.2 step 3), Who wrote it, and the ledger rules (From one version to the next, below). This holds for every ledger write it makes: the executor batch, an outcome, an outcome copied from a claim, a compaction and a release. If the ledger fails them, the executor writes no ledger version on it, and the Allowance needs its user's confirmation again; an outcome batch then records the attempt's outcome on its claim alone.
- **A grant implies a ledger:** right after it writes the first grant of an Allowance, its executor writes the empty ledger, conditioned on the new Allowance record version. Until that write lands, the executor alone takes the absence as an empty ledger. From then on a missing or deleted ledger is untrusted, "usage history lost": no automatic payment until the user confirms again. A visible delete is judged by its writer like any other write. Only an absence that contradicts the version the executor kept is a rollback (Last ledger version).
- **From one version to the next:** an app that holds a ledger version checks each newer one against it and ignores and flags one that counts less (Section 8.2), and the executor checks the ledger it builds on against the last version it accepted. An entry keeps its obligation, `attempt_id`, value, asset and time. Its outcome only goes from none to `done` or `failed`, or from `failed` to `done`. It leaves only by compaction, once old enough: a `done` one into the totals, and one the reader held without an outcome or `failed` into the compacted failed list, or into the totals, since it may have become `done` before it was compacted. A compacted failed attempt leaves that list only into the totals, and the totals never grow by less than what left them. New entries may come in any time.
- **Time of an entry:** each executor batch carries `server_time_in(at, at + 60 s)`, with `at` taken from the server time of the service's latest response and the interval cut short at the next boundary of any anchored limit. The entry therefore lies in exactly one period of every anchored limit. For a rolling limit of length L it counts from `at` until `at + 60 s + L`. The service can't write inside the sealed ledger, so the executor states the time and the condition makes the service vouch for it: whatever an executor's own clock says, its entries are dated within 60 s of when the service applied them, so every app and every later executor counts each payment in the same period.
- **Usage:** each app derives usage over the entries as `specs/allowances.md` defines it, for every period limit, the per-payment limit and the lifetime limit, with server time in place of the wallet's admission time and watermark. Each entry counts by the outcome of the attempt it names:

| Attempt outcome (Section 10.2) | Counts as |
|---|---|
| `open` | Reserved |
| `unknown` | Reserved, until reported paid or failed |
| `done` | Spent |
| `failed`, written by the attempt's owner | Released |
| `failed`, written by another app | Reserved, until the user releases it |

- **`failed` isn't final:** a later `done` from the payee's receipt (Section 10.2 row 3) makes the attempt spent, whatever the ledger says. The service keeps the claim of a failed attempt until 30 days after its deadline (Section 6.3), and the ledger keeps a `failed` entry, or after compaction its `attempt_id` in the totals, visible to the claim-based counting at least as long, so a `done` that a late receipt records in that window spends. After the window the receipt can't be recorded on the claim: an executor that gets it marks its own entry `done` (a `failed` entry may become `done`), so the limits stay right, and every app that gets it shows the user that a payment marked failed was paid. A `failed` written by an app other than the attempt's owner, for example after the owner's certificate expired, frees nothing on its own: the executor shows the user the amount, and only the user's explicit release, which the executor records as `failed` in the entry, frees it. An entry's own `done` spends, and its own `failed` releases unless its claim now shows `done`. A compacted `failed` attempt counts the same way, in the lifetime amount, until the executor moves a later `done` of it into the totals.
- **One entry per attempt:** a retry after a failed attempt is a new attempt with its own entry, so every attempt is counted once.
- **Outcomes in the ledger:** the current executor writes each attempt's outcome into its entry as soon as it learns it, including outcomes of a previous executor's attempts, in the same batch when it records the outcome itself, so usage doesn't depend on claims that may since have been deleted (Section 6.3). It writes `done` from a claim, `failed` only when the attempt's owner wrote it or the user released the amount, and a later `done` over a `failed`, for which it reads the claims of `failed` entries again. An entry without an outcome whose claim is gone counts as spent.
- **Compaction:** when the record nears its size limit, the executor drops entries whose outcome is final and which are older than the longest period limit plus 60 s. It adds the paid amounts and counts of `done` ones to the running totals, and keeps each `failed` one's `attempt_id`, obligation and value in the totals, so that a later `done` still counts, once. A ledger with an entry in another asset than the Allowance's, an attempt listed twice, or a value or time that doesn't parse is invalid: usage and compaction refuse it rather than count it as less.
- **Local usage:** only a cache, rebuilt on start, restore and handoff from the ledger record and, for entries without an outcome, the request claims.
- **Last ledger version:** the executor keeps the last ledger write it wrote or read with an authenticated version, from the transition proof it got with the write or the verified stub of the feed item (Section 10.3), and the write's item hash. A version number alone proves nothing, since the service gives it. Before an automatic payment it reads the ledger record: the write shown must be that one, by item hash, or one signed as built on that version or a later one (its `expected_version`). Any other write, a missing ledger record, or one that fails the checks of Section 10.3 is a rollback (Section 10.1). Two cases aren't. A write whose signature verifies with its writer's certificate, that is the kept write or is signed as built on it or later, but that fails a check by policy, such as its writer's standing, Who wrote it or the ledger rules, only pauses the Allowance: the executor refuses it as untrusted (Building on a version accepts it). And a record is absent after a delete the executor saw. A write whose signature doesn't verify with its writer's certificate, or whose item doesn't match its chain stub, can only come from the service altering what it serves: it is a rollback, whether or not the executor kept a version.
- **After a confirmation:** an Allowance whose ledger the executor didn't accept needs a repair, which the user confirms with its figures shown. The executor first shows the user what the repair would write: the usage per period limit, amount and count, the lifetime amount, the entries reserved, spent and released, and the amounts held reserved by a `failed` another app wrote. The user confirms those figures, and the confirmation writes exactly that ledger; if anything it was built from changed in between, the executor refuses and shows the new figures. The repair writes the ledger again, as a merge that never counts less: the last ledger version it accepted, which it keeps with its content, as it was; what the ledger shown adds to it (entries it lacks, a `done`, higher totals); every attempt its journal holds under the Allowance; and every attempt of an app named in the grant history that the claims of the counterparty's obligations show, unless the payment's verified proof names no Allowance or another one. Without an accepted version, the ledger shown is the only record of compacted totals, so the figures the user confirms are all there is to check them against.

**Paying under an Allowance:**

1. The executor reads the Allowance record, the ledger record and the request's claim.
2. It recomputes usage and checks the terms and limits at the current server time, and the transfer (Section 10.4 step 1): a destination that transfers another amount, or one the method can't tell, isn't paid automatically, nor is a payment priced by period details' rates (Section 11.2). It pays nothing automatically while its device clock and the service's differ by more than the clock tolerance (Section 10.1, Clock bound). Terms are checked whole against the table of `specs/v0.2/wire-format.md` Section 5.15; a time that doesn't parse fails closed, never as no limit.
3. It sends one batch:
   - the `attempt` on the request's claim;
   - the ledger record with the new entry, at its next version;
   - the activity record showing the payment as being handled;
   - when the activity record is a period record, a write of the request record that names the Allowance, at the request's first automatic payment (One Allowance per request, below), or adds the period to `attempted_periods` (Section 11.2), or both in one write, since a batch writes a record once;

   with the conditions `record_version(Allowance record) == r`, `server_time_in(at, at + 60 s)` and, on the attempt, the request's `deadline` (Section 10.2), the version of the request record it read (Section 10.4) and, for a Billing Period, the period's start as its not-before (Section 11.2).
4. It follows Section 10.4. Proofs carry `allowance_id`.

- **Conflicts:** if any check fails, nothing is written and the executor recomputes. The ledger record's version serializes every executor batch for the Allowance; a change to the terms, status or grant changes the Allowance record's version; a late batch fails `server_time_in`. If another wallet is already attempting the request, the attempt fails and nothing is added to the ledger.
- **Doubtful obligations:** an executor never attempts an obligation with an `unknown` or orphaned attempt, or whose next attempt would be flagged `possibly_duplicate` (Section 10.2).
- **One Allowance per request:** the first automatic payment of a request names its Allowance in the request record, in the attempt's batch, and every later automatic payment of the request or of its Billing Periods is made only under that one, as in v0.1. An ended, handed-off or exhausted Allowance leaves the request to manual payment: the executor never picks another one for it. An app that has seen the name ignores and flags a write that changes it (Section 8.2).
- **Limits:** the executor enforces the Allowance limits. Paykit coordinates the reservation (one ledger version, one terms version, server time) and never enforces spending limits at the protocol level, so a faulty or malicious executor can still exceed them.

**Handoff:** outstanding attempts keep counting as reserved until their outcomes arrive. The previous executor may still record the outcomes of its own attempts on their claims, without touching the ledger, which only the current executor writes; the new executor copies those outcomes into the ledger. Any other batch of the previous executor fails the Allowance record condition. A handoff doesn't cancel payments already started. When an executor stops being current, apps holding `allowance` prompt the user to choose another.

**Ending:** an app with `allowance` marks the Allowance record ended, at its expected version. The records stay as history.

**After provider loss** (Section 13.6): the Allowance record holds `confirmed_generation`, the generation in which its user last confirmed it. While that is lower than `recovery_from + 1` in the current `identity.json`, the executor makes no automatic payment under it. After the user confirms again, the executor writes a new grant with the current generation; no other app can end the pause. Earlier doubtful obligations stay blocked from automatic payment, and delayed outcomes of earlier attempts still count at their entries' times.

**Integrity:** every ledger write is a writer-signed operation, sealed and bound to its record key, so the service can't forge, alter or move amounts between Allowances. Rollback and incomplete batches are detected as in Section 10.1.

### 11.4 Paying without a request
- **Destinations:** the payee's latest Private Payment List from the `payment_lists` record, or its public endpoints. Private and public payment are separate modes, as in v0.1: the app or the user chooses one explicitly, and a payer never changes from one to the other on its own. The app that published the destination must be current (Section 10.4).
- **Record first:** before paying, the payer writes, in one batch, the `attempt` on the payment's own claim (its obligation is derived from the attempt ID alone, Section 14.3, and its `deadline` is 10 minutes after the latest service time the app has seen, so its tombstone goes 30 days after that, at the end of its reconciliation window, rather than 400 days after its last entry: there is no re-sent copy for it to stop), a `payer_activity` record for the payment, keyed by the attempt ID, and, for a single-use endpoint, the `payment_lists` record marking it used, at its next version. Two own apps therefore can't both pay one single-use endpoint, and a crash after paying leaves an attempt that shows "may be paid" and is resolved like any other (Section 10.5).
- **Without the switch:** a payment without a request to a public endpoint that isn't single-use may go ahead while the payer's own switch doesn't answer. Its obligation is its own, derived from the attempt ID, so no other app can attempt it, and a reusable endpoint has nothing to reserve. The app records the payment in its journal, still checks the destination and its own `identity.json` (fresh within 60 s and naming the service the app uses, so a switch the identity moved away from is followed first, Section 4.3), and pays. Once the switch answers again it writes the payment's `attempt` and `payer_activity` record, then `done` and the record update, and sends the proof, so the identity's other apps and the payee see it then. Until then it is in that app's journal only: if the app is restored from a backup taken before that write, the payment is lost from the shared history (Section 13.4), though not from the payment method's. Payments of requests, Billing Periods, under an Allowance or to a single-use endpoint still need the switch, since their claim or reservation is what stops a second payment.
- **After paying:** the payer writes `done` and updates the record, as in Section 10.4, and sends a `payment_proof` with no request reference. The proof is required after paying a single-use endpoint. Only the payee's receipt settles the claim by evidence: the payer matches a receipt to the payment through its record, whose counterparty must be the receipt's sender, since the obligation doesn't name the payee.
- **Unlabelled:** a payment without a request carries no label, so its proof reaches only the payee's apps holding `request`, which record and credit it (Section 3.5).
- **Credited once:** the payee records a payment without a request by its settlement: the Payment Endpoint Identifier paid and the settlement ID its payment method defines (Section 14.3). Every proof of one settlement names the same record, so a second proof with the same evidence, under a new `msg_id`, is a replay and isn't credited again. A proof whose method gives no settlement ID isn't credited. Each proof type has one spelling of its settlement ID, such as a `bitcoin-txid` proof's `txid` in lower-case hex, and a proof in another spelling isn't credited, so one settlement never names two records (`specs/v0.2/wire-format.md` Section 1.5).
- **Reusable and single-use endpoints.** Paying to a reusable endpoint consumes nothing, so the payer can pay again at once. Paying to a single-use endpoint consumes that list version until the publisher sends a newer one, even if the payment fails; the payer then asks for a newer list.
- **Publishing:** a publishing app sends its current list to the counterparties it chooses, for example each new contact, and a newer version whenever its list changes, when it receives a proof for one of its single-use endpoints, or when it receives a `private_payment_list_request` naming a used version.
- **No usable list:** if the list is missing, expired or used up, the payer sends `private_payment_list_request`. A list has expired at its `expires_at` or 30 days after the payer's inbox accepted it, whichever comes first (Section 5.4). The payee can't be forced to answer, so the payer tells the user it is waiting for the payee's list. It may offer to pay to the payee's public endpoints instead, if there are any, but pays there only when the user chooses to.

### 11.5 Two payer apps on one identity
Both receive the request and are notified. The other app learns about the payment through the feed, from the request's claim, whether a wallet or an Allowance executor paid it, and shows:
- "Being handled by your other wallet" after `attempt`;
- "Paid" only after SETTLED.

## 12. Delivery

| State | Meaning |
|---|---|
| Queued | In the sender's local outbox |
| Accepted | The recipient's inbox returned an `entry_id` and `accepted_at`. Delivery is complete; it doesn't mean an app has read it |
| Paid | For the payer: the obligation is SETTLED. For the payee: it has verified the proof |

- **No acknowledgements.** The inbox keeps an entry until every target app that is still current has read it, however long that takes, unless the app is marked lagging (Section 6.3). Replies such as acceptance, proof and receipt carry the payment flow; nothing else confirms delivery.
- **Retries until accepted:**
  - The outbox is durable. The app retries with backoff whenever it runs: on start, on returning to the foreground, when the network comes back, and in background time the platform gives it. It reuses the envelope bytes and so the `msg_id`, and retries `503` answers, including `staged`, and `429 quota_exceeded`.
  - A send answered with `stale_key` is sealed again to the current receive keys, with the same signed plaintext and so the same `msg_id`.
  - A send answered with `410 moved` waits until the recipient's `identity.json` names the new service, then goes there. If the freeze is cancelled instead (Section 13.5), the old service accepts writes again, and the sender retries it.
- **Sender retention:** the sender keeps the signed plaintext and `accepted_at` of each message it sent for at least 30 days from its first acceptance, to answer `resend_request`; it may keep them longer, but answers a `resend_request` only with messages first accepted in the last 30 days, the time recipients keep processed IDs, so every copy it re-sends is still deduplicated. A re-send doesn't restart this: the sender keeps one entry per `msg_id`, with its first acceptance time and the later ones, and a request naming any of those times selects it. A re-sent message is sealed to the current receive keys and keeps its `msg_id` and signed plaintext.
- **Provider changes:** pending entries go to the new service in a cooperative move (Section 13.5). After a provider loss, entries the old service held are gone, and the recovering apps ask their counterparties to re-send (Section 13.6).
- **Deduplication:**
  - The server recognizes a repeated append while it still holds the entry (Section 6.1).
  - Each app keeps processed (sender identity, `msg_id`) pairs with the message's hash durably, for at least as long as senders answer re-sends (30 days from a message's first acceptance) plus clock tolerance. A second message with the same pair and different bytes is rejected and shown as a conflict.
  - A re-sent request, even after that window, has the same obligation ID, so its claim shows whether it was already handled; once a claim without a deadline is gone, 400 days after its last entry, the payer's record of the payment does (Sections 8.3 and 10.4).
  - Shared records list the `msg_id`s of the messages they store and of at most 16 others they reflect, the newest, so a second own app doesn't apply a message twice. Older IDs are dropped, and each app's own processed pairs cover them, so a record stays bounded however many messages repeat a role it holds; a message a record stores counts as reflected whether or not the list names it.
  - Deduplication and the conflict check hold per reading app: each app judges a (sender identity, `msg_id`) pair by its own processed pairs and the records it reads. A sender that sends different messages under one `msg_id` to different own apps is noticed only by an app that sees both, and a copy that reaches an app past its window, or an app added later, is judged by the records alone.
  - A cursor advances only together with, or after, the shared record write, or after the app has stored the entry locally because the write can't be made yet (Section 8.2).
  - Rollback to an older backup and external effects are handled by reconcile mode, claims and the journal (Section 13.4).
- **Removed senders:** recipient apps check every sender app against the sender identity's `identity.json`. A message from an app listed in `removed` is rejected if the recipient's inbox accepted it after its `distrust_from`; a message from an app in neither `apps` nor `removed` is rejected. A message carrying an earlier certificate listed in `renewed` is accepted while its renewal is in progress or if the inbox accepted it before `until`, and a message whose certificate had expired when the inbox accepted it is rejected. The feed carries the acceptance time. `distrust_from` and `until` are times on the sender's service, while `accepted_at` is stamped by the recipient's, so these comparisons allow the clock tolerance (+/-5 minutes) against the sender: a removed app's message counts only if the inbox accepted it at least 5 minutes before `distrust_from`, and a message carrying a renewed certificate only if it was accepted more than 5 minutes before `until`. A renewal isn't a distrust event, so the signer adds the tolerance to `until` (Section 3.2), and recipients then reject only messages accepted after the service took the app's new record, or, for a reduction, the renewing `identity.json`. A re-sent copy (below) is judged at its new acceptance, like any message: only the app that signed it can append it again, since recipients check that the entry's certificate is the signing app's, and a copy a removed app re-sends after its `distrust_from` is rejected however old the message.
- **Recovery request:** `resend_request` asks the counterparty to re-send messages; answering is best effort. The counterparty re-sends only kinds that the requesting app's certificate allows it to receive (Section 3.4), and a payer's replies only to an app that would take them under their label (Section 3.5). It limits what it re-sends: one message to the same requester identity at most once an hour, and at most a number of messages per requester identity a day, which it chooses (the prototype: 500). It leaves the rest out, and the requester may ask again later.
- **What an app asks for:** the service writes the unopenable, unreadable and `missed` items that lead an app to ask for re-sends, and the app can't check them, so it bounds what it asks on their word. For an entry it can't open and a `missed` item, it never asks for a time before the time of its cursor, less the clock tolerance; for an unreadable item, only after a verified departure, for an entry accepted at or before it (Section 8.2); and never for a time that doesn't parse. A `resend_request` adds no conversation entry (Section 7).

## 13. Lifecycle

### 13.1 Adding an app
1. The app generates its keys and asks for a Pubky grant, with an app request signed by its signing key and bound to the auth request (Section 3.2). The signer checks the request, shows the user the App ID it derives, its scopes and the capabilities, which must be exactly the app's own paths (Section 3.5), and refuses an App ID it revoked or saw depart, or that is listed with other keys. It approves it, and the one approval carries the grant, the app's certificate with its scopes and bundle key, and its scope keys and the naming key, sealed in a key bundle to that bundle key (Sections 3.2 and 3.6). The signer delivers `identity.json` listing the app to the switch, and publishes that version once the service accepts it (Section 4.3).
2. In one batch with the switch, the app delivers its record and registers its first receive key (Section 3.7). An app with public endpoints also publishes the record on the Homeserver.
3. The app reads the current shared records its scopes allow, then follows the feed (Section 8.4). It starts with the identity's full shared state. No other app needs to be online.
4. Senders include it at once: an append sealed for an older app set is answered `stale_key` with the new app's records, and the sender seals it again (Section 8.1).

### 13.2 Revocation
1. **Revoke at the service.** The signer calls `revoke`. Immediately, the service:
   - rejects every read, write and push from that app;
   - stops serving it entries;
   - removes its record and receive key record from the directory;
   - rejects envelopes wrapped to its receive keys with `409 stale_key`;
   - withdraws the invite codes it registered (Section 7).

   The signer also revokes the app's Pubky grant, so it can no longer write its Homeserver record (Section 3.5). The signer and the service keep the App ID for good, also once it is purged from `removed`: it is never approved, listed or served again, and a key that once was the app's stays refused even if the user restores the app from a seed and asks again (Section 3.1). Its open attempts remain (Section 10.5). If it executed an Allowance, apps holding `allowance` prompt the user to choose another executor (Section 11.3). Its conversation entries stay, so its conversations continue through the identity's other apps (Section 7).
2. **Rotate keys.** The signer stores a new key bundle for each remaining own app, holding only its scopes' keys for data epoch e+1 and any earlier epochs it lacks (Section 3.6). Storing the bundles first means writers have the new keys before they are required.
3. **Publish.** The signer delivers `identity.json` with a higher version, the app moved from `apps` to `removed` with its `distrust_from` (the revocation time, or an earlier time the user picks after a compromise), and `data_epoch` increased to e+1, to the service, then publishes it. From then on, the service accepts sealed fields only at data epoch e+1, and payers ignore the app's destinations. Own apps treat every chain item the app wrote after its `distrust_from` as doubtful: no automatic payment relies on it.
4. **Clean up.** The signer deletes the app's Homeserver record, if it has one; its grant went at step 1.
5. **Counterparties** stop wrapping to it at their next send, when the service answers `stale_key`. If ciphertext wrapped to it before the revocation leaks, the departed app can still decrypt it with any receive key it hasn't deleted. Messages from it accepted later than 5 minutes before its `distrust_from` are rejected (Section 12). Own apps also deliver the new `identity.json` (`PUT /v1/{id}/peers`, Section 6.1) to the switches of the counterparties to which they sent a message that was accepted in the last 30 days, the time senders keep sent messages (Section 12), so those switches stop admitting the revoked app at once. Each own app delivers when it sees, in its feed, an `identity.json` delivery that adds an app to `removed` or closes a renewal (Section 3.2), and only to a switch whose copy is older, by the `known_version` it last answered (Section 6.1), so most deliveries are skipped.

**What the revoked app keeps:** everything it already read, including the scope keys for data epochs up to e, whether from its approval or from bundles, and the naming key, which doesn't rotate (Section 3.6). The service stops serving it immediately (step 1). After step 3 it can't read shared records written later, even if the service or a leaked backup hands them over. Older data is not re-encrypted.

**Reductions rotate too.** A renewal that removes a scope with keys rotates the data epoch the same way, steps 2 and 3 with the app kept: its bundle for e+1 is made for its new certificate and lacks that scope's key, and the renewing delivery raises `data_epoch` (Section 3.2). So the reduced app can't read data under the removed scope written after that delivery.

### 13.3 Leaving and inactivity
- **Clean leave** (the user logs out or disconnects the app): the app calls `leave` and then deletes its keys. The service treats it exactly like a revocation, records the departure (listed by `GET /v1/{id}/apps` and included in exports, so the departed app can't come back from a stale record) and flags it for rotation. When the signer is next online, it revokes the app's Pubky grant and completes steps 2 to 4 of Section 13.2, with the departure time as `distrust_from`; the App ID is kept for good, as after a revocation. Deleting keys can't be verified, so a leave always leads to a rotation. Until then `identity.json` still lists the app, so its destinations stay payable. An app that publishes destinations therefore leaves in two steps where it can: it deletes its Homeserver record and calls `leave`, and deletes its keys only after the signer has published the app as removed and payers' 10-minute caches have passed. An immediate leave, for example on uninstall, warns the user that payments to its destinations may still arrive. If the app executed an Allowance, apps holding `allowance` prompt the user, as after a revocation.
- **Silent leave** (the app is uninstalled, or every device is lost or wiped): nothing reports it.
  - The service records each app's last-seen time, and the signer lists them (`GET /v1/{id}/apps`).
  - The signer app decides when to suggest removing an app that hasn't been seen for a while; 90 days is a reasonable default. Nothing is removed automatically, and removal is a normal revocation.
  - Every certificate carries `expires_at`, 1 year after it is issued by default and at most 2, which the signer renews for current apps at its next run once less than half the lifetime remains (Section 3.2). The service rejects expired certificates, so an app nobody has removed stops being served once the signer stops renewing it.
- **Reinstalling:** a reinstall that can't restore the app's keys and state enrolls as a new app, and the old app is removed. Keys left in platform storage (on iOS, keychain items can outlive the app) are deleted unless the app restores its full state with them.

### 13.4 Restore
- **Backups** are the app's responsibility: whether it keeps one, where, and how. Keeping it in the app's private Homeserver folder (Section 4.1) is an option, not a requirement. Whatever the app chooses, a backup is encrypted under a key that the app or its user holds, never one derived from a Shared Data Key, since every app with that scope could otherwise read the backup's signing key, and it is best refreshed at every receive key rotation (Section 3.7). A backup that holds the signing key lets whoever reads it register receive keys and read new messages until the app is revoked (Section 3.7). Apps should therefore keep the signing key out of routine backups, or encrypt it under a separate key the user holds, so that a leaked backup is a confidentiality incident, not an impersonation. An app without a backup that loses its state joins again as a new app (Section 13.3).
- **First, is the previous device still yours?** Before restoring, the app asks the user whether the device the backup came from is still in the user's hands. If it was lost or stolen, a restore would give the new device the same signing key as whoever holds the old one, so a restore alone doesn't cut off a thief. The user revokes the old app instead (Section 13.2, with `distrust_from` at or before the loss) and adds this device as a new app (Section 13.1), with new keys or the next index of a derivation profile (Section 3.1); the old app's open attempts become orphaned and are resolved as Section 10.2 says. Only for a device the user still holds, or one known to be wiped, does the restore go on.

1. **Restore:** the signing key, bundle key, receive key, scope keys and naming key come back, and the app reads its feed from its backed-up cursor. Operations stay in the chain, so the feed shows every claim entry since the backup and the current value of every shared record written since. A backup that names a lost provider follows the newest `identity.json` to the new one first (Section 13.6).
   - **Older than the retained history:** if the service has checkpointed past the backup's position and dropped the stubs behind it, the app can't verify continuity from the backup and continues from the checkpoint only as a recovery decision (Section 8.4); this reconcile mode covers it, and its end ends that state.
   - **Certificate:** if its backup predates a renewal it took, the app takes the certificate its `identity.json` lists from its own app record (Section 3.2 step 3) before it sends anything or reads its key bundle parts, which name that certificate (Section 3.6).
   - **Receive keys:** the app reads its current receive key record from the directory. If its restored key is the current one, the app continues with it. If not, because it rotated after the backup, it registers a fresh key before reading the feed. Entries wrapped to keys it doesn't hold, and its own earlier registrations of them, are passed, and the app asks their senders to re-send (Section 8.2); the senders seal those messages again to the new key.
   - **Registrations since the backup:** every registration after the backup's newest key whose kid the app doesn't know may be its own or a thief's. The app asks the user whether it ran on this device after the backup, and makes no attempts until the answer; a "no" is a compromise (Section 3.7).
2. **Reconcile mode:** it makes **no new attempts** until these steps have run:
   1. Fetch the shared records it uses, and the claims of the obligations in records that aren't final.
   2. Mark as uncertain any attempt of its own, seen in the feed or the claims, that is missing from its restored journal, on any obligation its records name: a request, a Billing Period or a payment without a request. Mark as uncertain too every attempt its restored journal shows unfinished and the claim shows still `open` or `unknown`, whatever its journal stage: the backup may predate a payment, so the crash rule of Section 10.4 doesn't apply. Resolve those through the wallet's own payment history, as far as the payment method declares it authoritative across a restore (Section 10.4): any record of the attempt settles it, and an empty history means "never started" only for such a method, within its retention. Otherwise they stay "may be paid", resolved by a receipt or Section 10.5; the app never writes `failed` for them on its own.
   3. Rebuild derived state, such as Allowance usage, from the shared records and claims.
   4. Resume. Reconcile mode ends once these steps have run and the journal holds every own attempt they found, even if some are still uncertain. From then on uncertainty is per obligation, as in Section 13.6: an obligation with an uncertain attempt stays "may be paid" until that attempt resolves, and every other obligation is paid as usual.
3. **Recoverability:**
   - **Always:** claims and shared records, so every lasting effect of a processed message.
   - **If they still exist:** inbox entries after the backed-up cursor.
   - **Best effort:** messages the counterparty still has (`resend_request`).
4. **What the app shows:** attempts missing from its journal, and restored ones its payment history can't account for, are "may be paid" until resolved. Until then there is no automatic payment of their obligations, and a manual payment of one only after the user confirms "may already be paid"; other obligations aren't held back.

### 13.5 Moving to another provider (cooperative)
1. **Enroll:** the signer enrolls the new service N with the current `identity.json` and the App IDs it revoked or saw depart, which N keeps as tombstones from the start (Section 13.2). N stays staged: until it holds the `identity.json` that names it, it accepts only the import and uploads, and answers everything else with `503 staged`.
2. **Freeze:** the signer sends O a signed freeze naming N's URL and service key, the next generation g+1, its `issued_at` and a random nonce. Before it does, it completes the rotations that departures still owe (Section 13.3), so N never has to take a pending departure on O's word, and it checks that N's announced import limit is at least O's (Section 6.3); otherwise it doesn't move. It keeps the signed freeze before it sends it and sends those same bytes again until it has an answer: O answers the same freeze again with its original proof, and any other freeze while it is frozen with a conflict naming the freeze it holds, so a lost answer never strands the signer. A freeze is used once: one that an unfreeze cancelled is never applied again, so a replay can't freeze O after an abort. A move waits while admission is staged after a provider loss (Section 13.6 step 2): O refuses the freeze until the lists are restored or the signer ends the staging, since an export doesn't carry staged admission. From then on O's chain is final: apps can still read it, but it rejects every operation, late outcomes included, and answers inbox writes with `410 moved`, carrying the signed freeze. Feed pages of a frozen account carry the signed freeze too, so an app that only reads, with its cursor moves deferred (Section 8.2), learns of the move and uploads its evidence (step 3). O's public read of `identity.json` answers with its last document and the signed freeze, so a payer holding an old document that names O follows the freeze to N (Section 4.3). O keeps answering it so, after the move, for at least the identity's record age limit (90 days by default), after which no app record from before the move is payable (Section 4.2) and the signer may erase the account there (Section 13.7). Apps queue their writes, including late outcomes, and submit them to N after step 4; senders hold their messages (Section 12).
3. **Export and verify:**
   - **Uploads:** after the freeze, apps read O's feed to its end, then upload to N their newest signed head and the evidence they hold: the SETTLED and tombstone proofs they keep, through the later of each obligation's pinned deadline and their own plus 30 days (Section 10.4), the record versions they hold, with O's transition proofs, and the proofs of their own attempts still open. An app whose continuity is unverified (Section 8.4) uploads no head until it has reconciled, since it hasn't verified the chain the head would vouch for.
   - **Manifest:** the signer reads O's export manifest (`GET /v1/{id}/export`). O exports only while frozen, builds the export once per freeze and answers every retry the same way. The manifest is signed with O's service key and names the signed freeze, generations g and g+1, the last committed service time, the signed head the export ends at, and the chunks: each chunk's ID, length, BLAKE3 hash and the range of parts it holds, at most 1 MiB each. The parts cover every chain stub O still keeps, from the oldest, with the current value of each object, claims and tombstones, shared records with the transition proof that dates each one's current write, apps with their records, receive key records, key bundles, cursors and last-seen times, departures, pending inbox entries, contacts, conversation entries, the deny list, invite codes, connect requests, peer copies of `identity.json`, and the version floors dropped peer copies left (Section 6.3), so N refuses an older delivery as O did. Each operation travels once: a shared record names the chain item that holds its operation instead of carrying it again, and no batch proofs travel, since they serve only retries at O; N refuses an export that carries any. Every part fits one chunk, however long the account has lived: an app's key bundle parts, a live claim's entries and a record's divergent uploads each travel as parts of their own, and a signed operation is at most 512 KiB (Section 14.5), so N can take every account the limits allow (`specs/v0.2/wire-format.md` Section 11.3). The manifest's checkpoint is a head O signs for the newest stub it dropped, at the `seq` and chain hash it keeps for it (Section 6.3). O drops stubs oldest first, so that is the chain item just before the oldest stub it keeps, and its chain hash is that stub's previous chain hash; there is none when O keeps the whole chain. It needn't be O's latest checkpoint, which may lie ahead of stubs O keeps (Section 8.4). So every app whose stubs O's cursor rule keeps still finds them at N.
   - **Chunks:** the export goes from O to N directly, not through the signer's device. The signer signs an **export transfer** (`specs/v0.2/wire-format.md` Section 3.12): the authorization, under the identity key, naming the freeze, the manifest, O (its origin and the account's key there) and N (its origin and the key the freeze names). It starts the import at N with the manifest, the signed freeze and the export transfer (`POST /v1/{id}/import`). N checks that the freeze names it, that O's service key, as N's `identity.json` names it, signed the manifest, and that the export transfer is for this move; it then fetches each chunk it lacks from O (`GET /v1/{id}/export/chunks/{chunk_id}`), presenting the export transfer and signing each request with its own key for the account, checks it against the manifest and stores it. O serves the export to N only under an export transfer the identity signed that names its freeze, its manifest, itself and the next service the freeze names, and only to that service's key. N answers with the chunks it still lacks, and why it stopped, if it did. A production N fetches in the background once it has answered the import start, and the signer polls the import status by sending the same start again, which answers an import in progress with its status, until no chunk is missing or N names why it stopped; the prototype fetches before it answers, so that call lasts as long as the transfer (`specs/v0.2/wire-format.md` Section 11.4). **Fallback:** the signer can still fetch each missing chunk from O itself and store it at N (`PUT /v1/{id}/import/chunks/{chunk_id}`), for example when N can't reach O. A chunk already stored is a no-op; bytes with another hash are refused. Nothing is live yet, and every step can be repeated: an interrupted signer asks N which chunks it still lacks. The signer signs the freeze, the export transfer and the activation; it needn't carry the export.
   - **Activation:** the signer activates the import (`POST /v1/{id}/import/activate`), naming the manifest hash. N checks that every chunk is present, rebuilds the state, verifies the chain from its stubs, from the checkpoint or the first item, up to the manifest's head, which must be O's freeze transition, with every check an app makes on a stub (Section 10.1), so the apps O kept stubs for can read them at N, and checks that it extends every head the apps uploaded at or after the checkpoint. A head older than the checkpoint can't be checked against the imported chain, which starts after the checkpoint, so N ignores it: it is neither evidence for nor against the import. An honest app holds one only if O dropped the stubs after its position, as O may for an app more than 30 days behind or one restored from a backup (Section 8.4), so N doesn't refuse the activation for it. Parts out of the order the wire format fixes are refused (`specs/v0.2/wire-format.md` Sections 11.3 and 11.5). It checks that the imported `identity.json` is the one it was enrolled with or a newer one, at the same generation, and the newest one the imported chain holds, so O can't roll the identity back to a version that still lists a revoked app or an earlier data epoch; the signer, for its part, never builds on a lower version than it delivered (Section 4.3). It checks the rest of the state against the signed items it stands for, never taking a label O wrote. It accepts O's last committed time and the freeze time only within the clock tolerance of its own trusted time, and refuses the activation without trusted time (Section 10.1); the checkpoint must lie before the head, and O's last `seq` must be the head's. A shared record is derived from its signed operation, which verifies with its writer's certificate and holds one of its write scopes, and carries the transition proof of its current write, which names that write and verifies with the service key of its generation, O's or one the imported `identity.json` lists (Section 4.3), unless it came from a recovery upload: its key, collection, policy, writer, delete and size are the operation's, a write after the checkpoint is the chain item at its `seq` with that `seq` as its version and no later write of its key in the chain, and one at or behind the checkpoint is no later than the checkpoint. A live claim is replayed from its signed entries: their steps increase, each is the chain item at its `seq` with O's proof for it, and the claim's state is the one its last entry's proof shows. Every app the imported `identity.json` lists, and every app whose registration the chain holds, has its part, so O can't leave an app out. An app's receive key records come in increasing order, each is its chain item, and the newest registration the chain holds is the current key; a departure or revocation the chain records stays one, whatever the app's part says. Finally it checks the import against the evidence apps uploaded: an obligation a proof shows SETTLED must be SETTLED, unless its tombstone's deadline plus the 30-day reconciliation window is at or before O's last committed time, or, without a deadline, 400 days after the proof's entry is; an attempt an owner's proof shows must still be held; and a record must be the write a proof names, by its item hash, or one built on that version or a later one. It refuses the import otherwise. Evidence an app uploads after the activation is checked at once, and a mismatch is an import conflict, which holds back the `identity.json` naming N until the signer aborts. Only then does N make the imported state live, in one step. N continues O's `seq`, chain and service time under generation g+1, so cursors and heads stay valid. It refuses the `identity.json` naming it until the activation.
4. **Publish:** the signer delivers `identity.json` with generation g+1 and a higher version, naming N and keeping in `service_keys` the key of every generation O reports that a current record's proof names (Section 4.3), to N, which then accepts app operations and inbox writes, and then publishes it. Apps re-register their push handles bound to a push key from N (Section 9). Once it follows, each app:
   - uploads O's SETTLED proofs it keeps again, so the evidence of an app that missed the move still counts: N merges each one bound to the imported chain as after a provider loss (Section 13.6 step 3), rebuilding a tombstone O left out, or making the obligation divergent where it holds it open, and refuses any other mismatch;
   - reads its own entry in N's directory: an older key of its own shown as current is a rollback of its registrations, so it alerts the user and registers its current key again; a key it never registered is a compromise (Section 3.7);
   - compares N's admission lists with what it knows: an app with `lists.manage` adds back the contacts and deny list entries of its own copy that N lacks, and shows the user contacts N holds that it never saw added, since its copy starts at its own registration; an app that may read the lists withdraws the invite codes N holds in its name that it never registered, and those of apps that aren't current.
5. **Authorization rule:** an `attempt` counts only when the app holds a fresh `identity.json` naming the service that signed its transition proof (Section 4.3).

- **Abort:** while N holds no `identity.json` naming it, the signer may cancel the move with a signed unfreeze naming the hash of the freeze it cancels (`POST /v1/{id}/unfreeze`). It sends the unfreeze to N first. N discards the import bound to that freeze, partial or activated, refuses any manifest bound to it from then on, and answers with a signed confirmation that it discarded the import. The signer then sends the unfreeze to O with that answer. O checks N's answer with the service key the freeze names, and resumes only when it holds that answer, so O and N never both accept writes; from then on its public read carries no freeze. Apps then submit their queued writes to O. The cancelled freeze is used up: a later move signs a new one. If N can't be reached, the move can't be cancelled: the signer completes it to N, or, if N is gone, declares a provider loss (Section 13.6).
- **Fencing:** an app whose cached `identity.json` still names O can't get an attempt authorized there, because O is frozen. In a cooperative move the freeze is the fence. An app pays only on an attempt whose transition proof is signed by the service key its own `identity.json` names and whose chain stub is of the generation it names, so a stale instance of an earlier generation authorizes nothing, even at the same origin.
- **Key rotation in place:** each service key serves one generation, so rotating it is a generation change at the same service: the signer enrolls there again, which answers a pending key, and delivers and publishes the next version at g+1 naming it, keeping in `service_keys` the key of every generation the service reports that a current record's proof names, the outgoing one included when a record needs it (Section 4.3). The service continues its sequence and chain under g+1 with the new key, and apps follow as after a move; nothing is exported. The records' proofs signed with the outgoing key stay with them and still date their writes.
- **Residual risk:** N checks the import against the chain and the evidence apps uploaded. A faulty or malicious O that omits state, such as a tombstone or a ledger record, is detected only by apps holding evidence of it: the proofs and record versions they uploaded, before the activation or after it (step 4), the SETTLED proofs they compare before attempting (Section 10.4), and an executor's last ledger version (Section 11.3). A record whose newer write O dropped from the chain together with its document, and admission state no app can vouch for, aren't detected by N; the latter is shown to the user (step 4).

### 13.6 Provider loss (O unreachable or hostile)
1. **Declare:** the signer enrolls N, naming in the signed enrollment every App ID it revoked or saw depart, so N refuses them from the start although no export reaches it (Section 13.2). It then delivers `identity.json` with generation g+1, a higher version and `recovery_from: g`, naming N, to N, and publishes it once N accepts. N may be the same operator and origin as O: the enrollment there answers a pending key for the next generation, since each service key serves one generation, and the document at g+1 naming that key starts generation g+1 in the existing account. It starts afresh, as a new service would: committed state it may have lost can't be trusted, so it keeps only its service time, which never goes back, and the App IDs it must refuse, and the old key signs nothing more. N starts a new sequence and chain for generation g+1, beginning with a service-signed recovery record naming g; that record's server time is the time of the declaration. Apps read N's feed from its start, deliver their app records, register a receive key record with an `n` higher than every `n` they have registered (Section 3.7), and re-register their push handles bound to a push key from N (Section 9). Every app watches its own `identity.json` (Section 4.3), so even one that only receives finds N.
2. **Restore admission:** an app with `lists.manage` uploads the contacts and deny list from its own copy of the lists, which it keeps from the feed (Section 8.4). Apps with `lists.read` may upload deny entries too, which only restrict admission. Every app re-adds conversation entries for the counterparties in its records, except identities on its own copy of the deny list. Until the contacts upload arrives, N answers senders it can't otherwise admit with `503 staged`, so they retry instead of giving up; denied senders get the same answer, so the staging doesn't reveal the deny list. The signer can end the wait early (`POST /v1/{id}/recovery/admission`), for example when the app that manages contacts is gone for good; with no current app holding `lists.manage`, there is nothing to wait for.
3. **Collect:** apps upload what they hold, without decrypting anything for the service: signed operations, transition proofs, signed heads and sealed shared records. The SETTLED and tombstone proofs among them are every one an app still keeps: through the later of the obligation's pinned deadline and its own, plus 30 days (Section 10.4). Uploads are evidence: N merges them without renumbering its own sequence or rewriting entries already there. Each uploaded operation comes with its writer's certificate, which N checks against the identity key; an operation of an app listed in `removed` counts only if O's transition proof dates it before that app's `distrust_from`. An app uploads its copies of the records it holds before its first write at N. Writes at N follow N's current version of a record, whatever was uploaded. For each upload N appends one service transition listing what changed:
   - **Shared records:** uploaded versions fill in records that N lacks or holds only from earlier uploads at a lower version. They never supersede a write made at N; an upload that conflicts with one, or two different uploaded values at one version, is kept and listed as divergent until a writer writes a newer version at N. An uploaded record's version is the one O's transition proof gives it. Without that proof, the version it built on, plus one, is a lower bound: it fills in a record N lacks, and two different uploads that build on one version are divergent. A write at N conflicts with an upload newer than the uploaded version the writes at N built on, or with any upload if they built on none.
   - **Claims:** uploaded writer-signed entries merge per `attempt_id`, without re-checking their conditions or `expected_step`; evidence for an obligation N holds only as a tombstone re-opens it. An entry that carries no transition proof from O must satisfy the live writer rules of Section 10.2: `done` with basis `owner`, and `failed`, count only from the attempt's owner. Entries can only add attempts or move an obligation toward SETTLED: a writer-signed `done` of any basis settles it, flagged `duplicate` if another attempt is paid; `failed` or `unknown` applies only to an attempt still open at N. An uploaded open attempt that N lacks is added, orphaned (Section 10.2): on a FREE obligation it becomes the current attempt; if N already has an open attempt, the uploaded one is recorded beside it and the obligation is divergent. Evidence that conflicts, such as two outcomes for one attempt, makes the obligation divergent instead of applying `failed`, and a divergent obligation is doubtful: no automatic payment. It clears once every attempt on it that isn't final is resolved by its owner, a receipt, or a user-confirmed outcome. The owner may still record `done` on a `failed` attempt of a rebuilt obligation (row 2 of Section 10.2). An O-signed proof that an obligation is SETTLED with every attempt paid or failed rebuilds a tombstone for an obligation N holds nothing for. It can only move an obligation toward SETTLED, so a hostile O gains nothing by it; this is what lets apps drop claim evidence behind a checkpoint (Section 8.4).
   - **O's transition proofs and heads** show order and what apps saw; N doesn't treat them as authority, since O may be hostile.
4. **Ask for re-sends:** inbox entries that O held are lost. Each app sends `resend_request`, for messages accepted after the time of its cursor at O (the acceptance time of the last entry it processed there, which it keeps), to the counterparties of its unfinished activity records.
5. **Treat the unknown conservatively.** A missing claim is never treated as unused.
   - **Obligations from before the loss** are uncertain. Uncertainty is per obligation: an obligation is uncertain if an attempt on it could have been authorized at O, that is, if its request or Billing Period was payable before the declaration plus the residual window (residual risk, below). Apps treat as made before the loss every request already in their local state, and every request whose `created_at` is earlier than the declaration plus clock tolerance. The obligations of such a request are uncertain, except those of Billing Periods that start after the declaration plus the residual window: no app attempts a period automatically before its start, and O applied that rule on its own clock (Section 11.2). A period the user paid early by hand at O is known at N only from the uploads of the app that paid it (step 3), like any other attempt there. Re-sends reuse the original signed message, so an honest payee's old request keeps its original `created_at`; a payee that misdates requests falls outside the guarantee (Section 17). There is no automatic payment for uncertain obligations, and a manual payment requires confirming "may already be paid by another wallet". That confirmation lets that one manual payment go ahead; it doesn't end the uncertainty, so if the payment fails, the obligation stays uncertain. They resolve only through Section 10.5 and step 6.
   - **Allowance executors pause** until the user confirms each Allowance again (Section 11.3). A missed payment can't be ruled out, because both N's rebuilt state and the apps' journals may lack it.
6. **Close:** recovery ends per obligation and per Allowance. An uncertain obligation closes when it is SETTLED at N, or when the user states that it wasn't paid before the loss; nothing else closes it, not a confirmed manual payment that failed nor an `unknown` or `failed` resolution. An Allowance closes when its user confirms it again (Section 11.3). A closed obligation is paid like any other, automatically too.

**Residual risk:** N can't stop O. An app that still trusts O through a cached `identity.json` could get an attempt authorized there for up to 60 s after the declaration, or longer if its Homeserver serves it a stale `identity.json`. The residual window is 60 seconds plus the clock tolerance, since an app makes no attempt without an `identity.json` revalidated in the last 60 s (Section 4.3), plus the offset between O's and N's clocks, since O applied its time conditions on its own clock while N's dates the declaration. Each app measures that offset as the difference between the last service time it verified from O and the first from N, each taken against its own clock, and assumes twice the clock tolerance when it has none from O. Signed heads detect rollback of history an app saw; they can't prove that no newer authorization exists, which is why step 5 is conservative.

### 13.7 Erasing an account
The signer can erase the identity's account at a switch (`POST /v1/{id}/erase`, `specs/v0.2/wire-format.md` Section 8.4.16), so that a user can delete their account.

1. **Request:** a signer call like any other, signed with the identity key over the method, the path, the service's origin and a timestamp within the clock tolerance of the service's time (Section 6.1). It names the account's service key, so a replay can't erase a later account of the identity at the same service, which has another key. A request signed with an app's key, for another service's origin or at a stale time is refused.
2. **Deletion:** the service signs a confirmation with the account's service key, the last thing that key signs, and then deletes everything it holds for the identity: inbox entries, the chain and its batch records, shared records, claims and tombstones, contacts, the deny list, conversation entries, invite codes, connect requests, app records, receive key records and key bundles, cursors, push registrations and handles, its copy of the identity's `identity.json` and the peer copies it keeps for the account, enrollment answers, freeze, export and import state, rate-limit counts, and the service key with its mark (Section 6.5). It releases the confirmation only once that deletion is durable, so a crash can't leave the erased account recoverable; if the deletion can't be committed, no confirmation goes out and the signer retries. After that it knows nothing of the identity: every call for it, a retried erasure included, is answered as for an identity it doesn't host, and a later enrollment starts a new account, with a new key and nothing of the old one. What other accounts hold about the identity, such as their contacts, conversation entries and peer copies of its `identity.json`, is theirs and stays.
3. **Not during a move:** a frozen account refuses the erasure (`409 conflict`) until its export is finished, every chunk of it fetched at least once, and so does a staged account holding an import, until the signer aborts the move (Section 13.5). So a move can't lose data, and the old service can still resume. After a move given up for a provider loss (Section 13.6), the signer finishes the old service's export by fetching it itself, then erases there.
4. **For the account's life:** what Section 6.3 keeps for good, such as the App IDs of revoked and departed apps, is kept for the account's life and goes with it. The signer keeps its own records (Section 21), so a later enrollment names those App IDs again, as every enrollment does (Section 4.3). The new account starts as after a provider loss (Section 13.6), so the signer's next `identity.json` has a higher version and generation than any payer has seen.
5. **Effects:** erasing the account at the current switch is a provider loss for the identity's apps (Section 13.6), and payers' lookups of `identity.json` there fail closed (Section 4.3). So the signer asks the user to confirm, and offers erasure in two cases: at the old service after a move, once its pointer window, the record age limit, has passed (Section 13.5 step 2); and when the user stops using Paykit. In the second case it first deletes `identity.json` and the app records from the Homeserver and revokes the apps' grants, so payers find no Paykit identity instead of one whose switch doesn't answer.
6. **Backups** are the operator's duty (Section 6.5).

### 13.8 Handing the identity to another signer
An identity has one signer at a time. Any app can be its identity's signer, through the SDK's signer core, and the user can later hand the identity to a dedicated signer such as Bitkit or Ring (Section 22, decision 24). The hand-over moves the identity key and the signer's records to the new signer, as one sealed export of at most 64 envelopes (`specs/v0.2/wire-format.md` Section 3.13).

1. **The new signer is an app of the identity.** The user first approves it like any app (Section 13.1), so its certificate names its bundle key. The old signer splits the hand-over into parts, each sealed in its own envelope to that certified key, as it seals a key bundle (Section 3.6), and signs them together with the identity key over the new signer's App ID, their number and their order. Only that app opens them, and it refuses parts swapped, missing or added.
2. **What it carries:** the identity key and the signer's records:
   - the newest `identity.json` a service accepted from it: its version, generation and hash are the signer's high-water mark (Section 4.3), and it names the service keys the signer keeps (`inbox.service_key` and `service_keys`);
   - the App IDs it revoked or saw depart, kept for good (Section 13.2);
   - the certificates that `identity.json` references, of every listed app and each earlier one in `renewed`, so the new signer judges renewals and reductions as it did (Section 3.2). The signer acts on certificates only through that document: a removed or revoked app is handled by its App ID, and readers judge old writes and messages from the certificates they carry. So no other certificate is needed, and the hand-over stays within its bound however long the identity lives;
   - the limits the switch announced at enrollment, which it gives only then (Section 4.3).

   Before it seals the hand-over, the old signer delivers any closing version it owes (Section 3.2), and its newest version must be delivered. There is no hand-over during a provider move (Section 13.5).
3. **Handing over:** once it has sealed the hand-over, the old signer is handing over. It signs nothing new for the identity, no delivery, approval, renewal, revocation, rotation, key bundle, move or erasure, except an abort (below), and it keeps the key and its records until the hand-over takes effect.
4. **The new signer checks** that the hand-over opens, that the key it carries is the identity's, that its `identity.json` verifies and lists the new signer's app, and that every certificate that document lists is among those handed over. It then checks the records against the switch and the Homeserver: neither may hold an `identity.json` newer than the one handed over, or another one at its version, so a hand-over older than the switch's copy is refused. App IDs the switch reports revoked or departed join the kept ones. It then delivers the next `identity.json` version, built on the one handed over (Section 4.3), and publishes it. **The hand-over takes effect** when that delivery wins the compare-and-swap at the switch, and from then on the new signer is the only signer. A new signer that refuses the hand-over once it has opened it, at any of these checks, or whose delivery loses (`409 stale_identity`), deletes the identity secret and the records it received, and tells the user the hand-over was refused or cancelled.
5. **The old signer deletes** the identity key and every record of the signer, in every copy it keeps (Section 3.1), once it sees at the switch a version newer than the one it handed over that it didn't deliver: the new signer's. It keeps its own app keys and goes on as an ordinary app, and tells the user that it no longer manages the identity, and which app does.

- **Abort and retarget:** until the hand-over takes effect, the old signer may abort it. It delivers the version it handed over again, with the same content, at that version plus 2 and with `prev` its hash, and then publishes it. Plus 2, so that its bytes never equal the new signer's first version, plus 1 with the same content, which the switch would take as a retry of it. Exactly one of the two deliveries wins the compare-and-swap. If the abort wins, the export is dead: the new signer's check of the switch's copy (step 4), or its own delivery, fails, and either way the new signer deletes what it received. The old signer is then the signer again, and may seal a new hand-over from the new version, to the same app or another one, or carry on. If the new signer's delivery won first, the abort gets `409 stale_identity`: the old signer has been succeeded and deletes its copy (step 5). Aborting is the user's choice, for example after the target app was lost or failed for good. The app may suggest it when a hand-over hasn't taken effect after a while.

- **The limit:** the protocol can't stop an old signer that keeps a copy of the key. It is the same identity key, so the hand-over is a trust step, and the user is told so before it starts. The new signer's newer `identity.json` wins over anything older, as always (Section 4.3).
- **Keeping the key safe and backed up** is the new signer's job from then on (Section 3.1).

## 14. Encodings

### 14.1 General
- **JSON:** UTF-8 without BOM. Readers reject duplicate member names, compared after unescaping, reject lone surrogates, and reject documents whose `v` they don't support. They reject unknown members in conditions, operation bodies (at every depth, except opaque members), the entries of a batch request, certificates and receive key records (their `suite_keys` entries included), app requests and export transfers (their `from` and `to` included), so a future restriction there is never silently skipped, and ignore unknown members everywhere else. A later suite's keys still fit certificates and receive key records without a new version: they go in the reserved `suite_keys` member (Sections 3.2 and 4.4). Every integer is from 0 to 2^53 - 1, written without sign, fraction or exponent; readers, the switch and apps alike, reject any other number outside the opaque members, which the wire format names by their path: a message body's `metadata`, a payment proof body's `proof`, and an invite code's `context`, wherever it is carried. The check runs on the whole document when it is parsed, before its fields are read (`specs/v0.2/wire-format.md` Section 1.1).
- **Binary values in JSON:** base64url without padding.
- **Times:** RFC 3339, UTC, with seconds.
- **Identifiers in JSON:**

  | Value | Form |
  |---|---|
  | Pubky ID | z-base-32 public key, as defined by Pubky |
  | App ID | 16 bytes, z-base-32 |
  | kid | 8 bytes, base64url |
  | Obligation, record key, collection, hashes | 32 bytes, base64url |
  | `msg_id`, `allowance_id` | UUID version 4, lowercase hyphenated string; this form is a MUST, and readers reject any other |
  | `attempt_id`, batch ID, and the nonces of enrollments, freezes and push webhooks | 16 random bytes, base64url |
  | XChaCha20-Poly1305 nonces in envelopes and sealed fields | 24 random bytes (Sections 5.1 and 14.4) |

  Requests to the switch carry no nonce: their timestamp and signature bind them, and the service recognizes a retry by its content (Section 6.1).

- **Length-prefixed concatenation:** `lp(x1, ..., xn) = u32_be(len(x1)) || x1 || ... || u32_be(len(xn)) || xn`. Every signature input, derivation input, AAD and HPKE `info` below uses it, so fields can't be shifted between positions.
- **Field encodings inside `lp`:**

  | Field | Bytes |
  |---|---|
  | Identity, Pubky ID | 32-byte Ed25519 public key |
  | App ID | 16 bytes |
  | kid | 8 bytes |
  | Integer (`u64`) | 8 bytes, big-endian |
  | Label, scope name, collection name, method, path and query, origin | UTF-8 text |
  | Request header values (`Paykit-Timestamp`, `Paykit-Identity`, `Paykit-App`, `Paykit-Cert`, `Paykit-Invite-Code`) and `Paykit-Server-Time` | The exact header text, UTF-8, empty when the header is absent. The identity and app headers are signed as their z-base-32 text, not as key bytes |
  | Hash, object ID, key | Raw bytes |
  | Document or message body | The exact bytes |
  | Absent value | Empty (length 0) |

### 14.2 Signatures
- **Algorithm:** Ed25519 (RFC 8032), verified exactly this way, so that every implementation accepts and refuses the same signatures (`specs/v0.2/wire-format.md` Section 2.1 has the steps and the vectors):
  1. S, the second half of the signature, is below the group order L.
  2. The public key A and R, the first half, each decode to a curve point and encode back to the same 32 bytes (canonical).
  3. Neither A nor R is of small order (order 1, 2, 4 or 8).
  4. The cofactorless equation holds: the encoding of `[S]B - [k]A`, with `k = SHA-512(R || A || message)` reduced mod L, equals R's bytes.

  A mixed-order public key, a point of order 8L, is accepted, as RFC 8032 allows; nothing requires A to be torsion-free. A cofactored verifier, or one that skips step 2 or 3, isn't compliant. ed25519-dalek's `verify_strict` alone doesn't check step 2 for A.
- **Sign once:** a writer signs each document, operation and message once, keeps its exact bytes, and sends those bytes again for every retry, re-delivery and later use; it never signs or serializes it again. Retries recognized by content (Section 6.1), the no-op rules (Section 14.5), the compare-and-swap on `identity.json` and every hash over a signed document compare whole signed bytes, so a second signature of the same body counts as another document there. Deterministic signing (RFC 8032) is recommended, but nothing depends on it: a platform whose Ed25519 uses random nonces is compliant as long as it keeps the bytes. Equivocation compares bodies (Section 4.3).
- **What the identity key signs:** only the formats of the table below whose signer is the identity key (app certificates, `identity.json`, enrollments, key bundles, freezes, unfreezes, export transfers, and the signer's own requests to the switch and operations), and the formats Pubky defines for the same key (PKARR records, Pubky auth tokens and grants). Every Paykit signature input starts with the 4-byte length of its `paykit/v1/` label, so its first byte is 0; Pubky's inputs start otherwise (an auth token's with `PUBKY:AUTH`, a grant's JWS with base64url text, a PKARR packet's with `3:seq`), so no input of one format is valid in another. A signer never signs bytes a caller supplies: there is no generic signing with the identity key. A new format gets its own label in this table, and the list is kept in step with Pubky's.
- **Signature input:** `lp(label, field1, ..., fieldn)` with the label and fields below.
- **Signed documents** are carried as `{ "body": "<base64url of the exact JSON bytes>", "sig": "<base64url>" }`. Examples in this spec show the decoded body.
- **Signed document bytes** are `lp(body bytes, signature)`. Every hash over a signed document, such as a certificate hash or a chain item hash, covers these bytes, never re-serialized JSON.

| Collection | `derive("paykit/v1/collection", collection name, identity)` |
| Record key | `derive("paykit/v1/record", collection name, blind(natural key), policy hash)`. The operation that creates the record carries `blind(natural key)` in `id_inputs`, and the service recomputes the key from it and the policy (Section 10.3) |
| Natural keys | `payer_activity` and `payee_activity`: `lp(payee identity, request hash)` for a request record, and `lp(payee identity, request hash, u64(period start))` for a period record; for a payment without a request, `lp(identity, attempt_id)` on the payer's side and `lp(Payment Endpoint Identifier, settlement ID)` on the payee's, the settlement ID being the bytes the payment method defines to name one settlement, the same in every proof of it, such as a Lightning payment hash or an on-chain transaction ID, in the one spelling `specs/v0.2/wire-format.md` Section 1.5 gives each proof type. `payment_lists`: `lp(payee identity, publishing app ID)`. `allowances` and `allowance_ledgers`: `lp(counterparty identity, allowance_id)` |

### 14.4 Sealed fields

```json
{ "data_epoch": 4, "scope": "allowance", "nonce": "<24 bytes>", "ct": "<ciphertext and 16-byte tag>" }
```

- **Key:** `scope_key(data_epoch, scope)` (Section 3.6).
- **Cipher:** XChaCha20-Poly1305 with a random 24-byte nonce.
- **Padding:** the plaintext is `u32_be(len(JSON)) || JSON || zero padding`, padded to the smallest size bucket that holds it, so the stored length shows the bucket, not the exact size, as envelopes do. The buckets run from 512 bytes to 256 KiB in steps of at most half again, so padding adds at most half a value's size and about a fifth on average (`specs/v0.2/wire-format.md` Section 7.2 lists them). A delete stays the empty plaintext, unpadded, so it remains recognizable. The service refuses a value whose length isn't a bucket.
- **AAD:** `lp("paykit/v1/sealed", identity, scope, record key)`.
- **Service check:** `data_epoch` equals the current one, otherwise `409 stale_epoch`, except in uploads during a provider move or recovery (Section 13); and `scope` equals the record's `read_scope`, otherwise `400 bad_request`.

### 14.5 Operations, batches and conditions
Each operation is a signed document (Section 14.2) whose body names its type in `op`:

```json
{ "op": "claim", "identity": "<pubky id>", "app_id": "<app id>", "generation": 4,
  "batch": { "id": "<16 random bytes>", "count": 3 },
  "claim_key": "<id>", "type": "attempt", "expected_step": 2,
  "attempt_id": "<16 bytes>", "orphan_after": 86400, "deadline": "<rfc3339>",
  "conditions": [ { "record_version": { "key": "<id>", "generation": 4, "version": 17 } },
                  { "server_time_in": { "start": "<rfc3339>", "end": "<rfc3339>" } } ] }
```

| `op` | Body fields besides `op`, `identity`, `app_id`, `batch` and `conditions` | Who |
|---|---|---|
| `claim` | `claim_key`, `type`, `expected_step`, `attempt_id`, on `attempt`: `orphan_after` and optional `deadline`, and on `done`: `basis` and `evidence_ref`, required with basis `evidence` and optional otherwise (Section 10.2) | App with `claims.write` |
| `record.put` | `key`, `collection`, `read_scope`, `write_scopes`, `expected_version` (the version read, or 0 to create, Section 10.3), `value_sealed`, and `id_inputs` when, and only when, `expected_version` is 0 | App with a write scope |
| `allow.put`, `allow.delete` | `pubky` and `kind` (`contact` or `conversation`) (Section 7) | App with `lists.manage` for contacts; app with `conversation.add` for adding conversation entries, and `lists.manage` for removing them |
| `deny.put`, `deny.delete` | `pubky` | App with `lists.manage` |
| `invite_code.put` | `code_hash`, `expires_at`, `max_uses`, `context` (Section 7) | App with `conversation.add` |
| `invite_code.delete` | `code_hash` | App with `conversation.add` |
| `cursor.set` | `position`, as `<generation>:<seq>` (unsigned and not counted in `batch.count`, but one of the request's 8 entries; the request's signature covers it) | The app, for itself |
| `app.put` | The app's signed record (Section 4.2), with a later `updated_at` than the one the service holds unless it is that very record | The app, for itself |
| `receive_key.put` | The app's signed receive key record (Section 3.7) | The app, for itself |
| `key_bundle.put` | `target_app_id`, the signed key bundle, and `first_epoch` and `last_epoch`, the first and last data epoch it holds keys for, in the clear (Section 3.6); a bundle in parts takes one `key_bundle.put` per part | Signer |
| `cert.put` | Target `app_id` and the signed renewed certificate (Section 3.2) | Signer |

- **`generation`:** every operation names the generation it was written for. The service rejects an ordinary operation naming another generation: older operations reach a new service only as recovery evidence (Section 13.6), and apps sign queued operations again after a move.
- **`batch`:** a random ID and the number of signed operations in the batch, the same in each of them. The operations of one batch take consecutive `seq`s, and their chain envelopes carry the batch ID and count (Section 14.6), so every app can check from items and stubs that a batch is complete. A batch ID appears at most once within any 30 days of the chain. The service holds a batch's ID for 30 days, and after that while any of its chain stubs is kept (Section 6.3). It answers the ID with the original result while it keeps the batch's transition proofs, those 30 days, and with `409 conflict` after that. An app never sends a batch ID again after its immediate retries. A batch whose every operation changes nothing is a no-op and takes no `seq` (Section 6.3). An app that finds part of a batch, or a batch ID repeated within 30 days, treats it as a rollback (Section 10.1). It takes a new batch for a repeat when its ID is that of an earlier batch and `t_new - t_old < 30 days` (2,592,000,000 ms), both the service time of each batch's first stub, and forgets older ones on its own, whatever checkpoints it sees (Section 8.4). The service holds a batch's ID at least until 30 days after its first stub's service time and refuses the ID while it holds it, so an honest service never trips the check. Within that window an honest service holds every ID, so a repeat there is evidence of a replay or a rollback. Beyond it the app doesn't compare, so an ID an honest service has forgotten can never cause a false alarm. The 30 days are measured by the service's own stamps. An app refuses a stub stamped earlier than the one before it (Section 10.1), but nothing bounds the stamps by the app's clock. The window has a cost: a dishonest service that replays a batch older than 30 days isn't caught by its ID. One that stamps a stub ahead widens what the window lets through: a replay of any earlier batch, however recent, isn't caught by its ID either. The operations' expected steps and versions still refuse what a replayed batch already did. List operations carry neither, so a replayed list change looks like a new one; the service decides admission anyway (Section 7).
- **`id_inputs`:** the collection name and blinded natural key a record key is derived from (Section 14.3), without the policy hash, which the service computes from the operation's policy.
- **Conditions:** `record_version` (`key`, `generation`, `version`), `claim_step` (`claim_key`, `step`) and `server_time_in` (`start`, `end`, either may be null), each an object as in the example.
- **Signer operations** use `app_id: null` and the identity key.
- **Request:** `{ "ops": ["<signed operation>", ..., { "op": "cursor.set", "position": "3:1042" }] }`, 1 to 8 entries. A signed operation takes at most 512 KiB in its compact carrying form, without whitespace (`specs/v0.2/wire-format.md` Section 7.1), enough for a 256 KiB record value, so whatever a chain item or record holds fits one export chunk (Section 13.5); a larger one is `413 too_large`.
- **Order:** operations apply in order. Each operation's own `expected_step` or `expected_version` is checked against the state the earlier ones left, so one batch can write two entries for one claim. A batch writes each record at most once, since a record's next version is known only when the service gives it (Section 10.3); a batch that writes one record twice is refused (`400 bad_request`). Explicit `conditions` are checked against the state before the batch.
- **Atomicity:** all conditions and every operation's own checks pass, or nothing changes and the service answers `409 conflict` with the current values the caller may read.
- **Response:** `{ "proofs": ["<transition proof>", ...], "head": "<signed head>" }`, one proof per signed operation, in order.

### 14.6 Chain and transition proofs
- **Chain items:** every signed operation, every `identity.json` delivery and every service transition. Inbox entries and cursor moves are not chained.
- **Item hash:** `item_hash = BLAKE3(lp("paykit/v1/item", item type, item bytes))`. The item type is `op`, `identity` or `service`; the item bytes are the signed document bytes (Section 14.2).
- **Chain envelope** for each chain item, built by the service: `{ chain_version, generation, seq, prev_chain_hash, server_time, item_type, item_hash, batch_id, batch_count }`, with `chain_version` 1, where `prev_chain_hash` is the chain hash of the previous chain item, and the batch fields are those of the operation's batch, or absent for other items. It is sent and stored as exact bytes: `{ "envelope": "<base64url of the exact JSON bytes>", "chain_hash": "<base64url>" }`.
- **Chain hash:** `chain_hash = BLAKE3(lp("paykit/v1/chain", prev_chain_hash, chain envelope bytes))`, with 32 zero bytes before the first item of a chain. An export that starts from a checkpoint starts from the checkpoint head's chain hash instead (Section 8.4). A chain stub is the chain envelope plus its chain hash.
- **One chain per sequence:** a cooperative move continues the chain; a provider loss starts a new one (Section 8.4).
- **Later versions:** every chain envelope and signed head names its chain version. A later version, such as a Merkle log with consistency proofs (RFC 9162 style), would be added beside version 1: a service keeps serving version 1 stubs and heads by default, and messages, claims and records don't change. How an app asks for a later version is defined with that version. Apps that know only version 1 keep verifying as this section describes.
- **Transition proof:** a service-signed document `{ chain, object, step, version, state }`: the item's chain stub, the object it changed, the claim's step or the record's version where they apply, and the resulting state (`specs/v0.2/wire-format.md` Section 7.5 gives the exact fields).
- **Signed head:** `{ chain_version, generation, seq, chain_hash, sig }` of the newest chain item, `sig` being the service signature over `(identity, chain version, generation, seq, chain hash)` (`specs/v0.2/wire-format.md` Section 7.7).

redirect a payment, since destinations come only from messages the payee signed or its public endpoints (8.2); keep a record or Private Payment List it signed payable for long, since payers cap a record at its `updated_at` plus the identity's record age limit and a list at 30 days after its arrival (4.2, 5.4); | **Revoked or departed app** | Keep what it already read; with a key that once was the app's, reach another identity's switch that hasn't yet received the newer `identity.json`, and so learn that it corresponds with this identity, until its certificate expires (at most 2 years, usually 1) | Read new shared data after rotation; write to the switch; write its Homeserver record or `identity.json`, since its grant is revoked with it and no app grant covers `identity.json` (3.5); be approved or listed again (13.2); learn from a switch holding the newer `identity.json` whether it corresponds with this identity, since it is answered like a stranger (6.1) | 3.2, 3.5, 4.2, 6.1, 13.2, 13.3 |
| **Signer compromise** | Everything for the identity, including all its sealed data, past and future, and the naming key, which `paykit_root` gives (3.1, 3.6) | - | Out of scope: identity-level recovery |

- **Limits of the switch's copy:** a payer finds the payee's switch through the Homeserver's document, possibly an old one. After a cooperative move a stale copy names the old switch, which, frozen, answers with its last document and the freeze naming the new one, so the payer follows it to the newer document (Sections 4.3 and 13.5); it does so for the identity's record age limit, after which no record from before the move is payable. This doesn't help after a provider loss, where the old switch is gone or hostile. One that is gone doesn't answer, so the payer pays only on the user's explicit confirmation, and never automatically. A hostile one can answer with its last document and no freeze, which the payer can't tell from a current answer, so the old document's own limits apply (the record age limit, Section 4.2). Otherwise a switch that doesn't answer, or a malicious one, can only fail to help: it can't serve a newer document than the signer made, nor lower the one the payer uses. Someone flooding the read can't switch the lookup off silently either: reads are limited per network source, answers may be cached, and a payment the switch couldn't confirm needs the user (Section 4.3). Anchoring `identity.json` in PKARR would close the provider-loss case too, at the cost of PKARR space and of coupling every `identity.json` update to it; v0.2 doesn't anchor it (Section 22, decision 23).
- **Residual risk, removed apps at other switches:** a switch of another identity answers an app it holds as removed like a stranger (Section 6.1), but it learns of the removal only when an own app or the removed app itself delivers the newer `identity.json`. Until then it treats the app as current: the app can write to it, which recipient apps reject, and so learn that the identity there corresponds with its own. Where that identity allows connect requests, a removed app can also deliver an older document that still lists it, and so tell whether the switch already holds a newer one. Both end when the app's certificate expires, at most 2 years after it was issued and 1 year by default, since every reader refuses an expired certificate (Section 3.2).

The guarantees these protections provide are stated once, in Section 17.

## 16. Privacy

| Party | Learns |
|---|---|
| Anyone (including counterparties) | From the Homeserver: `identity.json`, which lists every current app by ID and certificate hash, and the records (signing key, accepted kinds, capabilities, public endpoints) of apps with public endpoints |
| Admitted senders | The directory, including receive key records, whose `n` shows roughly how often each app reads its inbox. Rotation follows reads (Section 3.7), so each new registration, seen in the directory, as a `stale_key` answer or as a new `directory_version`, tells them that the app read its inbox and opened something since its last rotation: roughly when each app is online, and that a message reached it. From a `429 quota_exceeded` for the inbox quota, that the recipient's apps haven't read for a while |
| Recipient's switch | Sender identity, time, size bucket, the `notify` bit, target apps, and from them which class of kind a message is, since apps of different scopes receive different kinds (Section 3.4); each sending app's full certificate (its scopes, switch permissions, `issued_at` and bundle key), contacts, denied IDs and conversation entries (so whom the identity writes to), who asked to connect, the `context` of every invite code in the clear (Section 7), claim states and times, shared record size buckets (values are padded, Section 14.4), versions and collections, the scopes each policy names, app last-seen times and when each app rotates its receive key; each app's push relay URL, which names its vendor; the network address and timing of every request; and, when it also serves the counterparty, both sides of the conversation. Not the counterparty of records and claims from their keys: natural keys and obligation inputs are blinded with the naming key (Section 14.3). That protects stored state, exports and dumps taken once the related entries are gone, not against a live operator: the batch that writes a message's record also moves the cursor past its entry, whose sender the operator sees, an attempt's condition names the request record's key, and an append followed soon after by an `attempt` links the two, so a live operator can rebuild whom the identity pays, and when. The exception is collusion with anyone who once held the naming key, which never rotates: together they can test guesses of counterparties against blinded keys whose inputs are public, such as `payment_lists` record keys, while those records exist. The obligation of a payment without a request names no payee, so it reveals none. Never the content of envelopes or sealed values |
| A payee's switch, from payers | An anonymous lookup of the payee's `identity.json` (Section 4.3) shortly before a payer without a fresh copy pays a public endpoint: the reader's network address and the time, so that someone is about to pay the identity, but not who. After a cooperative move the old service, frozen, sees the lookups of payers holding the old document for as long as it answers them (Section 13.5). A cache in front of the service sees what the service would |
| Own apps | When items they can't read were written, from chain stubs and gaps in `seq` |
| A revoked or departed app | Everything it read before leaving; nothing written after the next key rotation. Not which identities correspond with its own, from a switch holding the newer `identity.json`, which answers it like a stranger (Section 6.1); one that hasn't received it still serves it until its certificate expires |
| Counterparty | Which of your apps sent each message, as a signed copy it can show others, and the label of a request a labelled app sent (Section 3.3). Not your identity's activity: responses to it carry no `seq` or head |
| Push relay | That a notification is due for a handle, and when, and which handles share a push key, so which devices belong to one app. Push keys appear in no public document, but the webhook's source address and timing can still link a handle to its identity, without the switch operator's help (Section 9). Together with the switch operator, which sender's messages reached which device |
| Apple or Google | That a device received a push |
| The device's notification store | The text of every message the push extension showed, kept by the operating system outside the app's keys until the user clears it (Section 9) |
| Homeserver | Published records, and the encrypted backups of apps that keep them there; from each app's grant, the Homeserver paths it covers (Section 3.5) |

- **Forward secrecy by rotation.** An app deletes a receive key once it has read everything sealed to it, after its next rotation (Section 3.7). Rotation follows reads: about once a day by default, as often as once an hour if the app chooses, and not at all while the app opens nothing new, so there is no fixed bound for an app that doesn't read. An envelope someone captured (operator logs, a breach) stays readable through a leak of the app's state only until that deletion: about a day for an app that reads daily with the default interval, and longer for messages that sit unread. Someone who steals only a receive key reads new incoming messages only until the next rotation, with fresh random keys as recommended. A full copy of an app's state, or a backup, also holds its signing key, which can register a receive key of its own, so it reads new incoming messages until the app is revoked, whatever the rotation; the app sees that registration and alerts the user (Section 3.7). A malicious operator holding a stolen receive key can also keep senders that haven't seen a newer record on the old key (Section 15). This protects captured envelopes, not stored history: senders keep what they sent for at least 30 days and re-send it on request, activity records keep the messages they reflect, and backups keep both, so those copies are protected only by the app's own state and keys. Whoever holds an app's signing key, or a stolen current receive key together with the operator, can pull up to 30 days of what counterparties sent through `resend_request`, sealed to keys it holds, within the senders' limits (Section 12). Apps keep the scope keys of every data epoch, and a newly approved app receives them all (Section 3.6), so stored payment history remains readable to every app holding its scope keys, a seized one included, however old that history is. A copy of a current app's state goes on reading shared data written later too, until that app is revoked (Section 3.6). A malicious operator that holds any receive key of an app can open what was sealed to it and seal it again to the app's current key, so forward secrecy doesn't hold against it for those messages (Section 15). A message the push extension showed also stays in the operating system's notification store, outside this deletion (Section 9).
- **Erasure.** The signer can erase the account at a service. The service then deletes everything it holds for the identity, and its operator lets that data age out of its backups (Sections 6.5 and 13.7). An erasure doesn't reach what others keep: counterparties' accounts and the messages they received, senders' copies of what they sent, and the identity's own apps and their backups.

## 17. Guarantees
- **No duplicate payment for one obligation**, under these conditions:
  - *Holds for:* the same obligation, with compliant apps and a consistent switch: one that follows Section 6.5, so that every item it acknowledged is durable and it never serves a state behind what it signed.
  - *Does not cover:*
    - a user who confirms an outcome (`reconcile`, `unknown` or `failed`), or a manual payment marked "may already be paid";
    - a malicious or non-compliant switch, including one that shows different apps different histories after any shared prefix, or loses a write it acknowledged and serves on (Sections 6.5 and 10.1); on such a split a recurring obligation can be paid once per branch in every Billing Period;
    - a payer that carries out an authorized attempt more than once, for example on two devices of one app (rail-level idempotency is the wallet's responsibility);
    - a payment method that reports a final failure and then completes the payment anyway, or whose declared idempotency or history (Section 10.4) doesn't hold;
    - a payee that issues two obligations for one purpose, or misdates a re-sent request during provider loss;
    - an old provider that keeps authorizing attempts after a provider loss (Section 13.6, residual risk).
- **Confidentiality:** message content and sealed shared data are readable only by own apps holding the matching keys: recipient apps for messages, apps with the read scope for shared data. Every recipient app of one envelope reads the same plaintext (Section 5.1); two envelopes under one `msg_id` may carry different plaintexts, which an app notices only if it sees both (Section 12).
- **Forward secrecy:** a message can't be decrypted from its recipient app's state once the app has deleted the receive key it was sealed to (deleting in the sense of Section 3.1: from every copy the app keeps), which happens at the first feed read after the app's next rotation; with fresh random receive keys, a leaked receive key stops reading new messages at the app's next rotation. A leaked signing key, which a full state copy or backup contains, can register its own receive keys and read new messages until the app is revoked (Section 3.7). Rotation follows reads, so an app that opens nothing new keeps its current key (Section 3.7). This covers captured envelopes; plaintext kept by senders, and re-sent by them on request (Section 12), in shared records and in backups is outside it, and shared records stay readable to every app holding their scope keys (Section 16). It doesn't hold against an operator that holds a receive key of the app, stolen or leaked: the operator can open what was sealed to that key and seal it again to the app's current key, which recipients don't notice, since the message signature covers neither the kid nor the envelope header. Nor does it cover text the push extension showed, which the operating system keeps in its notification store (Section 9).
- **Integrity:** every message, operation and document is signed by its writer, and apps check the writer, its standing and the item's place in the chain for every operation they read (Section 10.3). Apps detect conflicting history while they can verify continuity: the chain and batch IDs expose a rollback of history an app has seen. If a restore or long absence predates retained history, the app enters explicit recovery; reconciliation does not prove the missing chain's continuity (Section 8.4). An app that may write a collection can still replace or omit records in it: signatures inside a record prove who sent each message, not that the record is complete. It can't change where a payment goes, because apps verify every stored message on use and take destinations only from the payee (Section 8.2).
- **Isolation:** an app acts and reads only within its scopes, and can be revoked on its own. Only an app that signed its own executor grant for that counterparty pays automatically under an Allowance, and an end it has seen is final. Departed apps lose access at once through the service, and cryptographically at the next key rotation.
- **Idempotent processing:** every message's lasting effect is applied once per identity, through the messages and `msg_id`s that shared records keep and each app's processed pairs; deduplication and the conflict check hold per reading app (Section 12). Backup rollback and external effects are handled by reconcile mode, claims and the journal.
- **Allowance executors** are responsible for their Allowances' limits.
- **Availability** depends on the switch and, for paying, on the payer's Homeserver, from which `identity.json` must be revalidated (Section 4.3). Delivery ends at acceptance. The service keeps entries for an offline app within its retention rules (Section 6.3); entries an app missed while marked lagging, and those a lost service held that no app had read yet, come back only through re-sends on request, best effort (Sections 8.2 and 13.6). Moving to another provider and a provider loss (Sections 13.5 and 13.6) bound the damage. The switch is one logical, replaceable coordinator for each identity, trusted for coordination: ordering, time, availability and delivery, not for content. Operators are expected to run it on synchronous replicas, so a failure of one machine loses nothing; what is forbidden is losing a write it acknowledged and serving on, which makes it non-compliant (Section 6.5): the account must move to a new generation instead.

## 18. Performance targets

| Action | Target |
|---|---|
| Send any message | 1 round trip: the append to the recipient's inbox and the shared record write at the sender's own switch, in parallel; 0.3-0.7 s. A first message to a new counterparty adds one round for the directory read, made in parallel with delivering the sender's `identity.json` and writing its conversation entry |
| Receive a message | Delivered on the open long-poll; the shared record batch makes it durable in 1 round trip |
| Recipient sees it | Under 1 s in the foreground; 1-5 s through push |
| Pay a request | Critical path before money moves: 1 claim write (~0.2-0.3 s), with `identity.json` revalidated in parallel. The acceptance, `done`, the record update and the proof follow in the background, plus wallet time |
| Save a contact | 1 operation: allowlist entry |
| Directory lookup | 1 request when a counterparty is new; afterwards cached while the recipient's `identity.json` names the same switch and generation, and refreshed in the background when an append shows a newer `directory_version` |
| Receive key rotation | 1 request, about once per active day per app by default, after a feed read; never on a user-facing step. A sender whose cached directory predates the rotation pays one extra round (`stale_key`), unless it refreshed the directory in the background (Section 8.1) |
| Add or revoke an app | One operation each for the service, `identity.json` and key bundles, whatever the contact count. A revocation also has own apps deliver the new `identity.json`, in the background, to the switches they wrote to in the last 30 days (Section 13.2) |
| New app catch-up | 1 list call per collection, then the feed |
| Idle | Foreground: one long-poll every ~25 s. Background: none (push) |

**Homeserver calls outside the critical path,** allowed by the design rule: revalidating the app's own `identity.json` in parallel with an `attempt` (Section 4.3); the event stream subscription that watches its own and its counterparties' `identity.json`, held while the app runs in the foreground; and fetching a counterparty's `identity.json` in the background when an event names it, or when a copy it doesn't watch is more than 10 minutes old, to route messages and to check the apps it hears from and pays to.

**Paying a public endpoint:** the lookup of the payee's `identity.json` at its switch runs in parallel with the Homeserver record read that follows the Homeserver's `identity.json`, and the payer waits for it at most a short grace after that read, so it adds no request in sequence. If it hasn't answered when money is about to move, for example because a lost request is noticed only after the client's timeout, the payment never waits longer: it needs the user's confirmation and is flagged (Section 4.3). M01 checks this on every sample: either the lookup answered before money moved or the payment was flagged, and with and without the lookup the requests in sequence before money moves are the same.

Targets are measured by counting requests per action, as the prototype does (Section 23). Latency is judged on a stated network profile for the user's own actions: sending a request, receiving one, tapping Pay until money can move, a first contact and a cold start. Background processing, such as the payer's follow-ups after paying, the payee's handling of an acceptance and a proof, and idle checks, and delivery on the open long-poll are reported separately.

## 20. Left to apps or later
- **Up to each app:**
  - local storage (the protocol is storage-agnostic), and its backups: whether to keep them, where, and the backup key;
  - offline endpoint issuing;
  - keeping its devices consistent: cursor, receive keys, payment journal and local state.
- **Decided later:**
  - detecting a split view, a service that shows different own apps different histories after any shared prefix, for example through witness files on the Homeserver or own apps exchanging signed heads: two service-signed heads at one `seq` with different hashes prove it. Witness files are defeated when one operator runs both;
  - read status for messages;
  - a state commitment in signed heads, covering claims, tombstones and record versions, so that an import, and every read by an app, can be checked for completeness against the chain (Section 13.5, residual risk);
  - a Merkle log as chain version 2, so a phone on a busy identity verifies a new head with a few dozen hashes instead of a stub for every operation since its last head. Version 1 works without it; the cost of waiting is that download, which matters only for very busy identities;
  - browser and WASM support;
  - strangers messaging without an invite (open mode);
  - filters for connect requests, such as identities on trusted Homeservers or in a social graph; later options, not in this version, are a proof of work or a payment stamp with each request, and a social graph of trust drawn from public data: who else approved the identity, and which Homeserver it uses;
  - accepting attestations in Pubky grants as app certificates;
  - a private identity file, written by the signer and encrypted for the identity, with opt-in details about each app for the user's own convenience, such as a device name and when and where it was added, to help with reinstalls and managing sessions;
  - Allowances that pay requests priced in another asset, for example a subscription priced in usd paid from a btc Allowance. For v0.2 an Allowance pays only requests in its own asset, as in v0.1 (Section 11.3); a payee that wants automatic payment in another asset bills in that asset at its own rate. A later term can widen this without breaking older executors, which keep refusing.
- **Migration from v0.1,** planned in full after the freeze (Section 23). v0.1 and v0.2 apps can't pay each other, so the payer and the payee both update to v0.2. The plan carries across:
  - each identity's Pubky grants, revoked or narrowed before its first v0.2 `identity.json` (Section 3.5);
  - public Payment Endpoints, republished in each app's v0.2 record (Section 4.2);
  - open Allowances, with their ledgers of what each has paid, so that no limit starts again from zero;
  - recurring requests in the middle of a Billing Period, so that the period is paid once, neither twice nor never;
  - receipts and the rest of the payment history;
  - sellers on paykit-server: each seller approves it as a v0.2 app with the `request` scope, and its open requests carry over.

## 21. What the Pubky stack needs
- **Pubky Switch:** open-source, run as a separate service, self-hostable, documented API.
- **A reference push relay.**
- **Signer support in Ring and Bitkit:**
  - app requests signed by the app and bound to the auth request, checked as Section 3.2 says, and certificates with scopes, switch permissions, bundle keys and a lifetime of at most 2 years, renewed before they expire, delivered in an approval of public material only as the grant approval's companion claim;
  - `identity.json` with versions, generations and the app list, delivered to the switch before it is published (Section 4.3);
  - Shared Data Keys and the naming key, derived from a Paykit root as in Section 3.6 and delivered as a key bundle sealed to the app's bundle key, in the approval and after rotation on revoke and leave;
  - the generation, version and hash of the newest `identity.json` a service accepted from it, kept so it never adopts a lower copy, and the App IDs it revoked, kept for good;
  - listing apps by last-seen time;
  - enrollment, revoke, freeze, recovery and erasure (Section 13.7);
  - labelled selling scopes, with their label keys in key bundles (Sections 3.3 and 3.6);
  - the hand-over to another signer, sending and receiving (Section 13.8).
- **Pubky grants** covering exactly each app's paths and never `identity.json`, issued and revoked by the signer, and the v0.1 grants revoked or narrowed before the first v0.2 `identity.json` (Section 3.5).
- **Pubky client:** HTTP/2 and a persistent pkarr cache.
- **Homeserver event stream keep-alives,** so that an open subscription proves it is live. That would let the stream replace the check before each attempt (Section 4.3).

## 22. Open questions for the team
Questions 1 to 12 are deliberate trade-offs. Each has a default, which this spec describes and the prototype implements and tests. Every question is now decided: 1 to 9, 11 and 12 as their defaults, with the metadata of 3 and 6 disclosed to users and push optional for each app, and question 10 is closed: shared contact details aren't part of Paykit. The package review asks the team to accept each one explicitly, as a product choice; until then the review records list them as accepted risks. The team's decision list explains each one. Allowances across assets are deferred (Section 20).

1. **No unsolicited first contact.** A sender needs to be a saved contact, invited, or answering someone who wrote to it first; a stranger can at most ask to connect, where the user allows it (Section 7). Decided: kept for v0.2.
2. **Forward secrecy by rotation, not a ratchet.** Receive keys are replaced by fresh random keys after reads, about once a day by default and configurable down to once an hour (Section 3.7). An app that opens nothing new doesn't rotate, so there is no hard one-day bound for an app that doesn't read. Receive-key deletion protects older captured envelopes. Stored payment history remains readable to apps holding its scope keys, so a seized device exposes the history its scopes cover, as well as its unread messages and captured envelopes sealed to keys it hasn't deleted yet (Section 16). A stolen receive key reads new incoming messages until the next rotation. A copied signing key, which a full state copy or backup contains, can register receive keys and read them until the app is revoked, which the app detects and answers by leaving (Section 3.7); rotation alone doesn't end that, and on iOS the push extension holds that key in storage readable after the first unlock, so a forensic extraction gets it and can send forged messages as the app until it is revoked (Section 9). A copy of a current app's state also reads its scopes' shared data, past and future, until the app is revoked: later key bundles are sealed to the app's static bundle key, kept by decision. An operator holding any receive key of an app can re-seal what was sealed to it to the app's current key, unnoticed (Section 15). Admitted senders see roughly how often each app reads its inbox, and when it rotates, so roughly when it is online (Section 16). A Double Ratchet would give per-message forward secrecy and heal within one round trip, at the cost of per-pair state and message loss on restore (the message protection study, Section 23). Decided: rotation after reads.
3. **Server-visible metadata.** The switch sees target apps, and from them the class of each message's kind, policy scope names, record size buckets (values are padded, Section 14.4), contact Pubky IDs, whom the identity writes to (conversation entries), invite code contexts, each app's push relay URL, network addresses and timing (Section 16). Blinding hides counterparties in stored state and exports, not from a live operator, which links records and claims to senders through batches and timing. Decided: acceptable, disclosed to users.
4. **Rollback detection, no fork detection.** Apps detect conflicting history while they can verify continuity (Section 10.1). If a restore or long absence predates retained history, they enter explicit recovery; reconciliation does not prove the missing chain's continuity (Section 8.4). Apps don't detect a split view: a service that shows different apps different histories after any shared prefix, from the start or later, or one that loses an acknowledged write and serves on, which is non-compliant (Section 6.5). On a split, each branch can pay an obligation once: a one-time request twice, a recurring request once per branch in every Billing Period, and an Allowance up to its limits on each branch (Section 10.1). Witness files on the Homeserver, or own apps comparing signed heads, could detect it, but witness files not when one operator runs both. Decided: accepted for v0.2. The switch is trusted for coordination, including ordering (Section 15), and detecting a split view stays later work (Section 20).
5. **Delivery ends at acceptance.** There are no acknowledgements: a message is done when the recipient's inbox accepts it, and the payment flow's own replies show progress. Offline delivery is retained within the service's retention rules (Section 6.3). Entries an app missed while marked lagging, and messages a lost provider held, are recovered only by re-sends on request, which are best effort (Sections 8.2 and 13.6). Decided: enough, without read status.
6. **Push metadata.** A switch operator and a relay operator together can link senders to devices, and a relay alone may link a handle to an identity from the webhook's source and timing (Sections 9 and 16). Decided: acceptable, disclosed to users; push stays optional for each app.
7. **Limits.** 64 KiB messages, 16 KiB for recorded kinds, 256 KiB shared records, about 1,500 live ledger entries per Allowance (a 256 KiB ledger record), 32 apps per identity by default. Decided: kept.
8. **Signer availability.** Rotation after a leave waits until the signer is online; until then, only the service blocks the departed app. Decided: acceptable.
9. **Signed messages.** Every message is signed by its sender app, so a counterparty can prove to anyone what you sent (Section 16). Signing only requests, proofs and receipts would make the rest deniable, but someone with an app's stolen keys could then forge those messages to it from its contacts. Should any kinds be deniable? Decided: every message stays signed.
10. **Shared contact details.** Closed: not part of Paykit. Contacts in Paykit are only the switch's allowlist and deny list (Section 8.2). Names, pictures and notes that all of a person's apps share belong in an address book for every Pubky app, not in Paykit's records.
11. **Who may end an Allowance.** Any own app with `allowance` may end one, and an `executor_notice` makes sure the executor stops even if it was offline and the Allowance record was rewritten afterwards (Section 11.3). This lets the user cancel from any device, including when the executor's device is lost or off. The alternative is that only the executor may end it, which removes the notice but means cancelling elsewhere requires revoking the executor or handing it off first. Decided: any own app with `allowance` may end it.
12. **Paying while the Homeserver is unreachable.** Before each attempt, an app revalidates its own `identity.json` unless it did so in the last 60 s (Section 4.3), so payments stop while the identity's Homeserver can't be reached. This keeps an app from paying through a switch the identity has moved away from, which matters most right after a provider change (Section 13.6). The alternative is a grace period on a cached copy, which keeps payments working through a Homeserver outage but widens that window. Decided: payments stop.

**Further team decisions.** The reviews of 2 and 3 November raised these. They aren't protocol fixes, and they are left to the team, as the review records note. They are numbered as in the team's decision list, after its closed decisions 13 and 14; that list gives each in full. All are decided or closed. Two of the decisions add protocol: the labelled selling scopes of 22 (Sections 3.3 to 3.6, 8.3 and 11.1) and the hand-over of 24 (Section 13.8).

15. **Who runs the default switch.** Decided: Synonym runs it, for users who don't choose one; any user can still choose another operator or host their own. Its availability target, cost per identity and runbook (Section 6.5) are set before launch. Recommended: a separate service with its own database, never inside paykit-server's process. A user whose Homeserver Synonym also runs has one operator for both, so witness files wouldn't detect a split view for that user (Section 20).
16. **Personal data: GDPR, retention and erasure.** Closed: the spec gives account erasure (Section 13.7). The signer erases the identity's account at a service, which deletes everything it holds for the identity, so what Section 6.3 keeps for good is kept for the account's life, and a user can delete their account. The rest, such as a privacy policy, records of processing and a data protection impact assessment, is each operator's own compliance work, not a protocol decision.
17. **Background payment on iOS.** Closed: whether an app pays while it is closed is each app's choice, within the key rules of Section 9, which describes the default in which the push extension only shows messages.
18. **Per-device or seed-derived app keys** (Section 3.1). Random keys per device keep devices apart, and every restore needs an approval; seed-derived keys restore without one, but make the devices one app, unprotected from each other. Decided: seed-derived keys. Keeping the devices of one app from carrying out one attempt twice is the wallet's job (Section 17).
19. **The signer at launch** (Section 21). Decided: Bitkit is the signer for now; whether Ring becomes one too is decided later. One Rust signer core serves both Bitkit platforms, and Ring if it does.
20. **The SDK timeline.** Decided: the v0.2 SDK's surface is drafted and Bitkit's calls mapped onto it before the freeze, then a phased plan with owners, dates and the kill criteria of Section 23.
21. **The name of the service.** Decided: it is the Pubky Switch, a name that isn't Paykit-specific, since the switch isn't payment-specific. Its mailbox part, where senders' messages land and apps read them, keeps the name "inbox", as in `POST /v1/{id}/inbox` and "send to their inbox". Pubky already has the `pubky/inbox` ping service and the relay inbox of Pubky auth. For now the switch doesn't merge with `pubky/inbox`, which sends wake-up pings and leaves message bodies on the sender's Homeserver.
22. **How finely history is shared.** A scope's keys open all of that scope's records, so every app holding a scope sees its whole history: a hosted app holding `request`, such as paykit-server, reads all of the identity's payee history, including requests the person's own wallets sent (Section 8.2). Should history be shared by scope, or more finely, for example per app or per label? Options: keep it by scope; finer sharing, such as a labelled request scope with its own keys, so that a hosted app reads only what is written under its label. Decided: labelled selling scopes, so that a hosted app holding a label reads only that label's history and the identity's own wallets, holding `request`, still read all of it. They change the scope and kind tables (Sections 3.3 and 3.4), and Sections 3.3 to 3.6, 8.3 and 11.1 specify them: payers see the label, plain `request` covers every label, and a certificate holds at most 8 labels.
23. **Anchoring `identity.json` in PKARR** (Sections 4.3 and 15). Decided: no anchor for v0.2. The switch's copy bounds what a stale Homeserver copy can do, and after a cooperative move the old switch points to the new one, but not after a provider loss. An anchor would cost PKARR space and couple every update to it. If one is wanted later, the smallest is the generation and switch origin.
24. **Who manages the identity when a user starts with a third-party app.** Decided: the signer core ships in the SDK, so any app can be its identity's signer; handing the identity to a dedicated signer such as Bitkit or Ring is recommended, not required. An identity has one signer at a time: a hand-over moves the identity key and the signer's records (the newest `identity.json` it accepted, the App IDs it revoked, the certificates that document references) to the new signer, and the old one deletes the key and becomes an ordinary app. Keeping the key safe and backed up is the signing app's job. Section 13.8 specifies the hand-over.

The prototype's results hold the full measurements, and the review records hold the status of every review finding.

**What the prototype covers**
- The reference prototype implements this spec on a local Pubky testnet: the switch with its feed and chain, shared records, conditions, batches, conversation entries, app and receive key registration, key bundles and `identity.json` delivery; apps with shared activity records, and Allowances and recurring requests built only on claims and shared records; moving to another provider and provider loss; an in-process push relay; and a full payment over HTTP against a local Pubky testnet Homeserver.

**Results**

The counts are the same under every network profile, and they are what Section 18's targets count.
- **Timings on localhost (measured):** every action's warm p95 at most 25 ms.
- **Timings on a simulated network (with retries):** in release, three seeds per profile (2026-11-04), given as the median of the three runs' p95 with the highest in brackets: tap Pay 29 ms (30 ms) on home Wi-Fi (20 ms round trip, no loss) and 106 ms (107 ms) on mobile 4G (80 ms, 1% loss); 331 ms on poor mobile (250 ms, 3% loss), from one earlier run. It is reported apart from the actions above.

**Kill criteria**
- **Fail:**
  - warm p95 latency above 2 s for a user's own actions, on a mobile 4G profile (80 ms round trip, 1% loss);
  - any duplicate payment outside the exclusions of Section 17;
  - any stuck state that isn't shown to the user with a way to resolve it;
  - iOS push p95 above 10 s.
- **Pass:** a paused "may be paid" state that is shown, with a way to resolve it.
- **Network profile:** latency criteria are judged on a stated network profile. The user's own actions are first contact, send, receive, tap Pay and a cold start (Section 18). Background processing, such as the steps after paying and a payee handling an acceptance and a proof, is reported separately, and so is delivery to an open long-poll, which Section 18's "Recipient sees it" target covers. Under the prototype's poor-mobile profile the user's own actions stayed under 1.5 s at p95 except a cold start at 2.3 s, and the payee's background processing exceeded 2 s; the criterion is judged on mobile 4G.
- **Results:** on the simulated mobile 4G profile the latency criterion passes in every run, with the user's own actions under 1.5 s at p95 (first contact the slowest, at 1.40 s at most over three seeds); the duplicate payment and stuck state criteria pass. These hold for the prototype, within the limits above. iOS push p95 isn't measured yet; it needs a real phone (Before freeze).

**Production plan.** Work for production, not for the prototype, from the crypto audit and the gaps review; the review records name the findings behind each item. Each item needs an owner before the SDK and the switch ship.
- **Secrets:** secret types that aren't `Copy`, zeroize on drop, print nothing in `Debug` (already so in the prototype) and derive no `Serialize`; keys in platform keystores (Section 3.1); deletion by crypto-shredding; and a test that a deleted key's bytes are gone from every file the app persists.
- **Supply chain:** a required cargo-deny job (advisories with expiring ignores, bans on duplicate crypto crates, sources, licenses) with scheduled runs and a Dependabot entry for cargo; the TLS crates kept current; the Android build's linker settings reviewed; one version of each direct crypto crate, one entry point for randomness and a getrandom backend per target; no patched or vendored pubky in any shipped crate, with a `cargo package` check in CI and a scoped conditional-write API asked of Pubky upstream.
- **A client and server crate split:** the mobile bindings must not link a web server, and the client gets TLS through an explicit feature, not through feature unification with pubky's dependencies.
- **A formal model:** state the at-most-once invariant and its assumptions in Section 17 (deadlines derived exactly, a restored journal never read as "not started", transitions durable before they are signed, service time that never goes back, `failed` only on authoritative evidence); model claims, the journal and recovery in Quint or TLA+; and export the model's traces as conformance tests.
- **Conformance:** freeze the vectors, so that a regenerated diff counts as a wire change; add boundary vectors for rules pinned only by text; build a second implementation on a crypto stack other than Rust's; run Wycheproof and the Ed25519 speccheck cases; fuzz the prototype against the clean-room implementation; and build a rejection corpus by mutating valid vectors, first the security bindings, the UUID form and the integer bound, then the rest, negative `stale_key` cases included. Releases are gated on it.
- **Fail-closed code:** no `unwrap`, `expect`, indexing or unchecked arithmetic in the protocol crates, enforced by Clippy, and fuzz targets for the parsers, times and Billing Period arithmetic.
- **Faults against real parts:** crash and failover tests against real storage, an approval end to end through Pubky auth, per-app grants enforced by a testnet Homeserver, and an on-device test of the iOS notification extension, with its choice of entry to show, a feed view of entries only and a fixed generic relay payload.
- **Bindings:** only the Rust core parses and verifies signed bodies; Swift and Kotlin never parse them again. CI builds every binding (`build.sh all`) and checks the bindings' diff.
- **The external crypto audit's scope:** the subset of hpke 0.14 that Paykit uses, strict Ed25519 verification with ed25519-dalek 3 and curve25519-dalek 5, and the approval's companion-claim channel.
- **CI:** the reference prototype's test job runs a PostgreSQL 16 service and sets `PAYKIT_E2E_REQUIRED=1` (2026-11-03), so the end-to-end tests run there and fail rather than skip if the database is missing.
