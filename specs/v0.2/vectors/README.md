# Paykit v0.2 test vectors

Test vectors for Paykit's own wire format in `specs/v0.2/wire-format.md`: its amounts, derivations, the Paykit
member of app records, the executor grant, messages and shared record values. Every file is computed from fixed keys and fixed
randomness, by the reference prototype's own code, shared separately, or, for the cases "How the files were generated" lists, by
`paykit-lib`, so any implementation can check them byte for byte.

**This set depends on [the Switch's set](https://github.com/pubky/pubky-switch/tree/1259961f96a6284f3cc7028bbe848c7795bf0f6d/spec/vectors), at pubky-switch commit `1259961f96a6284f3cc7028bbe848c7795bf0f6d`, the commit Paykit's spec builds on**: its fixed keys (`keys.json`), the certificates and documents of its `documents.json`, its envelopes and its encodings. The seeds, encodings and times follow that set's conventions.

## Conventions
- **Seeds, encodings and times** are those of the Switch set's README.
- **Sections.** Descriptions and the table above cite sections of `specs/v0.2/wire-format.md` as "wire N"; "spec N" is the Paykit v0.2 spec, and "Switch wire N" and "Switch spec N" are the Pubky Switch's documents.
- **Allowance usage.** An entry counts by its own `outcome`, else by the state of its attempt's claim listed in `claims` (`open` and `unknown` reserve, `done` spends, `failed` releases, missing spends). `refused_by` is the limit that refuses a candidate.
- **Permissions** (Switch wire 3.1, wire 3.1). The switch checks a certificate's `permissions` for form and enforces them as signed; Paykit's verifiers check them against Paykit's scopes: every permission those need, and, in a certificate without another protocol's scope, no other.
- **Rejections.** Where a file lists inputs to refuse (`documents.json` `certificate_rejections`, `labelled_scope_rejections` and the `refused` cases of `app_records` and `multi_protocol_certificates`, `sealed.json` `binding_rejections` and the rejections of `labelled`, `messages.json` `label_rejections` and the `refused` cases of `multi_protocol_senders`, `cancellation_roles`, `conversion_terms` and `proof_members`, the `refused` cases of `sealed.json` `activity_records` and `allowance_records`, and of `allowance_usage.json` `period_limit_spellings` and `period_limit_members`), what is normative is that the input is refused. An `error` or `reason` text is the wording of the code that generated the case, the prototype's or, for the cases below, `paykit-lib`'s, quoted without the section number it starts with there, and only informative.

## How the files were generated
The reference prototype, shared separately, generated every file but the cases listed below, which it hasn't run, and its tests recompute every vector it generated and fail on any difference. While computing, the builder also checks each vector with the implementation: every signature verifies, every envelope opens for each recipient, every message passes the recipient checks and decodes by kind, the chain verifies, and the rejection cases fail.

`paykit-lib`, the v0.2 Paykit Library, added these cases, each built from the Switch set's fixed keys, certificates and shop app record and this set's messages, signed again with Ed25519, which needs no randomness:
- `documents.json` `multi_protocol_certificates`, whole;
- `documents.json` `app_records`, the last 4 of `refused` (the cases of wire 1.4);
- `messages.json` `multi_protocol_senders`, whole;
- `messages.json` `cancellation_roles`, `conversion_terms` and `proof_members`, whole;
- `sealed.json` `activity_records`, `msg_ids_bounds` and `allowance_records`, whole;
- `allowance_usage.json` `period_limit_spellings` and `period_limit_members`, whole;
- the descriptions of those members, of `app_records`, and of the files `documents.json`, `messages.json`, `sealed.json` and `allowance_usage.json`.

Its vector tests build each of these cases again and compare it with the file, value for value, and check every case of `app_records`, `multi_protocol_certificates`, `multi_protocol_senders`, `cancellation_roles`, `conversion_terms`, `proof_members`, `activity_records`, `msg_ids_bounds`, `allowance_records`, `period_limit_spellings` and `period_limit_members` byte for byte and verdict for verdict: the bodies sign again to the signatures given, the switch takes each certificate and record, and Paykit's readers and verifiers take or refuse each as its list says. The generator lives in those tests, `paykit-lib`'s vector tests (`paykit-lib/tests/vectors/`), which run with `pubky-switch-core`'s test-only `test-vectors` feature, and no production build has it. Adding the cases changed no other value of those files. The same tests rebuild and check every other vector of this set too, so every vector here is checked by public code; neither the prototype nor the independent implementation has run the cases above.

After an intended wire change, the vectors are generated again, by the prototype or, for the cases above, by `paykit-lib`'s vector tests with `PAYKIT_WRITE_VECTORS` set, and the diff is reviewed.

The JSON examples in `specs/v0.2/wire-format.md` are taken from these files and the Switch set's; update them with the vectors.
