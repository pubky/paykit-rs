# Paykit v0.2 implementation evidence

This table follows the [wallet branch](https://github.com/pubky/paykit-rs/tree/v0.2). The links identify the [wallet revision](https://github.com/pubky/paykit-rs/tree/3fc11db321ef094d008a6ea134e19d343a21e721) used for this copy unless a row links a later revision. Update the affected row with its implementation. The [conformance cases](conformance.md) state the required outcomes, including cases for which wallet evidence is still missing.

| Rule | Library check | Stored examples | Wallet checks and limits |
|---|---|---|---|
| App records and public destinations (§§4, 7.2, 8.4) | [App-record reader](https://github.com/pubky/paykit-rs/blob/3fc11db321ef094d008a6ea134e19d343a21e721/paykit-lib/src/app_record.rs) | [`app_records`](vectors/documents.json) | [Expiry, cutoff and renewal](https://github.com/pubky/paykit-rs/blob/3fc11db321ef094d008a6ea134e19d343a21e721/paykit-sdk/tests/flows/own_record.rs) and [destination reads](https://github.com/pubky/paykit-rs/blob/3fc11db321ef094d008a6ea134e19d343a21e721/paykit-sdk/tests/flows/public_read.rs). The host keeps the display name. A user can authorize a public payment during an own-service outage. [Recording after an outage](https://github.com/pubky/paykit-rs/blob/3fc11db321ef094d008a6ea134e19d343a21e721/paykit-sdk/tests/flows/offline_public/recording.rs) checks the original attempt. |
| Private Payment Lists (§§8.4–8.4.1) | [List version](https://github.com/pubky/paykit-rs/blob/3fc11db321ef094d008a6ea134e19d343a21e721/paykit-lib/src/list_version.rs) and [collection policies](https://github.com/pubky/paykit-rs/blob/3fc11db321ef094d008a6ea134e19d343a21e721/paykit-lib/src/collections.rs) | [`private_list_publications`](vectors/sealed.json), [`list_versions`](vectors/messages.json) | [Publication, lost answers and restore](https://github.com/pubky/paykit-rs/blob/3fc11db321ef094d008a6ea134e19d343a21e721/paykit-sdk/tests/flows/publishing.rs) covers reusable endpoints. The publisher needs a new sharing choice after restore. When the recipient holds an incoming list over an unreadable, deleted or divergent `payment_lists` record, it compares only the signed generation and counter. If another message has the same pair and different content, the wallet keeps the held list but does not report the authenticated writer. Automatic renewal with fresh single-use payloads still needs a wallet case. |
| Selling labels and sender authority (§§3.1–3.4) | [Scopes](https://github.com/pubky/paykit-rs/blob/3fc11db321ef094d008a6ea134e19d343a21e721/paykit-lib/src/scopes.rs) and [message kinds](https://github.com/pubky/paykit-rs/blob/3fc11db321ef094d008a6ea134e19d343a21e721/paykit-lib/src/kinds.rs) | [`payee_label_senders`](vectors/messages.json), [`payee_certificates`](vectors/documents.json) | [Seller and sibling-app authorization](https://github.com/pubky/paykit-rs/blob/3fc11db321ef094d008a6ea134e19d343a21e721/paykit-sdk/tests/flows/labels.rs) checks original signer authority. An unrequested payment receipt requires the plain selling scope. |
| Invitation delivery (§§3.3–3.4, 7.2) | The invite code and delivery hash are Switch transport metadata. The signed Paykit request uses the ordinary sender-scope checks. | No invitation-specific Paykit vector. | [Enrolled wallet tests](https://github.com/pubky/paykit-rs/blob/55c96d22330017436d5bda60d62a21e389125b19/paykit-sdk/tests/shared_settlement/invitations.rs) exercise request sending, flush and receive on Scripted and PostgreSQL. After a lost append answer, the same sealed request retried with a second valid code returns the original entry and append result. The second code has zero uses and admits a distinct request. A sibling wallet and a fresh restore of a backup taken before registration receive each request’s authenticated invitation hash and no hash for ordinary admission. A sender without the required scope is refused. |
| Extension intake, admission and recovery asks (§§3.3, 8.1, 9) | [Scope and kind checks](https://github.com/pubky/paykit-rs/blob/3fc11db321ef094d008a6ea134e19d343a21e721/paykit-lib/src/scopes.rs) | [`extension_app`](vectors/documents.json), [`multi_protocol_senders`](vectors/messages.json) | [Extension eviction and restore](https://github.com/pubky/paykit-rs/blob/3fc11db321ef094d008a6ea134e19d343a21e721/paykit-sdk/tests/flows/extensions.rs), [admission prerequisites](https://github.com/pubky/paykit-rs/blob/3fc11db321ef094d008a6ea134e19d343a21e721/paykit-sdk/tests/flows/spam/prerequisites.rs) and [re-send rules](https://github.com/pubky/paykit-rs/blob/3fc11db321ef094d008a6ea134e19d343a21e721/paykit-sdk/tests/flows/resend.rs). Test the dropped-reply mark and acknowledgment of its waiting-pool notice in one local commit before claiming that guarantee. An evicted payload may be unrecoverable. |
| Pending Allowances and the original acceptance (§8.3.1) | [Pending record binding](https://github.com/pubky/paykit-rs/blob/3fc11db321ef094d008a6ea134e19d343a21e721/paykit-lib/src/records/pending.rs) and [permanent records](https://github.com/pubky/paykit-rs/blob/3fc11db321ef094d008a6ea134e19d343a21e721/paykit-lib/src/records.rs) | [`allowance_proposals`](vectors/sealed.json), [`allowance_initial_ledger`](vectors/sealed.json), [`record_keys`](vectors/identifiers.json) | [Signed proposal and reply flows](https://github.com/pubky/paykit-rs/blob/3fc11db321ef094d008a6ea134e19d343a21e721/paykit-sdk/tests/flows/allowances.rs) exercises both proposer roles, conflict, discard, deletion and recreate. Both sides record P and Q. The approving Allower also creates the zero bound to the signed acceptance. Reopening can recover the original batch while its service generation is current and all three authenticated results remain available. A backup before local capture followed by replacement of a member can still leave the evidence unavailable. |
| Pending withdrawal after restore or a late acceptance (§8.3.1) | [Signed proposal members](https://github.com/pubky/paykit-rs/blob/3fc11db321ef094d008a6ea134e19d343a21e721/paykit-lib/src/bodies.rs) | [`allowance_proposals`](vectors/sealed.json) | [Proposer withdrawals](https://github.com/pubky/paykit-rs/blob/3fc11db321ef094d008a6ea134e19d343a21e721/paykit-sdk/tests/flows/allowances.rs) checks the original payer or seller app’s signed proposal creation, exact deletion on rejection, and original service key across an orderly move. A missing key holds the withdrawal. Other retirement sources still require qualification. |
| First grant, budget and debit (§8.3) | [Grant signatures](https://github.com/pubky/paykit-rs/blob/3fc11db321ef094d008a6ea134e19d343a21e721/paykit-lib/src/grant.rs) and [ledger and usage](https://github.com/pubky/paykit-rs/blob/3fc11db321ef094d008a6ea134e19d343a21e721/paykit-lib/src/allowances.rs) | [`executor_grant`](vectors/documents.json), [`failure_evidence`](vectors/allowance_usage.json) | [Same-wallet grants, funding, repeats and restored history](https://github.com/pubky/paykit-rs/blob/3fc11db321ef094d008a6ea134e19d343a21e721/paykit-sdk/tests/flows/allowance_executor.rs). One-time payments and eligible Billing Periods reserve the transfer amount, including rounding. Insufficient history, incomplete original authority or insufficient budget holds payment. |
| Repair and handoff (§8.3) | [Repair merge](https://github.com/pubky/paykit-rs/blob/3fc11db321ef094d008a6ea134e19d343a21e721/paykit-lib/src/allowances.rs) and [handoff binding and preservation](https://github.com/pubky/paykit-rs/blob/3fc11db321ef094d008a6ea134e19d343a21e721/paykit-lib/src/records.rs) | [`allowance_records`](vectors/sealed.json), [`signatures`](vectors/signatures.json) | The pure checks take evidence supplied by their caller. An enabled repair or a handoff to another executor requires complete usage and verified history, consent, exact conditional placement and durable evidence of application. Those positive paths remain unqualified. |
| Billing Periods, later destinations and quotes (§§7.2, 8.2) | [Period and amount rules](https://github.com/pubky/paykit-rs/blob/3fc11db321ef094d008a6ea134e19d343a21e721/paykit-lib/src/periods.rs) and [message bodies](https://github.com/pubky/paykit-rs/blob/3fc11db321ef094d008a6ea134e19d343a21e721/paykit-lib/src/bodies.rs) | [`details_rates`](vectors/periods.json), [`conversion_amounts`](vectors/messages.json), [`proof_members`](vectors/messages.json) | [Required seller, expiry and current senders](https://github.com/pubky/paykit-rs/blob/3fc11db321ef094d008a6ea134e19d343a21e721/paykit-sdk/tests/flows/period_payments.rs) and [restored ledger evidence](https://github.com/pubky/paykit-rs/blob/3fc11db321ef094d008a6ea134e19d343a21e721/paykit-sdk/tests/flows/allowance_executor.rs) cover signed later destinations. After pruning, a matching receipt still requires the correct seller scope, signed request, period, destination and proof fields. |
| Settlement marks and retained receipts (§§6, 8.1) | [Fixed policies](https://github.com/pubky/paykit-rs/blob/3fc11db321ef094d008a6ea134e19d343a21e721/paykit-lib/src/collections.rs) and [record values](https://github.com/pubky/paykit-rs/blob/3fc11db321ef094d008a6ea134e19d343a21e721/paykit-lib/src/records.rs) | [`settlement_marks`](vectors/sealed.json), [`policies`](vectors/identifiers.json) | [Concurrent credit and retained marks](https://github.com/pubky/paykit-rs/blob/3fc11db321ef094d008a6ea134e19d343a21e721/paykit-sdk/tests/flows/receipts.rs), [receipt-backed deletion](https://github.com/pubky/paykit-rs/blob/3fc11db321ef094d008a6ea134e19d343a21e721/paykit-sdk/tests/flows/deletions.rs) and [provider recovery](https://github.com/pubky/paykit-rs/blob/3fc11db321ef094d008a6ea134e19d343a21e721/paykit-sdk/tests/flows/provider_loss.rs). A one-time payee can publish an issued receipt from a verified deletion and predecessor in the same generation. Broader protected-family creation and put-back still require the incarnation and cursor evidence in wire Section 5. |
| Recovery reports, backups and ownership (§§2, 7.2–7.3) | [Original report signatures](https://github.com/pubky/paykit-rs/blob/3fc11db321ef094d008a6ea134e19d343a21e721/paykit-lib/src/recovery.rs) | [`recovery_report`](vectors/signatures.json), [`policies`](vectors/identifiers.json) | [Original authors and removals](https://github.com/pubky/paykit-rs/blob/3fc11db321ef094d008a6ea134e19d343a21e721/paykit-sdk/tests/flows/recovery_reports.rs), [multiple protocol owners](https://github.com/pubky/paykit-rs/blob/3fc11db321ef094d008a6ea134e19d343a21e721/paykit-sdk/tests/flows/mixed_protocols.rs) and [restore](https://github.com/pubky/paykit-rs/blob/3fc11db321ef094d008a6ea134e19d343a21e721/paykit-sdk/tests/flows/restore.rs). A verified report authenticates its original app’s commitments. Evidence for each debit or credit is still required. Backup checks are family-specific. They do not establish exhaustive validation of every stored value. |
